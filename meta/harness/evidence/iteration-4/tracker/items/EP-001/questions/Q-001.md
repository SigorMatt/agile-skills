## Question

What does the user operate to add a card and to do a review — a command-line tool run in a
terminal, a web page in a browser, or a library that other code calls?

## Options considered

- **A — a command-line tool.** Something like `recall add`, `recall review`, run in a terminal.
  Consequence: acceptance criteria become exact commands with exact output and exit codes, which
  is the easiest thing in this list to verify without a human watching. No browser, no server,
  nothing to install beyond the tool. The review session is text in a terminal.
- **B — a web page.** A local page you open in a browser. Consequence: nicer to review in, and
  the natural home if you ever want this on a phone. Costs a server process, a front end, and
  acceptance criteria that need a browser to decide — verification gets slower and less certain
  for the same behaviour.
- **C — a library.** A module other code imports; no user interface at all. Consequence: only
  useful if you are building the interface yourself. "Review due cards daily" stops being
  something the deliverable does and becomes something its caller does, which does not match how
  you described it.
- **Recommendation: A.** It is the smallest thing that delivers the whole outcome you described,
  and it makes every criterion checkable from a terminal. B remains reachable later on top of the
  same stored data; A does not close it off.

## Answer

[human] Command-line tool. I'll be sitting at a terminal doing this once a day, that's all it needs to be.
