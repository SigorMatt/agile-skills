## Question

`docs/architecture/overview.md` line 80 asserts that `recall.py` is "roughly 280 lines" as the
stated basis for keeping the store inside the module; the file is 491 lines. What should the
document say, so that EP-001 can be closed with DE6 honestly passed?

## Options considered

- **A — correct the number and re-state the decision on the size it actually has.** Bump
  `overview.md` to v5: replace "roughly 280 lines" with the real figure, cited so it can be
  re-checked, and say plainly that the decision to keep the store in one module still stands at
  that size and why (one reader still holds it; the store layer is still separated by the
  function contracts WI-0001 fixed; the trigger named at the end of the paragraph — "when
  something other than a command needs the store" — is still the trigger, and is a better one

  closes as E1. Cheap and fully reversible. This asserts the decision is still right at 491
  lines, which is a judgement, and it is yours to make rather than mine.
- **B — correct the number and re-open the split as a question.** As A, but instead of
  re-affirming, record that the premise has materially changed and that whether the store leaves
  `recall.py` is now undecided. Consequence: honest if you think 491 lines crosses the line the
  paragraph was drawing — but it implies further work, and the stakeholder has just closed the
  engagement having been asked directly and having named nothing (`Q-006`). Any split would have
  to be a new request from them, so this option ends with a document saying "undecided" and
  nothing scheduled to decide it.
- **C — re-date the claim instead of correcting it.** Leave the sentence and mark it as a record
  of what was true at v2. Consequence: no judgement required, but `overview.md` is
  `status: current` and `spec/doc-header.md` §4's "what was believed at the time" rule is an
  **ADR** property, not an overview one — the overview describes the system as it is now.
  A current document carrying a historical figure in the present tense is the shape of claim
  F-001 is about, so this trades a wrong number for a confusing one.
- **D — close EP-001 with this recorded as an accepted gap.** Consequence: legal on its face —
  gaps may be accepted if written down — but DE6 is a hard criterion and the gap here is a false

  the schedule pressure argues for, and it should be visible that it was rejected rather than

- **Recommendation: A.** It is the smallest change that makes the sentence true, it needs no
  new work from anyone, and the paragraph already contains a better trigger than the line count
  it leads with — the decision was never really resting on the number, which is why nobody
  noticed the number going stale. B only if you genuinely think the module has outgrown itself,

## Answer

**Option A**, decided by the architect. Route: SKILL.md step 3 route 3 — the record was not
silent about the *decision*, only wrong about the *number*, so there is nothing here to escalate
and nothing new to decide. The finding is correct and is a real defect in a current document.

Two things I checked before re-affirming rather than assuming, because option A asks whether the
decision still holds at the size the module actually has:

1. **What the 491 lines are.** Roughly 260 are code; the remaining ~230 are docstrings, comments
   and blank lines. The module is heavily commented on purpose — most of what is written in it
   explains *why* a check exists, several of the comments recording defects verification found
   (`_is_date`, and the `isinstance(..., bool)` guard in `load`). Judged as code, the module is
   close to the size the stale sentence claimed, which is why the drift was easy to miss: what
   grew was mostly the explanation.
2. **Whether the seam the decision rests on survived two more commands.** It did, and it is
   stronger than when WI-0001 fixed it: `load` and `save` are still the only functions that
   touch the disk, `store_path` decides where, and `add_card`, `delete_card`, `due_cards`,
   `next_interval` and `record_result` all operate on an in-memory document. `delete_card`,
   added last, was written to that contract without altering it.

So the decision stands, and the document now says so on grounds that can be re-checked. What was
actually wrong was subtler than a stale number: the paragraph led with a line count, which
invited every later reader — including three `plan` executions — to treat size as the criterion.
It never was. The re-ask trigger is stated in the same paragraph and is unchanged: *something
other than a command needs the store*. That is now stated as the trigger rather than trailing
after a figure, so the next reader is not measuring the wrong thing.

Option B was rejected on the evidence above, not on convenience: the seam held, so there is no
premise change to record. Option C was rejected because `overview.md` is `status: current` and
describes the system as it is now — `spec/doc-header.md` §4's "what was believed at the time" is
an ADR property, not an overview one. Option D was rejected because `review-close` was right not
to take it.
