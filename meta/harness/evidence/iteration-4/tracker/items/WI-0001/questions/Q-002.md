## Context

**WI-0001 — "add a card and have it persist" — round 1, question 2 of 2, and that is all of them
for now.** The frame is in `Q-001`.

This one is about where your cards actually live. AC5 already says the store must be a file a
person can open and read, and that its location is written down — that part is settled. What is
not settled is *which* file, and it is a question about your data rather than about the code:
it decides whether the cards you add follow you around the machine or belong to the folder you
happened to be standing in when you typed the command.

I am asking rather than choosing because getting it wrong is the kind of mistake that looks like
lost work. Someone who adds cards in one directory, then runs `recall` from another and sees an
empty pile, has no way to tell that their cards are safe somewhere else.

It also interacts with your "one flat pool" answer on the epic: a per-directory store would give
you several pools by accident, which is the thing you said you did not want.

## Question

Where should the card file live — one file in your home directory that you get wherever you run
the command, or a file in whichever directory you run the command from?

## Options considered

- **A — one file under your home directory**, at `~/.local/share/recall/cards.json` (the
  standard place on Linux for a program's own data, and honouring `XDG_DATA_HOME` if you have
  set it). Consequence: one pile, always the same one, from anywhere. It matches "one flat pool"
  literally. The path is longer to type when you want to look inside it, and if you want a
  second unrelated pile some day you cannot have one without a new feature.
- **B — one file in your home directory, plainly named**: `~/.recall.json`. Consequence: same
  behaviour as A and much easier to open by hand, which matters because AC5 exists so that you
  *can* open it. Slightly untidy by modern convention, and it is your home directory that gets
  the clutter.
- **C — a file in the current directory**, `./cards.json`, created where you run the command.
  Consequence: several piles, one per folder, and you choose which by choosing where you stand.
  Useful if you ever want to keep a project's cards with that project. Against it: it is the
  option where cards go missing, and it quietly contradicts the single pool you asked for.
- **Recommendation: B**, with `RECALL_FILE` respected if it is set so that any of these
  remains possible without a decision now. It gives you the single pile you asked for and keeps
  the file somewhere you can actually open and read, which is what AC5 is for. A is the tidier
  convention if you would rather the tool behaved like other Linux tools; C is the one I would
  argue against.

## Consequences

**How this was settled, stated plainly.** The stakeholder's reply is a deferral that authorises a
decision rather than one that withholds it, so `answer-questions` took move 1 of
`spec/question.md` §2: decide it under the deferral, and mark the question answered citing the
deferral as the basis. `answered-by` is `answer-questions`, not `human`, because the stakeholder
did not pick a path — they declined to, and the architect chose. Recording `human` here would
claim more than the record supports.

**The decision.** The card store is one JSON file. Its path is `RECALL_FILE` when that
environment variable is set and non-empty, and `~/.recall.json` otherwise — option B of the three
offered, with the `RECALL_FILE` override the recommendation mentioned. Option C, a file per
working directory, was rejected outright: it would have produced several pools by accident, which
contradicts the one flat pool the stakeholder asked for in `EP-001/Q-004`. Option A's XDG path
was rejected because AC5 exists so that the user *can* open the file by hand, and a two-directory
path defeats that purpose. The override is load-bearing rather than a convenience: it is what
lets every acceptance criterion in this epic be checked by running commands against a scratch
file instead of the checker's own home directory.
