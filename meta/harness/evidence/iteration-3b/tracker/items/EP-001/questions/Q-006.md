## Question

The three work items under this engagement are:

- **WI-0001 — Align markdown table columns, passing all other content through unchanged.**
  **Delivered.** Every column of a recognised table is padded to the display width of its widest
  cell, and everything that is not a recognised table comes back byte for byte — prose, headings,
  fenced code blocks, blockquoted tables, malformed tables, CRLF files, files with no final
  newline, and files containing bytes that are not valid UTF-8. Eleven acceptance criteria, all
  verified with evidence; closed `delivered`.

- **WI-0002 — Honour column alignment markers when aligning table cells.**
  **Delivered.** The colons in a table's delimiter row decide which side of a cell its padding
  falls on: left marker, padding right; right marker, padding left; centre marker, split, with the
  odd leftover space going to the right of the text as you chose. The markers themselves survive
  colon-for-colon — the filter adds none, removes none, moves none. Ten acceptance criteria, all
  verified with evidence; closed `delivered`.

- **WI-0003 — Leave a cell containing a line break at the left of its column.**
  **Delivered.** This is the item your last reply created. A cell whose text contains a break tag
  is written flush to the left of its column whatever that column's marker says, and it is still
  padded out to the column's full width so the closing pipes line up — which is what you asked for
  when we put that question to you. `<br>`, `<br/>`, `<br />`, `<BR>`, `<Br />` and `<br >` all
  count and all behave identically; a trailing backslash does not count, as you said it should not.
  The exemption is per cell, not per column: an ordinary cell sitting in the same column as an
  exempt one is still placed by the marker. Eleven acceptance criteria, all verified with evidence;
  closed `delivered`.

There are no other child items. No bug was ever filed, and nothing was dropped or left blocked.

Against your eight success measures for the engagement we believe all eight are met: ragged tables
come back with every line the same width and every column in the same place; a file with no table
comes back byte-identical; a diff of input against output changes lines only inside tables; running
it twice is the same as running it once; markers place the text, with your multiline exception; a
fenced block of pipes is untouched; a malformed table is untouched; and no line it writes ends in a
space or a tab.

**Do you accept this engagement as it stands?**

Three things you should weigh first, because each is a place where what we built and what you
pictured could still differ. None of them was raised at the last sign-off; all three are new with
`WI-0003`.

1. **A cell that merely *mentions* `<br>` is exempted too.** The rule looks at the cell's text and
   nothing else, so a cell reading `` use `<br>` for a line break ``, or a cell in a table
   documenting HTML tags, is left flush-left exactly as a cell that really contains a break would
   be. We chose a rule you can predict without reading the code over one that tries to tell the two
   apart, and this is its cost.
2. **"Top-left" was read as "left".** A pipe-table cell is one physical line in the source, so there
   is no "top" for the text to sit at; we implemented the "left" half and did nothing about the
   "top". If you meant something more — a cell actually split across lines in the output — that is
   not what was built, and it is not a small change.
3. **A cell containing both a `<br>` and an escaped pipe (`\|`) is not specified.** How an escaped
   pipe is measured and re-emitted was never decided for any cell — it is an open design question
   carried since `WI-0001` — and the exemption does not settle it. Such a cell will do something,
   consistently; nobody has written down what, and nobody has checked it against a renderer.
