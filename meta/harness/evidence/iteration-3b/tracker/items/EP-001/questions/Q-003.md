## Context

This is question 3 of 3 that intake is asking about EP-001, "Pretty-align markdown tables from a
stdin filter", in one round; they are meant to be read together and answered in one sitting.
This is the last of them.

You said the filter should align "its tables" and leave non-table content untouched. That
sentence draws a line through the input, and everything the tool does depends on where the line
falls. "Markdown" has no single table syntax: the common one is GitHub-flavoured pipe tables,
which look like this —

```
| Name | Qty |
|------|----:|
| bolt | 12  |
```

— but the pipes at the start and end of each line are optional in that dialect, some documents
use reStructuredText-style grid tables drawn with `+---+` borders, and some tools support tables
with multi-line cells or merged cells.

There is also the question of text that *looks* like a table but is not meant to be one. A
fenced code block can contain pipe characters laid out in rows; so can a quoted email, a log
excerpt, or a line of prose about the `|` operator. Reformatting those would be exactly the
"non-table content" damage you asked us to avoid, but recognising them costs us work we should
only do if you want it.

We cannot answer this from any document: the repository is empty and there is no corpus of your
files to look at.

## Question

Which input should the filter treat as a table it may reformat — and, specifically, must it
recognise fenced code blocks and leave table-looking lines inside them alone?

## Options considered

- **A —** GitHub-flavoured pipe tables only, requiring a leading and trailing pipe on every line,
  and no awareness of fenced code blocks. Consequence: the simplest rule and the easiest to
  predict; but a pipe-delimited row inside a ``` fence would be reformatted, and any table you
  wrote without the outer pipes would be silently ignored.
- **B —** GitHub-flavoured pipe tables with the outer pipes optional, plus fenced-code-block
  awareness so that anything between ``` or ~~~ fences is passed through untouched. Consequence:
  matches what most markdown tools and editors do, so the filter's idea of a table matches the
  renderer's; costs a little more work, because the filter must track fence state as it reads.
- **C —** B, plus at least one non-pipe table syntax — grid tables, or simple/rst tables.
  Consequence: covers documents the other options would leave ragged; substantially more work,
  and it makes "leave non-table content untouched" harder to guarantee, because the patterns that
  identify those tables match more innocent text.
- **D —** Narrower than A: only reformat a table when it is unambiguous, and pass through
  anything the filter is not sure about. Consequence: safest for your existing documents, and it
  makes the failure mode "did nothing" instead of "mangled something"; but it means some of your
  real tables come back untouched with no indication why.
- **Recommendation:** Ours is **B**. It is the dialect people actually write, and the fenced-code
  exclusion is the one case where getting it wrong damages content rather than merely declining
  to help. This is our preference, not a decision — if your documents contain grid tables, or if
  you would rather have the strict rule in A, say so and that is what we will build.

## Answer

[human] Ordinary pipe tables, the kind you showed — that is all I write. I have never written one
of those grid tables in my life and I do not want the tool looking for them. Code blocks must be
left completely alone; a fenced block full of pipes is not a table and touching it would be the
worst thing this could do. Where it cannot tell, it should pass the text through and do nothing.
