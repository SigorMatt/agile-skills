## Context

You asked us for this:

> A filter that reads markdown on stdin and pretty-aligns its tables: pads columns, honours
> alignment markers, leaves non-table content untouched.

Then, when we asked what else mattered, you told us three things that shaped everything after:

> Anything that is not a table comes out exactly as it went in, byte for byte — that is the part I
> care about most, and I will stop using it the first time it edits a paragraph. If a table is
> broken — a row with the wrong number of cells, a missing separator line — leave it alone rather
> than guess what I meant; I would much rather it did nothing than mangled something. And no
> trailing whitespace at the end of any line it writes: columns are as wide as the widest cell in
> them, with no maximum, but nothing hangs off the right-hand edge.

You also said where it had to run — *"me, at my own machine, piping a file through it from my
editor before I commit… a thing I can just run, with no build step and nothing to install first"* —
and what it had to recognise: *"Ordinary pipe tables, the kind you showed… Code blocks must be left
completely alone; a fenced block full of pipes is not a table and touching it would be the worst
thing this could do. Where it cannot tell, it should pass the text through and do nothing."*

Every work item under this engagement has now stopped, no question is open anywhere in it, and
nothing is left that we can run. That is the moment this question exists for: before we write down
that the engagement is over, you get to say whether you agree that it is.

**What you can actually do with it today.** It is one file, `mdtab.py`, at the root of the
repository. There is nothing to install and nothing to build:

```
python3 mdtab.py < notes.md > notes.tidy.md      # or, via its shebang:
./mdtab.py < notes.md > notes.tidy.md
```

It reads standard input, writes standard output, and exits 0. Running it a second time over its own
output changes nothing.

## Question

The two work items under this engagement are:

- **WI-0001 — Align markdown table columns, passing all other content through unchanged.**
  **Delivered.** Every column of a recognised table is padded to the display width of its widest
  cell, and everything that is not a recognised table comes back byte for byte — prose, headings,
  fenced code blocks, blockquoted tables, indented-inconsistently blocks, malformed tables, CRLF
  files, files with no final newline, and files containing bytes that are not valid UTF-8. All
  eleven of its acceptance criteria were verified with evidence and it closed as `delivered`.

- **WI-0002 — Honour column alignment markers when aligning table cells.**
  **Delivered.** The colons in a table's delimiter row now decide which side of a cell its padding
  falls on: left marker, padding to the right; right marker, padding to the left; centre marker,
  split, with the odd leftover space going to the right of the text as you chose. The markers
  themselves survive colon-for-colon — the filter adds none, removes none and moves none. All ten
  of its acceptance criteria were verified with evidence and it closed as `delivered`.

There are no other child items: no bug was ever filed, and nothing was dropped or left blocked.

Against your success measures for the engagement, we believe all eight are met — ragged tables come
back with every line the same width and every column in the same place; a file with no table comes
back byte-identical; a diff of input against output changes lines only inside tables; running it
twice is the same as running it once; markers place the text; a fenced block of pipes is untouched;
a malformed table is untouched; and no line it writes ends in a space or a tab.

**Do you accept this engagement as it stands?**

Two things you should weigh before answering, because they are the places where what we built and
what you pictured could still differ:

1. **A centred column that cannot split evenly leans left.** `| ab  |`, not `|  ab |`. That is what
   you asked for, and it is now in every centred column of every file you run this over.
2. **Column widths are measured in terminal columns, not characters.** CJK text and emoji count as
   two, combining accents as zero. This makes tables line up on screen; it also means a row
   containing them has a different number of *characters* from its neighbours, so a tool that counts
   characters will disagree that the table is aligned.

## Answer

[human] Not quite as it stands — one thing before I sign. A cell with a line break or a `<br>` in
it should just sit top-left, plain, whatever the column marker says; markers are for normal cells,
not for those. The two things you flagged are both fine by me: leaning left when it cannot split
evenly is what I asked for, and measuring by what I see on screen is the whole point. Fix the
multiline cells and we are done.

## Cross-answer check

Checked against: WI-0002/Q-001; EP-001/Q-001; EP-001/Q-003; WI-0001/Q-001; WI-0001/Q-003;
WI-0001/Q-004.

- `WI-0002/Q-001` — **conflicts.** That answer's second half says: *"the alignment marker decides
  everything. Whatever the marker says, that is where the text sits in the cell — every row, every
  column, no exceptions."* This one says: *"A cell with a line break or a `<br>` in it should just
  sit top-left, plain, whatever the column marker says; markers are for normal cells, not for
  those."* An exemption for a class of cell cannot stand beside "no exceptions", and the earlier
  sentence is not merely quoted in the record — it is recorded as ADR-0005 decision 3, *"No content
  cell is exempt"*, and as a paragraph of `docs/product/vision.md` v4 carrying `[src:
  WI-0002/Q-001]`. Superseding a decision of theirs is not ours to do (`spec/question.md` §4,
  third condition), and the reconciliation they offered in the same breath — *"markers are for
  normal cells, not for those"* — is a reading of their own earlier sentence that we would be
  grading if we accepted it silently. Escalated as `EP-001/Q-005`, which quotes both by ID and asks
  which wins. This answer's *first* half is a different matter and settles nothing new: their
  endorsement of the lean-left remainder restates the choice they already made in `WI-0002/Q-001`,
  and nothing about that is in tension.
- `EP-001/Q-001` — compatible. *"no trailing whitespace at the end of any line it writes: columns
  are as wide as the widest cell in them, with no maximum, but nothing hangs off the right-hand
  edge."* Placing an exempted cell's text at the left of its column moves padding to the right of
  the text, which is inside the cell and before its closing pipe — the same place WI-0001 already
  puts it — so no composed line gains trailing whitespace and no column's width changes
  [src: ADR-0005].
- `EP-001/Q-003` — compatible, and pointing the same way. *"Where it cannot tell, it should pass
  the text through and do nothing."* A cell whose content is not a plain run of text is exactly a
  case where the tool cannot tell where the text "sits", and this answer resolves it towards doing
  the least.
- `WI-0001/Q-001` — compatible, and reaffirmed here in as many words: *"measuring by what I see on
  screen is the whole point."* Display width remains how a column is measured [src: ADR-0003].
- `WI-0001/Q-003` — compatible. *"One space each side, always."* This answer is about where a
  cell's text sits inside the column's width, not about the two spaces either side of it, which
  are untouched [src: ADR-0005].
- `WI-0001/Q-004` — compatible. *"Dashes all the way across, pipe to pipe. That row is a rule
  under the header, not a row of content."* A delimiter cell holds no text and can hold no `<br>`,
  so the exemption cannot reach the row this answer governs [src: ADR-0004].

`EP-001/Q-002` (the runtime constraint) and `WI-0001/Q-002` (indented tables) were read and are
not listed: neither says anything about what is inside a cell or where its text sits, and naming
them would pad the check rather than perform it.
