## Context

This is question 1 of 4 that refinement is asking about WI-0001, "Align markdown table columns,
passing all other content through unchanged", in one round. They are meant to be read together
and answered in one sitting.

You have already told us what the tool must not touch, and that decided a great deal. These four
are about the one thing left: exactly what a tidied table looks like when it comes back. They
matter now because `verify` — the stage that decides whether we built what you asked for — cannot
ask you anything, and can only check what these criteria say.

You said a column should be *"as wide as the widest cell in them, with no maximum"*
[src: EP-001/Q-001]. That is clear for plain ASCII, where one character takes one column on
screen. It stops being clear as soon as a cell contains anything else, and markdown tables in
real documents often do:

- **Wide characters.** CJK text, and most emoji, occupy two terminal columns each but are one
  character. A cell containing four Chinese characters is 4 characters long and 8 columns wide.
- **Combining marks.** `é` can be one character or two (`e` plus a combining accent) depending
  on how your editor saved it; the second form is 2 characters and 1 column wide.

So "the widest cell" has two different answers, and they disagree about how much padding to add.
If we count characters, a table with CJK in it comes back looking crooked in your terminal even
though every row has the same number of characters. If we count terminal columns, that table
lines up on screen, but the rows no longer contain the same number of characters, and a tool that
counts characters — including a naive diff or a future version of this one — will disagree that
it is aligned.

We cannot settle this from anything on record. It depends on what is actually in your documents,
and on where you look at them.

## Question

When a table cell contains characters that are not plain ASCII, what should the tool make equal
across the rows of a column — the number of characters, or the number of columns the text
occupies on a terminal?

## Options considered

- **A — Count characters.** Padding is computed from the number of Unicode characters in the
  cell. Consequence: simple, has no lookup tables in it, and behaves identically whatever
  terminal or font you use. A table containing CJK or emoji will have equal-length rows but will
  not look aligned on screen. If your tables are all Latin text, this and option B are the same
  thing and you will never see a difference.
- **B — Count terminal columns.** Padding is computed from display width, so East Asian wide
  characters count as 2 and combining marks as 0. Consequence: CJK and emoji tables look right in
  a terminal and in most editors. It costs a width table (Python ships one, so no dependency),
  and the output's rows have unequal character counts, which makes "every row is the same length"
  false as a way of checking the tool — we would write the criteria in terms of display width
  instead. It is also not universally correct: emoji width in particular varies between
  terminals, so some cases will still look off by one.
- **C — Count characters, and say so.** As A, and we record in the item that non-ASCII tables are
  known not to align visually, so nobody later reports it as a bug. Consequence: same behaviour
  as A, but the limitation is written down where you and we can both find it.
- **Recommendation:** ours is **A or C**, and which one only depends on whether you ever put
  non-Latin text in a table. If you do not, A is strictly simpler and you lose nothing. If you
  occasionally might, C is the same code with the limitation on the record. We would pick B only
  if aligning CJK is something you actually need, because it makes the tool's own definition of
  "aligned" harder to check. This is our preference and not a decision — choose against it
  freely, and "I only ever write ASCII" is a complete answer.

## Answer

[human] It has to line up on the screen — that is the entire reason I want this tool, so make the
columns equal in what I see, not in some count I never look at. I write English almost all the
time, but names with accents turn up and I paste an emoji into a status column more often than I
would like to admit, and those are exactly the tables that come out crooked today. If a rare emoji
is off by one in some terminal I will live with it.
