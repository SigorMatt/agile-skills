## Context

This is question 4 of 4 that refinement is asking about WI-0001, "Align markdown table columns,
passing all other content through unchanged", in one round. This is the last of them.

Every pipe table has a second line made of dashes — the delimiter row that tells the renderer
where the header stops. AC2 of this item says every column must start at the same character
offset on **every** row of the table, and the delimiter row is one of those rows, so the tool has
to decide what to write there. There are two reasonable answers and the criteria do not currently
choose between them:

```
| Name | Qty |          | Name | Qty |
|------|-----|          | ---- | --- |
| bolt | 12  |          | bolt | 12  |
```

On the left the dashes run the full width of the column, pipe to pipe. On the right the delimiter
cell is padded like any other cell, with a space either side of a run of dashes. Both render
identically; both satisfy "the columns line up"; they produce different files.

This is separate from question 3 — that one is about the cells with your text in them, this one
is about the row that has no text in it — and it is separate from WI-0002, which will decide
where the alignment colons go once markers are in play. What is being asked here is only the
appearance of a delimiter row that carries no marker at all.

## Question

In the output, should the delimiter row's dashes fill the whole column from pipe to pipe, or
should they be padded like an ordinary cell?

## Options considered

- **A — Dashes fill the column.** `|------|-----|`. Consequence: the delimiter row is visually a
  solid rule under the header, which is what most people draw by hand and what the example in the
  original question shows. It reads as a separator rather than as a row.
- **B — Dashes padded like a cell.** `| ---- | --- |`. Consequence: one uniform rule for every
  row, which makes the tool's behaviour easier to state and to test — every cell, on every row,
  is padded the same way. It is what several markdown formatters emit. The table looks slightly
  more open in source.
- **C — Preserve whichever the input used.** Consequence: smallest diff on a document that is
  already consistent; needs a tie-break rule when a file's tables disagree with each other, which
  is the kind of guessing you asked us not to do.
- **Recommendation:** ours is **A**, because it is what your example showed and because a solid
  rule under the header is what the delimiter row is *for*. This is our preference and not a
  decision — B is arguably cleaner as a rule, and if you would rather have one padding rule with
  no exceptions, say so. That is all four questions for now.

## Answer

[human] Dashes all the way across, pipe to pipe. That row is a rule under the header, not a row of
content, and it should look like one — the padding rule I just gave you is about cells with my
words in them.
