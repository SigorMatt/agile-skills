## Context

This is question 2 of 4 that refinement is asking about WI-0001, "Align markdown table columns,
passing all other content through unchanged", in one round. They are meant to be read together
and answered in one sitting.

You said the tool should handle *"ordinary pipe tables, the kind you showed"* [src: EP-001/Q-003],
and the example you were shown starts each line hard against the left margin. From that, and from
*"where it cannot tell, it should pass the text through and do nothing"*, we wrote the recognition
rule in ADR-0002: a line is part of a table only if it begins with `|` and ends with `|`.

Taken literally, that rule ignores two shapes of table that are common in hand-written markdown
and are unambiguously tables:

```
1. First step:

   | flag | meaning |
   |------|---------|
   | -v   | verbose |
```

— a table indented under a list item, which markdown requires to be indented in order to stay
inside the list; and

```
> | flag | meaning |
> |------|---------|
> | -v   | verbose |
```

— a table inside a blockquote, where every line carries a `> ` prefix.

Both are real tables that a renderer will render as tables. Under the rule as it stands, the tool
would silently leave both of them ragged, and you would have no way to tell that from a tool that
was simply not working. That is a different thing from "it could not tell": here it can tell
perfectly well, and we would be declining anyway because of where the line starts.

Recognising them is not free. It means the tool has to work out that every line of the block
shares the same prefix, strip it, align what is left, and put the prefix back — and that prefix
has to be reproduced exactly or your byte-for-byte rule is broken for the part of the line the
tool did not compose. Whether that work is worth doing depends entirely on whether you write
tables in those places.

## Question

Should the tool tidy a table that does not start at the left margin — one indented under a list
item, or one inside a blockquote — or leave any such table alone?

## Options considered

- **A — Left margin only.** A table is only recognised when its lines begin with `|` in column
  one. Consequence: the simplest and safest rule, and the one already written into ADR-0002. Any
  table you write inside a list or a blockquote is never tidied, silently. If you do write them,
  you will notice this as "it ignores some of my tables".
- **B — Allow a uniform indent.** A block whose lines all share the same run of leading spaces is
  recognised, aligned, and re-emitted with that same indent. Consequence: covers tables in lists,
  which is the common case, for a small amount of extra work. Blockquoted tables are still
  ignored. A risk to be aware of: four or more leading spaces is also markdown's indented-code
  syntax, so this option means the tool must decide that a four-space-indented pipe block is a
  table rather than code — we would need to pick one, and would take the same conservative line
  as everywhere else.
- **C — Allow any uniform line prefix.** As B, but the shared prefix may also contain `>`
  characters, so blockquoted tables are covered too. Consequence: covers every case we can think
  of. It is the most machinery, and the most ways to get the reconstruction of the prefix subtly
  wrong on a line the tool rewrites, which is the one class of bug your byte-for-byte rule is
  there to prevent.
- **Recommendation:** ours is **A**, unless you know you write tables inside lists — in which
  case B. Our reasoning is that A is what ADR-0002 already says, it cannot damage anything, and
  widening later is additive: turning A into B or C only changes the behaviour of input that is
  currently passed through untouched, so nothing we build now would have to be undone. This is
  our preference and not a decision; if you write tables in lists or quotes often, say so and we
  will do the work.

## Answer

[human] Tables under a numbered list are all over my notes — that is half of what I write, so yes,
tidy those. Quoted ones I have never written and do not expect to, so do not spend anything on
them. Whatever the indent was, put it back exactly as it was.

## Cross-answer check

Checked against: EP-001/Q-003; EP-001/Q-001.

- `EP-001/Q-003` — compatible, and it is the one that needed looking at. It says *"code blocks
  must be left completely alone"* and *"where it cannot tell, it should pass the text through and
  do nothing"*. Neither is contradicted: the protection they named is for a **fenced** block,
  which ADR-0003 decision 1 keeps exactly, and an indented pipe table is a case the tool can tell,
  not one where it cannot. The residue — a pipe table inside an *indented* code block, which this
  tool cannot distinguish — is recorded in ADR-0003 as an accepted risk of the option they chose,
  rather than settled as though they had spoken to it.
- `EP-001/Q-001` — compatible and mutually reinforcing: *"exactly as it went in, byte for byte"*
  is what makes reproducing the indent exactly mandatory, and this answer says the same thing in
  their own words — *"put it back exactly as it was"*.

This answer supersedes a decision of **ours**, not one of theirs: ADR-0002 decision 2 required a
table to start in column one. That ADR invited the question and `spec/question.md` §4 requires the
stakeholder's authorisation before an ADR is superseded; this answer is that authorisation, given
on a question that quoted the rule it changes.
