## Context

This is question 3 of 4 that refinement is asking about WI-0001, "Align markdown table columns,
passing all other content through unchanged", in one round. They are meant to be read together
and answered in one sitting.

This one is about the literal characters the tool puts in your file, and it is being asked
because the acceptance criteria as they stand do not pin it down. They say every row of a table
must be the same length and every column must start at the same offset. Both of these outputs
satisfy that, and they are not the same document:

```
| Name | Qty |          |Name|Qty|
|------|-----|          |----|---|
| bolt | 12  |          |bolt|12 |
```

The left one is what the example you were shown looks like: one space between the pipe and the
text on each side of every cell. The right one is just as "aligned" by the letter of the
criteria, and would show up in every diff of every file you ran the tool over.

You already told us one thing about the shape of the output — *"no trailing whitespace at the
end of any line it writes"* [src: EP-001/Q-001] — which is why we are asking about the rest of it
rather than assuming. This is also the decision that determines how big the diff is the first
time you run the tool over an existing document: whichever convention we pick, every table you
already have that does not match it gets rewritten.

## Question

How much space should the tool put between a cell's pipes and its text — one space on each side,
or none?

## Options considered

- **A — One space on each side of every cell.** `| bolt | 12   |`. Consequence: matches the
  example in the original question, matches what GitHub and most markdown formatters emit, and
  is the most readable in a raw editor. Every column ends up two characters wider than its
  content needs.
- **B — No padding spaces.** `|bolt|12  |`. Consequence: the narrowest possible table, which
  matters if you have many columns and a hard line-length habit. It is harder to read in source,
  which is the thing this tool exists to improve.
- **C — Preserve whatever the input used.** Consequence: the smallest diff the first time you
  run it, because a table already in your preferred style is only re-padded, not restyled. It
  needs a rule for what to do when a table's own rows disagree with each other, which they very
  often do in exactly the ragged tables this tool is for — so it turns one clear rule into a
  guess, which is the shape you asked us to avoid.
- **Recommendation:** ours is **A**. It is what your own example showed, it is what other tools
  produce so a document stays consistent if anything else ever touches it, and it is the most
  readable in the place you actually read it. This is our preference and not a decision — B is a
  perfectly good answer if you want the tables narrow.

## Answer

[human] One space each side, always. The cramped version is unreadable and it is the readability I
am paying for; a couple of extra characters per column costs me nothing. I do not care how big the
first diff is — one big tidy-up and then everything is consistent forever.

## Cross-answer check

Checked against: EP-001/Q-001; WI-0001/Q-004.

- `EP-001/Q-001` — compatible: *"no trailing whitespace at the end of any line it writes"*
  constrains where a line **ends**, and the closing space of the last cell sits before that
  cell's closing pipe, so a composed line still ends with `|`. Nothing hangs off the right-hand
  edge.
- `WI-0001/Q-004` — compatible, and reconciled by the stakeholder themselves in the same round
  rather than by us: *"the padding rule I just gave you is about cells with my words in them"*.
  Cells are padded; the delimiter row is not.
