## Context

This is question 2 of 2 that refinement is asking about **WI-0003**, *"Leave a cell containing a
line break at the left of its column"*, in this round, and it is the last one — there is nothing
else we need from you on this item. Question 1 asked *which* cells are exempt; this one asks what
an exempt cell actually looks like coming out.

You said such a cell should *"just sit top-left, plain"* [src: EP-001/Q-004]. "Top-left" tells us
where its text goes: hard against the left of its column. "Plain" is the word we cannot act on,
because it has two readings and they produce visibly different files.

Everything in a tidied table sits inside a column of a fixed width. A left-placed cell puts its
text first and the leftover spaces after it, before the cell's closing space and pipe — which is
exactly what WI-0001 already does for every column with no marker. The question is whether an
exempt cell keeps those leftover spaces.

Here is the whole of it. A centred column, four rows, one of which contains a `<br>`:

```
padded to the column's width          not padded
| Task    |            Notes             |     | Task    |            Notes             |
|:-------:|:----------------------------:|     |:-------:|:----------------------------:|
| deploy  | build<br>test<br>ship        |     | deploy  | build<br>test<br>ship |
| review  |            ready             |     | review  |            ready             |
| ship    |             ok               |     | ship    |             ok               |
```

On the left every line of the table is the same width and the closing pipes line up, which is the
thing you asked this tool for. On the right the exempt row is shorter than its neighbours and its
closing pipe sticks in.

You have said two things that point at the left-hand version, which is why we are not treating
this as wide open: *"columns are as wide as the widest cell in them"* [src: EP-001/Q-001], and
your reason for wanting the tool at all — *"it has to line up on the screen"* [src: WI-0001/Q-001].
But neither was said about this case, "plain" could honestly mean "no padding at all", and we
would rather ask you once than write a criterion on our reading of one word.

Two things this question is **not** asking, because they are already settled and we do not want
to reopen them: the column's width is unchanged either way — an exempt cell is still measured
like any other and can still be the widest cell in its column — and the one space either side of
every cell's text stays [src: WI-0001/Q-003].

## Question

Does a cell that is exempt from its column's marker still get padded out to the column's width,
so that the table's lines stay the same length — or does it end right after its text, leaving that
row short?

## Options considered

- **A — Still padded, with the leftover spaces after the text.** Consequence: the left-hand table
  above. Every line of the table stays the same width, every closing pipe lines up, and the row
  containing a `<br>` is laid out exactly like a row in an unmarked column — which is behaviour
  you have already seen and accepted from WI-0001. The exemption then means only *"the marker does
  not move this cell's text"*, and nothing else about the table changes.

- **B — Not padded; the cell ends after its text.** Consequence: the right-hand table above. The
  exempt row is shorter than the others and its closing pipe does not line up with theirs. Choose
  this if by *"plain"* you meant the tool should stop touching such a cell altogether rather than
  merely stop aligning it. It is a coherent thing to want — it makes the exemption visible in the
  source, so you can see at a glance which cells the tool has left alone — but it does cost you
  the ragged edge this tool exists to remove, on those rows.

- **C — Not padded, and the whole row left byte-for-byte as you typed it.** Consequence: stronger
  than B — the *other* cells in that row keep whatever spacing they had too, so one `<br>`
  anywhere in a row exempts the entire row from tidying. Choose this if what you want is "hands
  off any row I put a line break in". The cost is that the row's other columns then disagree with
  the rest of the table as well, not just the one cell.

- **Recommendation (ours, not yours to inherit):** **A**. It is the only one of the three that
  keeps *"columns are as wide as the widest cell in them"* [src: EP-001/Q-001] true of every row,
  and it reads to us as what *"plain"* was contrasting with — placed by a marker, versus laid out
  the ordinary way. B and C are both real answers and neither is a problem for us to build; if
  what you wanted was for the tool to visibly keep its hands off those cells, say so and we will
  write that instead. We say this last and mark it as ours because it is your file that ends up
  looking one way or the other.

## Answer

[human] Pad it — the left-hand table. The closing pipes lining up is the whole reason I want this
tool, and I'd be annoyed if one `<br>` in a row put a kink in the right-hand edge. By "plain" I
meant only that the marker shouldn't push the text around; everything else about that cell stays
ordinary.
