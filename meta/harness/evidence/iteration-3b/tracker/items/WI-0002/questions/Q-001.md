## Context

This is question 1 of 1 that refinement is asking about WI-0002, "Honour column alignment markers
when aligning table cells", in this round. It is the only one — everything else this item needed
turned out to be answered already, either by you or by a decision recorded while WI-0001 was
built, and the list of what was settled and where is in
`tracker/items/WI-0002/artifacts/refinement-qa.md`.

WI-0001 shipped: the filter pads every column to the width of its widest cell and puts all the
padding on the right, because nothing yet told it to do otherwise. This item is the "honours
alignment markers" half of your original sentence — the colons in the delimiter row now decide
which side the padding goes on. Left marker, padding on the right; right marker, padding on the
left. Those two are unambiguous.

A **centre** marker (`:---:`) is not, and the criteria as written do not choose. Centring splits
the padding between the two sides, and when the number of spaces to split is odd, one side gets
one more than the other. There is no way to avoid picking a side; there is only the question of
which.

Concretely, with a centred column three display columns wide holding the text `ab`:

```
| Item |  Q  |          | Item |  Q  |
|------|:---:|          |------|:---:|
| bolt | ab  |          | bolt |  ab |
```

On the left the leftover space is on the right of the text; on the right it is on the left. Both
render identically in any markdown renderer — the difference is only in the source file you read,
which is the thing this tool exists to make readable. Whichever you pick, the rule is applied the
same way to every centred cell in every table, so your files stay internally consistent.

This is not about how much padding there is: a column is still as wide as its widest cell, with
no maximum, exactly as you said [src: EP-001/Q-001]. It is only about where the one leftover
space goes. And it is measured in what you see on screen, not in a character count, following
your answer about lining up [src: WI-0001/Q-001].

That is all of them for now.

## Question

When a centred column has an odd number of leftover padding spaces to split between the two
sides of a cell's text, should the extra space go to the **left** of the text or to the
**right**?

## Options considered

- **A — The extra space goes on the right.** The text sits one column left of true centre; the
  rule is "half the leftover, rounded down, on the left". Consequence: a centred cell's text
  starts at the same place as, or to the left of, where it would if the column were not centred,
  so short cells stay closer to the left edge where your eye already reads the rest of the table.
  It is also the same direction as every other column in the file, all of which pad on the right.
- **B — The extra space goes on the left.** The text sits one column right of true centre; the
  rule is "half the leftover, rounded down, on the right". Consequence: centred text is pushed
  as far right as the rounding allows, which makes a centred column stand out more distinctly
  from its left-aligned neighbours. Nothing else in the file behaves this way.
- **C — Something conditional** — alternate the side, or match whichever side the input already
  had. Consequence: the output stops being predictable from the input's content alone, and a
  document's tables can disagree with each other. It also means the filter's output would not
  always be stable when run twice, which breaks the guarantee that running it again changes
  nothing. We are recording this option to be complete, not because we think it is viable.
- **Recommendation:** ours is **A**. That is this team's preference, not a decision — it is a
  weak preference resting only on consistency with the padding direction everywhere else in the
  tool, and B is an entirely reasonable answer if you would rather a centred column read as
  visibly different. If you have no view either way, say so and we will record A as an
  assumption made on your behalf rather than as your decision.

### On consuming the answer — `answer-questions`

The reply has two halves. The first chooses option A. The second — *"the alignment marker decides
everything. Whatever the marker says, that is where the text sits in the cell — every row, every
column, no exceptions"* — was unprompted, and it is the half that had to be checked.

- `EP-001/Q-001` — **compatible**. *"no trailing whitespace at the end of any line it writes:
  columns are as wide as the widest cell in them, with no maximum, but nothing hangs off the
  right-hand edge."* Neither half of this answer changes a column's width, and both put the
  padding inside the cell, before its closing pipe, so no composed line gains trailing whitespace
  [src: ADR-0005].
- `WI-0001/Q-001` — **compatible**. *"make the columns equal in what I see, not in some count I
  never look at."* The leftover being split, and the offsets the marker decides, are measured in
  display width, not in characters [src: ADR-0003].
- `WI-0001/Q-003` — **compatible**. *"One space each side, always."* Both halves move padding only
  within the column's `width` characters; the one space either side of the cell text is untouched,
  so a cell is still `|`, space, padding, text, padding, space, `|` [src: ADR-0005].
- `WI-0001/Q-004` — **compatible**, and this is the pair worth stating rather than assuming.
  *"Dashes all the way across, pipe to pipe. That row is a rule under the header, not a row of
  content."* Read at its widest, *"every row … no exceptions"* would reach the delimiter row and
  contradict it. It does not, and the reconciliation is the stakeholder's own and needs no ruling
  from us: the sentence's subject is *"where the text sits in the cell"*, and by their own words
  the delimiter row is not a row of content — it has no text to place. What that row does with a
  marker's colons was separately decided as ADR-0004 decision 1, which preserves them. So the two
  answers are about different rows, and neither was narrowed to fit the other. Recorded at length
  because a later reader who meets these two sentences side by side will otherwise reach for a
  conflict that is not there — and because if some future answer does make the delimiter row's
  own layout a live question, that is the moment to put both of these to their author rather than
  to decide it here.

One further reading is the team's and not theirs, and is marked as such rather than folded in: a
column with **no** marker has no marker saying anything, so *"every column"* does not reach it and
WI-0001's right-hand padding stands [src: WI-0002 AC4; ADR-0005]. That changes no
behaviour and contradicts nothing they have said, which is why it was recorded in ADR-0005 rather
than put back to them.

## Answer

[human] Put the extra space on the right. When it cannot sit dead centre I want the text leaning
towards the side I read from, and it matches the way the rest of the file pads. While you are on
this: the alignment marker decides everything. Whatever the marker says, that is where the text
sits in the cell — every row, every column, no exceptions.
