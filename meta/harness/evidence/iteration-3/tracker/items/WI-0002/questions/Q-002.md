## Context

WI-0002, refinement round 1, question 2 of 2, and that is all of them for now.

You told us that a table written without the outer bars is still a table and must still line up,
and that whichever way you wrote it is the way it stays: *"I only want the spacing changed, never
the punctuation"* (`WI-0001/Q-002`). mdtab does that today. Right- and centre-alignment collide
with it in exactly one place, and the collision is not something we can resolve from anything you
have said.

Right-aligning a cell means putting the padding *before* the text. For every column but the first
that padding sits between two `|` characters and nobody notices. For the **first** column of a
table you wrote **without** a leading `|`, there is no `|` in front of it — so the padding lands
at the very start of the line, as leading whitespace:

```
input                        with the first column right-aligned
a  | b                        a | b
--:|---           →          --:|---
xx | yyy                     xx | yyy
```

That single leading space is the problem. mdtab decides that an indented table is a table by
requiring every one of its lines to start with the *same* leading run of spaces, tabs and `>`
(WI-0001 AC15) — that is how a table inside a blockquote or under a bullet gets aligned. After
the change above, the first line starts with one space and the delimiter line starts with none,
so the lines no longer agree, and mdtab stops recognising the thing as a table at all. We
checked this against the shipped tool rather than reasoning about it:

```
$ printf ' a | b\n---:|---\nxx | y\n' | python3 -m mdtab
 a | b
---:|---
xx | y
```

— returned untouched, because the prefixes differ.

The practical consequence is not that the file gets corrupted; it does not. It is that mdtab
would produce a table it will never tidy again. You add a row to it next month, run mdtab, and
nothing happens — the columns stay ragged and the tool says nothing, because it says nothing
about anything.

This only ever arises for the first column of a table with no leading `|`, and only when that
column's marker is `---:` or `:---:`. A table with a leading `|` is unaffected, and so is every
column after the first.

## Question

For the first column of a table written without a leading `|`, when that column's marker asks
for right or centre alignment, what should mdtab do?

## Options considered

- **A — honour the marker and emit the leading spaces anyway.** Consequence: the alignment you
  asked for is exactly what you get, in every column, with no exceptions to remember. The cost is
  the one demonstrated above: mdtab will not recognise its own output as a table on any later
  run, so that table is tidied once and then silently never again. Nothing warns you, because the
  tool emits no diagnostics at all.
- **B — align every column except that one; the first column of a table with no leading `|`
  stays flush against the left of the line whatever its marker says.** Consequence: the table
  keeps working with mdtab for ever, the marker itself is still written out unchanged so every
  renderer still right-aligns that column when the document is displayed, and nothing else in the
  table changes. The cost is one honest exception: in the plain text of a bare table, the first
  column's declared alignment is not visible in the padding. Note that in a bare table the first
  column has no left border to be pushed away from — the start of the line *is* its edge — so
  "right-aligned" there means indenting the whole line, which is arguably not what the table
  looked like anyway.
- **C — leave the entire table alone, byte-for-byte, whenever it has no leading `|` and its
  first column is right- or centre-aligned.** Consequence: consistent with *"if it doesn't
  understand one it should keep its hands off"* — mdtab never produces a half-honoured table.
  The cost is much larger than B's: a perfectly well-formed table that mdtab understands
  completely goes untidied for ever because of one `:` in one cell, and again nothing tells you
  why.
- **D — add the leading `|` to such tables**, which removes the problem entirely by giving the
  first column a border to align against. Consequence: every column aligns properly and mdtab
  keeps understanding its own output. We are listing it for completeness rather than
  recommending it, because it contradicts what you already told us — it changes punctuation you
  did not write. If you have changed your mind about that, this is the option that costs
  nothing else, but it would rewrite every bare table in your documents on the first run.
- **Recommendation:** **B**. It is the only option that keeps all three promises mdtab has
  already made to you — it changes spacing and never punctuation, it leaves your tables in a
  state it can go on maintaining, and it tidies every table it understands. The thing it gives
  up is the least valuable of the four: padding that would represent an alignment in a position
  where there is no column edge for the eye to align to, in the one table style where it cannot
  be shown without breaking something else. Choose C instead if you would rather mdtab refuse a
  job than do part of it, and D if you have decided you would accept the outer bars after all.

## Answer

[human] Honour the marker there too. If I wrote the colon on that column I meant it, and I don't
want one column quietly ignoring what I asked for because of where it happens to sit on the line —
a space at the front of the line is a price I'll pay. Don't add the bars, and don't leave the table

the tool and I'd want it sorted rather than worked around.
