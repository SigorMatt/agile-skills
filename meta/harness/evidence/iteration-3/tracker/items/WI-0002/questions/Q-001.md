## Context

WI-0002 ("honour the alignment markers"), refinement round 1, question 1 of 2 — please treat both
as one conversation about the same item. WI-0001 is delivered and merged: `mdtab` now lays out
the tables it recognises, padding every cell on the right. This item makes that padding follow
the `:` markers you write in the delimiter row. Everything else about the item is settled from
what you have already told us; these two are the only things left that are yours to decide.

This one has been carried as an open unknown since intake, and it is the last thing standing
between this item and a specification someone could build from without guessing.

A centred column has to divide its spare space between the two sides of the cell, and sometimes
that space is an odd number of columns, so the two sides cannot be equal. Concretely, with a
column three columns wide and a cell containing `ab`, there is one spare column and it goes
either before the text or after it:

```
| ab  |        | ab |            |  ab |
|:---:|   vs   |:--:|    →       |:---:|
| xyz |        | xyz|            | xyz |
```

(the middle table is only there to show the width; the real choice is between `| ab  |` and
`|  ab |`.)

It is a small difference, but it is one you would see every time you looked at the file, it has
to be the same every time or the tool stops being idempotent, and neither answer is derivable
from anything you have said so far — so we are not going to pick it for you without asking once.

Note that under ADR-0002 the spare space is counted in *display* columns, so a single wide
character such as `表` can make the remainder odd even when the text looks short.

## Question

When a centred column has an odd number of spare display columns to distribute, does the extra
one go on the left of the cell's text or on the right?

## Options considered

- **A — the extra column goes on the right**, so the text sits one column left of true centre
  (`| ab  |`). Consequence: matches what `prettier`, `pandoc` and most markdown formatters do,
  so a table laid out by mdtab and a table laid out by one of those tools agree; text drifts
  leftward, which reads as slightly left-of-centre in a narrow column and is invisible in a wide
  one.
- **B — the extra column goes on the left**, so the text sits one column right of true centre
  (`|  ab |`). Consequence: the mirror image; the columns still line up perfectly and the table
  is still idempotent. Its only real cost is that your files would differ by one space per
  affected cell from what other formatters produce, which matters if anything else in your
  toolchain ever reformats the same file.
- **C — never let the remainder be odd:** widen any centred column by one column when the
  arithmetic comes out odd, so both sides always get the same padding. Consequence: perfect
  symmetry in every centred cell, at the cost of tables that are wider than they need to be, a
  column width that depends on its alignment marker, and a rule that interacts with the
  minimum-width rule WI-0001 already carries. More machinery for a cosmetic gain.
- **Recommendation:** **A**. It is the convention every other markdown formatter follows, so
  choosing it means mdtab's output and another tool's output are the same bytes rather than
  differing by one space in every centred cell — which is the only consequence here that could
  ever cost you a confusing diff. Say "B" if you would rather the text leaned right, and we will
  record that instead; there is no technical reason to prefer one.

## Answer

[human] The alignment marker decides everything. Whatever the marker says, that's where the text
sits in the cell — every row, every column, no exceptions. For the odd one out, put the spare
space on the right so the text leans left; if that's what the other tools do then my files should
look the same as theirs rather than argue with them by one space.
