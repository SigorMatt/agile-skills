## Context

**WI-0004, round 1, question 1 of 3.** You said, refusing the sign-off, that a cell with a line
break in it should sit plain at the left whatever the column marker says. That is now a work item
and this is the round where it is written down precisely enough that someone with a terminal and
no context could tell whether it had been done. Three things in it can be read more than one way,
and this is the first of them. All three are below in this same round; there is nothing else after
them.

The thing that makes this one a question rather than our call: a markdown table row is a single
line of text, so a cell cannot contain an actual newline. Every "line break" inside a cell is
written as an HTML tag — and people write that tag in several ways, all of which render
identically:

```
$ printf '| longer heading | b |\n|:---:|---:|\n| a<BR/>b | x |\n| c<br />d | y |\n' | python3 -m mdtab
| longer heading | b |
|:--------------:|--:|
|    a<BR/>b     | x |
|    c<br />d    | y |
```

You named `<br>`. `<br/>`, `<br />`, `<BR>` and `<br class="x">` are the same authoring act
spelled differently, and today all of them are centred like the rest. There is also a case that is
*not* the same act — the tag written inside backticks, where the author is showing the tag rather
than using it:

```
$ printf '| longer heading | b |\n|:---:|---:|\n| `<br>` | x |\n' | python3 -m mdtab
| longer heading | b |
|:--------------:|--:|
|     `<br>`     | x |
```

That cell has no line break in it; it has the text of one. Whether the tool should notice the
difference is part of the same decision, so it is here rather than in its own question.

## Question

**Which cells does the new rule apply to — what counts as "a line break in a cell"?**

## Options considered

- **A — exactly the characters `<br>`, and nothing else.** The narrowest reading of what you
  wrote. Consequence: `a<br>b` sits left; `a<br/>b`, `a<br />b` and `a<BR>b` go on being centred
  or pushed right. Two cells that render identically would be laid out differently, and the author
  would have no way to see why from looking at the table.
- **B — any HTML line-break tag, however it is written.** `<br>`, `<BR>`, `<br/>`, `<br />` and a
  tag carrying attributes all count; a case-insensitive `br` tag is a line break. Consequence: the
  rule matches what the document *does* rather than how it was typed, and nothing that renders as
  one line changes. A cell containing the tag inside backticks (` `<br>` `) would also count,
  because this option does not look at backticks — so that cell would sit left despite being an
  ordinary one-line cell. Rare, and visible if it happens.
- **C — B, except inside a code span.** As B, but a `br` tag between backticks is treated as
  ordinary text and the cell keeps obeying its column's marker. Consequence: the rule matches your
  intent in the one case where B gets it wrong, at the price of the tool having to know what a
  code span is — a construct it does not currently look for anywhere. It is one more thing that
  can be got wrong on a document nobody thought of.
- **Recommendation: B.** It is the rule that matches what you would see rendered, and a rule that
  keyed on the exact string `<br>` would leave a `<br/>` cell centred for a reason no author could
  work out. C is more correct on a document that shows markup inside a table; if you write such
  documents, say so and we will take C instead — it costs a little care, not a redesign.

## Answer

[human] If it breaks the line when I read the document, it counts — capitals, a slash, spaces, an
attribute, doesn't matter, they are all the same thing to me and should be the same thing to the
tool. The one in backticks is different: that is someone showing the tag, not using it, so that
cell is an ordinary cell and keeps whatever its column says. I do write about markup in these
tables, so please get that case right.
