## Context

WI-0003 ("recognise a table mdtab laid out itself"), refinement round 1, question 1 of 1 — this
is the only thing we need from you on this item, and that is all of them for now.

WI-0002 is delivered and merged. mdtab now honours the alignment markers everywhere, including
the place you were shown the price of: *"a space at the front of the line is a price I'll pay.
Don't add the bars, and don't leave the table alone either"* (`WI-0002/Q-002`). This item is the
other half of that answer — *"if the tool then can't recognise a table it laid out itself, that's
a fault in the tool and I'd want it sorted rather than worked around"* — and it is the last item
in the engagement.

**What actually goes wrong.** mdtab decides a run of lines is a table only if every line of it
starts with the same indentation, byte for byte. Right-aligning a first column that has no `|` in
front of it puts spaces at the start of some lines and not others, so the tool stops seeing its
own output as a table. Both forms, run against the tool as it stands today:

```
$ printf 'a | b\n---:|---\nxxxx | y\n' | mdtab
   a | b
----:|--
xxxx | y

$ printf '   a | bbbbb\n----:|--\nxxxx | y\n' | mdtab     # a cell edited, ready to re-tidy
   a | bbbbb
----:|--
xxxx | y                                                   # ← untouched: no longer a table
```

The same thing happens to a bare table inside a blockquote or under a bullet, where the padding
lands just after the `>` or the indent.

**The fix, and the only bit of it that is yours.** The rule has to stop treating "how many
spaces are at the front of the line" as part of the indentation and start treating it as part of
the first cell. I prototyped that and ran it over all 33 test documents the project ships:
**none of them changes**, including the tangled blockquote you asked us to leave alone. Tables
written with outer `|` bars are untouched by the change, because their bars still have to line up.

But it is not free, and the cost is a class of document you have ruled on before. A table with
**no** outer bars whose rows are indented by *different* numbers of spaces is left alone today,
and would start being tidied — and tidying it pulls the whole table back to the shallowest
indent in it:

```
  a | b            becomes         a   | b
---|---                            ----|--
  ccc | d                          ccc | d
```

You told us in `WI-0001/Q-003`: *"If a table is indented in some tangled way you can't make sense
of, that's one you leave alone, same as any other table you don't understand."* A two-space
difference is arguably not "tangled", but it is your line to draw, not ours, and this is the one
place drawing it differently changes what the tool does to documents you already have.

Two things we settled ourselves rather than asking, both recorded in
`artifacts/refinement-qa.md`: tab characters and `>` in the indentation must still match exactly
— only plain spaces may differ, because nothing in this project defines how wide a tab is — and
where in the code the fix lives is the architect's call. Say so if either is wrong.

## Question

A table written **without** outer `|` bars, whose rows carry different numbers of leading spaces:
should mdtab start tidying it — pulling it back to the shallowest indent in the run — in exchange
for going on recognising the tables it has laid out itself?

## Options considered

- **A — Yes: leading spaces belong to the table, not to the indent.** mdtab treats the shared
  part of the indentation as the indent and anything past it as part of the first cell.
  Consequence: the fault is fixed in both its forms, tables written with outer bars are entirely
  unaffected, and none of the 33 shipped test documents changes. The price is the example above —
  a bare table with uneven leading spaces is tidied and ends up at its shallowest indent, where
  today it is left alone.
- **B — Only re-recognise a table whose leading spaces are already exactly the padding the
  markers call for.** mdtab would accept its own output back but would still refuse anything
  else. Consequence: it fixes the fault only until you edit the table. The moment you change a
  word in the *first* column — which is the commonest reason to re-run the tool — the padding
  stops matching, the table stops being recognised, and it is left ragged again. It buys a
  narrower rule at the cost of the fault coming back exactly when you would notice it.
- **C — No: leave the recognition rule alone, and accept that mdtab will not re-tidy a bare table
  whose first column is right- or centre-aligned.** Consequence: no document that is left alone
  today changes behaviour, and WI-0003 is dropped rather than built. This reverses part of what
  you said in `WI-0002/Q-002`, so we are only listing it because you should be able to change
  your mind now that the price of the other half is on the table. mdtab would go on producing
  those tables; it would just never tidy them a second time.
- **Recommendation: A.** It is the only one of the three that actually delivers what you asked
  for, and its cost is confined to documents that are already inconsistent about their own
  indentation. B looks safer and is not: it re-creates the fault on the commonest edit. If the
  cost of A turns out to matter, tightening the rule later is cheap, because the tool's whole
  behaviour on anything it does not recognise is one branch (ADR-0003).

## Answer

[human] Yes, tidy it. Spaces at the front of a line are part of how the table sits, not something
I put there on purpose, and a table with two spaces on one row and none on the next isn't tangled
— it's just untidy, which is the exact thing I wanted the tool for. Tabs and the quote marks having
to match exactly sounds right to me, and where the fix goes in the code is yours to decide.
