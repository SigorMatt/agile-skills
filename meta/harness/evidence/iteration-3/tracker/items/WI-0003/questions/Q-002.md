## Context

The plan's seven steps are done apart from the gates. `shared_prefix` is in `mdtab/scan.py`,
`lay_out`'s rule 2 calls it, the two tests the plan names are amended, and all seven fixture pairs
exist — commits `a502bc8` and `f32d681` on `wi/WI-0003`. Every transcript in AC2, AC3, AC5 and AC6
was run against the branch and produces exactly the bytes the criterion states.

One test fails, and it is not one the plan or AC9 expected to.

`tests/test_fixtures.py::ContentPreservationTest::test_ac11_cell_content_survives_apart_from_the_spaces_around_it`
checks WI-0001 AC11 over every fixture by splitting each **raw line** on `|` and comparing the
fields with `.strip(" ")` applied. It does not strip the run's prefix first. While ADR-0003 rule 2
required every line of a run to carry a byte-identical prefix, that made no difference: whatever
the prefix was, it was the same on the input line and the output line, so field 0 compared equal.

Under ADR-0008 rule 2 it can differ, in exactly one shape — a run whose **shared prefix ends in a
non-space character** and whose rows carry uneven spaces after it. That is AC5's third document,
which the plan turns into the fixture `uneven-blockquote-space`:

```
in:   >  a | b        out:  > a | b
      > ---|---             > --|--
      >  c | d              > c | d
```

The test splits `>  a | b` into `[">  a ", " b"]` and strips to `[">  a", "b"]`, and the output
into `["> a", "b"]`, and reports them as different content. They are not: the shared prefix is
`> `, the first cell is ` a `, and it strips to `a` on both sides, exactly as WI-0001 AC11 and
WI-0003 AC1 say it should. The test is comparing prefix-plus-cell and calling it a cell. Its own
docstring and name say it checks cells.

This is the only failure in the suite. It fires on one subtest, for one fixture:

```
$ python3 -m unittest discover -s tests -t .
FAIL: test_ac11_cell_content_survives_apart_from_the_spaces_around_it (fixture='uneven-blockquote-space')
AssertionError: Lists differ: ['>  a', 'b'] != ['> a', 'b']
Ran 71 tests in 0.089s
FAILED (failures=1)
```

The other five laid-out fixtures pass it: their shared prefix is either empty or the uneven spaces
sit before a prefix that is spaces to its end, so field 0 strips to the same thing either way.

Why this is not mine to settle: [src: WI-0003 AC9] states, as a checking clause, that **exactly
one** pre-existing test changes — `test_ac10_a_bare_right_aligned_first_column_pads_at_the_start_of_the_line`
— and that "all other 64 tests must pass unmodified". Repairing this test is a second pre-existing
test changing, which the criterion forbids; dropping the fixture is choosing which evidence AC5
gets on the basis that the other choice is inconvenient. `implement` may not edit an acceptance
criterion and may not decide which of two criteria gives way.

## Question

`test_ac11_cell_content_survives_apart_from_the_spaces_around_it` compares a raw line's
pipe-separated fields, so it counts a non-space shared prefix as part of the first cell, and it
therefore fails on AC5's blockquote document — a document the code handles exactly as AC1 and AC5
require. Should the test be corrected to strip the run's shared prefix before comparing, and
WI-0003 AC9's "exactly one test changes" clause corrected with it, or should AC5's blockquote
document be evidenced some other way that leaves the test untouched?

## Options considered

- **A — Correct the test, and correct AC9's count.** Strip the shared prefix from each line before
  splitting it into fields, in that one test. Consequence: the test then checks what its name says
  — cells — and stays sound for every document ADR-0008 admits, including ones nobody has written
  yet. Two pre-existing tests change instead of one, so AC9's checking clause is false as written
  and must be amended to name both and say why the second one changed. That amendment is an
  acceptance-criterion edit, which only the architect (or `refine`) may make, and it is visible in
  the record rather than silent. The fixture stays and AC5 keeps document-level evidence.

- **B — Drop the `uneven-blockquote-space` fixture and evidence AC5's third document with a unit
  test on `lay_out` instead.** Consequence: AC9 stays literally true and no pre-existing test is
  touched; the item finishes this turn. But `test_ac11` stays wrong for a class of document mdtab
  now lays out, and stays wrong *invisibly* — the reason it passes is that no fixture exercises
  the shape that breaks it. The next person to add a blockquote fixture with uneven spaces meets
  this failure with none of this context, and reads it as a bug in the code. AC5 loses the only
  one of its three documents that has a `>` in it.

- **C — Treat it as a defect in WI-0001's delivered test and file a bug item.** Consequence: the
  test is left failing on the branch, WI-0003 cannot reach `verifying` with a red suite, and the
  bug item cannot be worked until this item is done because it edits the same file. It converts a
  question that can be answered now into a dependency cycle. Rejected on those grounds, and
  recorded because "file a bug and carry on" is `implement`'s standing instruction for a defect in
  another item's work and it does not fit here: the test is not wrong about behaviour anyone
  shipped, it is stale about a rule this item changed.

- **Recommendation: A.** The test is measuring the wrong thing, and it is measuring the wrong
  thing *because of this item's change*, so this item is where it gets fixed. AC9's clause exists
  to stop a silent rewrite of the suite, not to stop a second necessary correction — and it names
  the mechanism itself: WI-0002/Q-003 is cited in AC9 as the precedent for what an unsatisfiable
  checking clause costs, and this clause has become one. Option B buys a green suite by removing
  the document that proves the problem, which is the shape of thing this protocol exists to
  prevent.

## Answer

**Option A.** Correct the test, and correct AC9's count with it. AC9's checking clause now reads
"**exactly two** of its 65 tests are expected to change; all other 63 must pass unmodified", and
names `test_ac11_cell_content_survives_apart_from_the_spaces_around_it` as the second, with the
reason. `plan.md` gains a step 7 saying how to correct it — remove each line's leading run of
space, tab and `>` before splitting it on `|`, restated locally rather than imported, because this
file's whole method is that no test asks the code under test where something is. The old step 7,
the gates, becomes step 8. The `uneven-blockquote-space` fixture stays.

**Answered from the record, not decided fresh**, on three things already written down:

- **The behaviour the test disagrees with is the criterion.** [src: WI-0003 AC1] says in terms
  that when a run is recognised, "the shared prefix — not each line's own prefix — is what is
  stripped… every space past it belongs to the row, and therefore to that row's first cell, and is
  removed with the rest of that cell's leading spaces by WI-0001 AC11", and [src: ADR-0008] rule 2
  says the same. On `>  a | b` the shared prefix is `> `, the first cell is ` a `, and it strips to
  `a` on both sides of the transformation. WI-0001 AC11 holds on that document. The test says it
  does not because it splits the raw line and counts `> ` plus the cell as one field — it is
  measuring prefix-plus-cell and calling it a cell, which its own name and docstring say it is
  not. So this is route 1 of `spec/question.md` §3: the code follows the criteria and the test does
  not follow the code. No ADR is needed, and none was written; ADR-0008 already decides everything
  the answer rests on.

- **Why the test was right before and is wrong now, exactly.** Under ADR-0003 rule 2 every line of
  a run repeated one prefix, so field 0 carried the same prefix on the input line and the output
  line and cancelled. Under ADR-0008 rule 2 it can differ, in one shape only: a shared prefix
  ending in a character that is not a space, with uneven spaces after it. That is why five of the
  six new laid-out fixtures pass the test and only `uneven-blockquote-space` fails it — and it is
  why the failure is a stale approximation rather than a defect.

- **The project has answered this shape twice, the same way.** [src: WI-0002/Q-003] amended
  AC14's checking clause when it named a fixed set of places the suite would change and the set
  turned out to be wrong, and [src: WI-0001/Q-005] amended AC12's wording when a criterion carried
  two clauses that could not both hold. AC9 cites the first of those itself — it says its
  exception is "named here because WI-0002/Q-003 showed what an unsatisfiable checking clause
  costs" — so amending the count is the route this criterion's own text points at. What is
  **not** amended is AC9's substance: every acceptance criterion of WI-0001 and WI-0002 must still
  hold, and the corrected test still fails if any cell's characters change.

**Why not B or C.** B — dropping the fixture and evidencing AC5's blockquote document with a unit
test — makes AC9 literally true by deleting the only document that exercises the shape the test
gets wrong. The test then stays wrong and stays *invisibly* wrong, and the next person to write a
blockquote fixture with uneven spaces meets this failure with none of this context. That is buying
a green suite by removing the evidence, which is what the asker said it was. C — filing a bug
against WI-0001's test — is worse: it leaves this item red, and the bug edits the same file, so it
cannot be worked until this item is done. The test is not wrong about anything WI-0001 shipped; it
is stale about a rule **this** item changed, which is what makes the correction this item's.

**A note on what an amendment of this kind may not be.** Editing a criterion so that what was
built passes is the failure this skill is warned about most sharply. This is not that, and the
distinction is checkable: the amendment changes only how AC9 says its pass is demonstrated, not
what must be true; it makes the suite **stricter** on the point at issue, because it keeps a
fixture the other option would have deleted; and it was decided before the corrected test was
written, not after it was seen to pass. `implement` does the correction on resuming — the answer
does not touch code.
