## Context

This is the only question this round, filed while fixing the four findings `review-close`
recorded in `artifacts/review.md`. Findings 2, 3 and 4 are fixed and committed
(`78c7bf4`, `cc0eea6`); finding 1 is fixed in the same commits and is what raised this.

Finding 1 requires the AC9 undecodable-bytes document to stop being a Python bytes literal in
`tests/test_fixtures.py` and become a fixture pair, because [src: ADR-0005] says "Fixtures are
the only place a test may express a document; a test may not build one from a Python literal".
ADR-0005 fixes the fixture naming too — "Document fixtures live under `tests/fixtures/` as
pairs: `<name>.in.md` and `<name>.out.md`" — and names this exact case as one it expects:
"Cases that cannot be written as literals at all, such as a file whose last line has no
terminator **or one containing invalid UTF-8**, become ordinary fixtures."

I created `tests/fixtures/invalid-utf8.in.md` and `.out.md` accordingly. The document contains
a literal `0xFF` byte, which is what makes it evidence for AC9 and [src: ADR-0004]: it is not
valid UTF-8, so `surrogateescape` is the only thing carrying it through.

**That makes `validate-workspace` — a hard gate of this skill — crash, not fail.**
`check_claim_citations` walks every `.md` file in the project that is not git-ignored and not
under `.git`, `__pycache__`, `.claude` or `node_modules`, opens it with
`encoding="utf-8"`, and catches only `OSError`:

```
[src: run: python3 .claude/agile-skills/scripts/validate-workspace . → exit 1
  File ".claude/agile-skills/scripts/validate-workspace", line 1266, in check_claim_citations
    text = handle.read()
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xff in position 12: invalid start byte]
```

I isolated it: with the pair moved out of the tree the validator reports
`checked 3 item(s), 7 document(s) — 0 errors, 0 warnings`, exit 0; with it back, the traceback
above [src: run: mv tests/fixtures/invalid-utf8.*.md /tmp/hold; validate-workspace . → exit 0;
mv back; validate-workspace . → exit 1]. The other new fixture, `tab-in-cell`, is valid UTF-8
and is not involved. The other six gates are green on the branch head.

So ADR-0005 and the `workspace-valid` gate cannot both be satisfied as they stand. I am not
entitled to decide this: every way out either amends an ADR, edits the pipeline's own machinery,
or leaves a must-fix review finding unfixed.

## Question

How should the AC9 undecodable-bytes document be stored, given that ADR-0005 requires it to be a
`.md` fixture and `validate-workspace` requires every `.md` file in the project to decode as
UTF-8?

## Options considered

- **A — Amend ADR-0005 so a fixture that is not valid UTF-8 carries a different extension**
  (`invalid-utf8.in.bin` / `.out.bin`), and generalise `test_fixtures.py`'s `NAMES`
  discovery from `.in.md` to `.in.*`. Consequence: the toolkit is untouched and the rule
  "fixtures are the only place a test may express a document" is kept intact. ADR-0005 goes to
  v2 and gains a sentence; `NAMES` gains a suffix split; every fixture-wide test
  (round-trip, AC6 idempotence, AC11, AC14) picks the pair up unchanged. The cost is that
  `tests/fixtures/` stops being uniformly `.md`, and a reader has to know why one pair is not.
- **B — Fix `validate-workspace` to catch `UnicodeDecodeError` alongside `OSError`** at
  line 1266 and skip the file, exactly as it already skips unreadable ones. Consequence: no
  project artifact changes at all, and the fix is one identifier wide. But it edits the
  pipeline's own machinery from inside a work item, which is not this item's scope and which no
  acceptance criterion covers; it also silently exempts the file from the citation rule rather
  than reporting it. It is arguably a real defect in the toolkit either way — a legitimately
  binary `.md` file anywhere in a project takes the validator down with a traceback instead of
  a finding — and that is worth reporting whichever option is chosen.
- **C — Revert finding 1 and keep the bytes literal in the test**, declaring the ADR-0005 breach
  as a deviation in `impl-report.md` this time. Consequence: cheapest, and honest in a way the
  first pass was not — but `review-close` marked finding 1 *must fix*, and the reason it gave
  was the undeclared breach *and* the false module docstring, not the declaration alone. It also
  leaves ADR-0005's own worked example ("one containing invalid UTF-8") as something the project
  cannot actually do.
- **D — Drop the AC9 undecodable-bytes case entirely.** Consequence: no conflict, and no
  evidence for the surrogateescape half of ADR-0004 either. AC9's other two clauses (CRLF, no
  final newline) have fixtures, but the byte that only `surrogateescape` can carry would go
  untested. Rejected as a loss of coverage that nothing asked for.
- **Recommendation: A**, with B reported as a toolkit defect regardless of the answer. A keeps
  the fix inside the project, leaves ADR-0005's rule ("no document in a Python literal") whole
  while correcting the one detail that turned out to be unworkable, and needs no change to the
  machinery the pipeline validates itself with. B on its own would leave ADR-0005 asserting an
  arrangement that only works because a validator was patched for it.

## Answer

**Option A, decided here rather than escalated, and recorded as [src: ADR-0006].**

A document fixture whose bytes are deliberately not valid UTF-8 carries `<name>.in.bin` and
`<name>.out.bin`. Every other fixture keeps `<name>.in.md` and `<name>.out.md`.
`tests/test_fixtures.py` discovers pairs by the `.in.` infix rather than by the `.md`
suffix, so the `invalid-utf8` pair is picked up by the round-trip test, the AC6 idempotence
test, the AC11 test and the AC14 test without being registered a second time. Both halves of a
pair always carry the same extension. `.gitattributes` already marks `tests/fixtures/**` as
`-text -diff`, so nothing about git's handling changes
[src: tracker/items/WI-0001/artifacts/plan.md].

**Why this was not escalated.** None of the four conditions in `spec/question.md` §4 holds.
It does not depend on intent no document records — the stakeholder deferred exactly this class of
decision: *"The rest of how it's built is your call, not mine"* [src: EP-001/Q-001]. It is not
irreversible: reversing it is renaming two files and changing one expression, and no module under
`mdtab/` refers to `tests/` at all [src: run: grep -rn "tests" mdtab/ → no match]. It does not
contradict [src: ADR-0005] — it narrows one clause that ADR fixed in passing and never weighed
against an alternative, while leaving intact the decision it did weigh and the rule this question
arose from. And the record is not silent: [src: ADR-0005] names "one containing invalid UTF-8" as
a case it intends to support, so the amendment carries out its intent rather than overriding it.

**Why not the other options.** B (make every fixture `.bin`) costs twenty-two renames and the
readability of the twenty-one fixtures that genuinely are markdown, to save one sentence of
explanation. C (patch `validate-workspace`) puts a local edit to the pipeline's own machinery
inside a work item, where no reviewer of mdtab can audit it, no criterion covers it, and the next
toolkit install discards it — the underlying defect is real and is reported in this execution's
journal instead. D (keep the literal, declare the deviation) leaves [src: ADR-0005]'s rule broken
in the one place it was written for. E (drop the case) removes the only evidence for the
`surrogateescape` half of [src: ADR-0004].

**What `implement` must do on resuming.** Recreate the pair as
`tests/fixtures/invalid-utf8.in.bin` and `tests/fixtures/invalid-utf8.out.bin` with the bytes
`a table:\n\n| \xff | bb |\n|---|---|\n| 1 | 2 |\n` and
`a table:\n\n| \xff | bb |\n|---|----|\n| 1 | 2  |\n`; change `NAMES` to key
on `.in.`; add `"invalid-utf8": (2, 5)` to `ALIGNED`; restore the AC9 test to read the
fixture; and correct `tests/test_fixtures.py`'s module docstring, which currently records the
exception as parked. Commit `a2059b7` is the state to undo, and `cc0eea6` is what it looked
like before the extension changed. Declare it in `impl-report.md`'s `## Deviations from the
plan` — `plan.md` step 10 now carries the rule, so it is a plan step rather than a deviation
from one, but the route by which it got there is worth stating.

**One thing this answer does not settle.** AC12's "exactly `2 + max`" clause still needs
amending for the all-empty `:---:` column [src: WI-0001]. That is a different decision with a
different basis and it belongs in its own question; `Q-004` did not touch it and neither did
this execution.
