## Context

WI-0001's second verification passed all fifteen criteria against branch head `e0fd6b0`. This
question is not about whether the code is right — it is, and this is the only question filed from
that verification.

AC12 contains two clauses that cannot both hold for one class of input:

- "every column is exactly `2 + max(display width of its cells)` columns wide"; and
- "The delimiter row's cells are filled with `-` to the same width, keeping any `:` at the ends
  they had."

For a column whose header and body cells are **all empty** and whose delimiter marker is `:-:`,
the first clause gives 2, and no delimiter cell can be written into 2 columns while keeping both
colons: `::` contains no `-`, so a second run would not recognise the row as a delimiter row and
AC6's idempotence would fail as well. The tool renders 3:

```
$ printf '| a |  |\n|---|:-:|\n| b |  |\n' | python3 -m mdtab
| a |   |
|---|:-:|
| b |   |
```

which is idempotent and is the only width satisfying the delimiter clause and AC6 together.

This is not new and nothing about it is disputed. `plan.md` decided it under `## Assumptions`
before implementation; the first verification confirmed the behaviour and its idempotence;
`review-close` accepted it as a gap, wrote that **"the wording of AC12 is what should change, not
the code"**, told `implement` explicitly not to touch AC12, and recorded that amending an
acceptance criterion belongs to `answer-questions`. It also recorded that the amendment "is worth
making before WI-0002 builds on AC12's arithmetic". The same paragraph is in `item.md`'s
`## Notes` and in `impl-report.md`'s `## What I did not do`.

What has not happened is the amendment. `answer-questions` runs only when a question is open, and
no skill had filed one, so the obligation would have died silently when WI-0001 closed — leaving
WI-0002, whose whole subject is the alignment markers in the delimiter row, to be refined and
planned against a criterion whose arithmetic is known to be wrong in exactly the case that
involves a marker.

Hence this question, and hence `blocking: false`: WI-0001's behaviour is settled and its
verification stands, so nothing about the item is blocked and it proceeds to `in-review`. But
`next` dispatches `answer-questions` on an open architect question (step 4) before it dispatches
the status owner (step 5), so the amendment lands before the review that would close the item.

`verify` may not amend an acceptance criterion itself: the criteria are the standard it judges
against, and a verifier that edits the standard to fit what it measured has verified nothing.

## Question

How should AC12's width clause be worded so that it and AC12's delimiter clause are jointly
satisfiable for every column — including one whose header and body cells are all empty and whose
delimiter marker is `:---:` — without changing the behaviour that `plan.md`, both verifications
and `review-close` have already accepted?

## Options considered

- **A — Amend the width clause to state the floor explicitly.** Replace "every column is exactly
  `2 + max(display width of its cells)` columns wide" with something like: "every column is
  `2 + max(display width of its cells)` columns wide, except that a column is never narrower than
  its delimiter cell can be written — at least `1 + one for a leading ':' + one for a trailing
  ':'` characters of delimiter, plus the surrounding spaces the row's outer-pipe style keeps
  (AC14)". Consequence: AC12 becomes satisfiable everywhere and describes the shipped behaviour
  exactly; the arithmetic WI-0002 inherits is correct; the criterion gets longer and encodes a
  rule that `plan.md` already states in its `## Approach`. Nothing in the code, the tests or any
  fixture changes.

- **B — Amend the delimiter clause instead, dropping the colon-preservation promise for a column
  too narrow to hold both colons.** E.g. "…keeping any `:` at the ends they had, except where the
  column is too narrow for both, in which case the leading `:` is kept". Consequence: AC12's
  arithmetic stays clean, but the tool would have to render `|:-|` or `|::|`-ish output for the
  degenerate column, which is a **behaviour change** — it breaks AC6 for that document unless the
  result is still a delimiter row, and it silently loses an alignment marker that WI-0002 is
  about to start honouring. It also contradicts the epic's "never the punctuation" promise from
  `WI-0001/Q-002`.

- **C — Rule the degenerate column out of scope.** Add to AC12 or to `## Out of scope`: "a column
  whose header and body cells are all empty is not specified". Consequence: cheapest to write, and
  it makes the contradiction disappear rather than resolving it. But the input is trivially
  reachable — three lines of markdown — and the tool must do *something* with it; leaving that
  something unspecified means AC6 is the only thing constraining it, and the next person to touch
  the width calculation has no criterion telling them why the 3 is there. It also leaves WI-0002
  to rediscover the same contradiction.

- **D — Leave AC12 as it is and record the exception permanently.** It is already recorded in
  `item.md`'s `## Notes`, in `review.md` and in both verification reports. Consequence: no work,
  and the record is honest about it. But a criterion that is known to be unsatisfiable stays in
  the item as the standard a future re-verification would judge against, and WI-0002's refinement
  would have to re-derive the whole argument from the notes of a closed item.

- **Recommendation: A.** It is the option all four prior artifacts already point at — they say the
  wording is what should change — and it is the only one that changes no behaviour, no test and no
  fixture. B changes behaviour and loses a marker just as WI-0002 begins to depend on markers; C
  and D both leave WI-0002 to inherit a criterion that is wrong where it matters most.

## Answer

**Option A, with one addition: AC12 now carries *two* qualifications rather than one, because
both are forced by AC6 and only one of them was in the question.**

Answered from the record, not decided fresh. Every element of the amendment is already written
down somewhere authoritative; what was missing was the amendment itself.

- The floor rule — a column is never narrower than its delimiter cell can be written — is stated
  in `plan.md`'s `## Approach` as rule 2, "not a free reading of AC12 and must be implemented as
  written here, because AC6 forces it", and again in its `## Assumptions`.
- The exclusion rule — the maximum is taken over the header and body rows only, never over the
  delimiter row's own cell — is `plan.md`'s `## Approach` rule 1, forced by AC6 for the same
  reason: a column measured over a delimiter cell that was itself widened to the column grows on
  every run, and `mdtab | mdtab` stops being a fixed point. AC12's original "max(display width of
  its cells)" does not say which cells, and the second verification confirmed the tool excludes
  the delimiter cell (mutating `if index != 1` to `if index != -1` fails 29 tests, `test_ac6_…`
  among them). Leaving that unstated would have left AC12 still not decidable from its own text,
  which is what the question was for, so it is amended in the same edit and declared here.
- That the wording is what should change, not the code, is `review.md`'s `## Accepted gaps` 1,
  in those words, and it is repeated in `verify-report.md` (both cycles) and in `item.md`'s
  `## Notes`.
- That the amendment must not lose a `:` — which is what option B would have done — is the
  stakeholder's own: *"I only want the spacing changed, never the punctuation"* (`WI-0001/Q-002`,
  answered by the human). WI-0002 is about to start honouring those markers, which makes losing
  one worse than cosmetic.
- The authority to amend at all rests on `refinement-qa.md`, which records AC12 as `[assumed]`
  and "not asked", under the stakeholder's standing deferral *"The rest of how it's built is
  your call, not mine"* (`EP-001/Q-001`, answered by the human).

**Not escalated.** None of `spec/question.md` §4's four conditions applies. It is not intent no
document records — five documents record it. It is not irreversible: it is one paragraph of a
criterion, and the behaviour it describes has been shipped, verified twice and reviewed once. It
contradicts no ADR; ADR-0002 fixes how a *character* is measured and says nothing about a column's
floor, and ADR-0003 is about which runs are laid out at all. And the record is not silent.

**No behaviour changed, and nothing was reshaped around the code.** Both qualifications were
already obligations of AC6, which is a criterion of this item that the stakeholder's own
idempotence requirement produced; the amendment makes AC12 consistent with AC6 rather than with
`mdtab/table.py`. No code, test or fixture was touched by this execution, and the tool's output
is byte-identical to what the second verification measured. Checked against the amended text:

```
$ printf '| a |  |\n|---|:-:|\n| b |  |\n' | python3 -m mdtab   # marker ':-:' -> 3 wide
| a |   |
|---|:-:|
| b |   |
$ printf '| a |  |\n|---|---|\n| b |  |\n' | python3 -m mdtab   # marker '---' -> 2 wide
| a |  |
|---|--|
| b |  |
$ printf '| a |  |\n|---|:--|\n| b |  |\n' | python3 -m mdtab   # marker ':--' -> 2 wide
| a |  |
|---|:-|
| b |  |
$ printf 'a |  | c\n--- | :-: | ---\nb |  | d\n' | python3 -m mdtab   # bare rows, ':-:' interior
a |   | c
--|:-:|--
b |   | d
```

**The verification stands.** `verify-report.md`'s AC12 row and its `### AC12's one exception`
section are the evidence for the amended clause; what they record as an exception is now what the
criterion says. AC12 remains ticked and no other criterion was touched.

**Scope was not widened, so no new item was filed.** The amendment implies no work: the code
already does what the amended text says, and WI-0002's scope is unchanged — it inherits a
criterion that is now correct instead of one that was not.
