## Context

WI-0001 ("align table columns"), refinement round 1, question 1 of 3 — please treat all three as
one conversation about the same item. Your three answers on the epic settled the runtime, the
table syntax and how width is measured, and those are now in the criteria. These three are what
is left before someone with a terminal and no context could decide whether the tool did its job.

Markdown lets you write a table whose rows disagree about how many cells they have:

```
| name  | role      |
|-------|-----------|
| Ada   | engineer  | 1815 |
| Grace |
```

The first row has two cells, the second three, the third one. A renderer silently drops the
extra cell and pads the short row. The tool has to decide what *it* does, and the three sensible
answers produce visibly different documents.

This is your call rather than ours because it decides what happens to text you wrote. Option B
below moves a value out of the column a renderer would show it in; option C leaves a table
looking broken when you might have wanted it fixed. Both are things you would notice in your own
files, which is the first escalation condition in `spec/question.md` §4 — intent about your
documents that no artifact records.

## Question

When a table's rows do not all have the same number of cells, what should the tool do?

## Options considered

- **A — Lay it out on the widest row, padding short rows with empty cells.** The example above
  becomes a three-column table; `Grace` gets two empty cells beside her. Consequence: nothing is
  lost, every row lines up, and the document now shows an empty column you may not have wanted.
  This changes what a renderer displays: the stray `1815` becomes a visible third column
  instead of being dropped.
- **B — Lay it out on the header row's cell count, dropping nothing but leaving extra cells at
  the end of the line.** `Ada`'s `1815` stays on the line, past the last `|`. Consequence:
  the table's columns line up and the renderer keeps ignoring the extra cell, but the output has
  ragged tails hanging off some rows, which looks like a bug even though it is deliberate.
- **C — Leave a malformed table exactly as it is, byte-for-byte.** Consequence: the tool only
  ever touches tables it fully understands, so it can never mangle one; the cost is that a table
  with one bad row stays unaligned and the tool tells you nothing about why (it emits no
  diagnostics — that is out of scope for the whole epic).
- **Recommendation:** **A**. It is the only option that both aligns the table and keeps every
  character you typed somewhere a reader can see it, and a stray cell is far more often a typo
  you would want made visible than a value you meant to hide. Choose C if you would rather the
  tool never surprise you, and are content to fix such tables by hand.

## Answer

[human] Leave it alone. A table with a row that doesn't match is a table I got wrong, and I want
to see it still looking wrong so I go and fix it — not have the tool invent a third column or
leave bits hanging off the end of a line. The tool's job is to tidy tables it understands, and if
it doesn't understand one it should keep its hands off.
