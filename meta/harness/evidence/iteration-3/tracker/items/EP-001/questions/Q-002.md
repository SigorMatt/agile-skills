## Context

This is question 2 of 3 filed on EP-001 during intake, in one round — please treat all three as
a single conversation.

Your idea says the tool "pretty-aligns its tables" and "leaves non-table content untouched".
That sentence is only actionable once we know what counts as a table, because the tool has to
decide, line by line, whether it is looking at one. Markdown has no single table syntax: the
pipe-and-dash form is what GitHub, GitLab and most editors support, but reStructuredText-style
grid tables and raw `<table>` HTML also appear in markdown documents in the wild, and each needs
completely different detection and rewriting code.

Nothing in the workspace records which of these you have in your documents. This is the first
escalation condition in `spec/question.md` §4 — it depends on intent about your own documents
that no artifact captures — and getting it wrong in either direction is costly: too narrow and
the tool silently ignores tables you wanted fixed, too wide and we build detection and layout
code for syntaxes you never write.

A related detail we are *not* asking about, because we think the answer is obvious and have
written it into the epic's scope: a pipe table that appears inside a fenced code block is
content, not a table, and will be left alone. Say so in your answer if you disagree.

## Question

Which table syntaxes must the tool align — GFM pipe tables only, or others as well?

## Options considered

- **A — GFM pipe tables only** (rows delimited by `|`, with a `---` delimiter row under the
  header). Consequence: covers what almost everyone writes and what every markdown renderer in
  common use supports; anything else in the document passes through untouched, silently. This is
  the smallest thing that satisfies the idea as stated.
- **B — Pipe tables plus reStructuredText/grid tables** (`+---+---+` borders). Consequence:
  roughly doubles the detection and layout work, and adds a decision we would then have to ask
  you about — whether a grid table should stay a grid table or be converted.
- **C — Pipe tables plus HTML `<table>` elements.** Consequence: requires parsing HTML embedded
  in markdown, which is a different and substantially larger problem, and "aligning" an HTML
  table means indenting tags rather than padding cells — arguably a different tool.
- **D — All of the above.** Consequence: three parsers, three layout engines; this stops being
  a small filter and becomes a markdown formatting project.
- **Recommendation:** **A**. It is what "markdown table" means to almost everyone, it is the
  only form your one-line description matches, and B or C can be added later as their own work
  items under this epic if your documents turn out to contain them. If you know your documents
  contain grid or HTML tables, say so now — retrofitting a second syntax later is more expensive
  than designing for it from the start.

## Answer

[human] The pipe ones, the ones with the dashes under the header. That is the only kind I write
and the only kind I care about — I have never put a grid table or raw HTML in a document in my
life. And yes, a table inside a code fence is text I typed on purpose; don't touch it.

**Recorded by answer-questions (architect).** The stakeholder chose option **A** and explicitly
confirmed the code-fence assumption the question flagged. Both halves are propagated: what a
table *is* became WI-0001 AC7, and what is left alone inside a fence became WI-0001 AC8, so each
is separately checkable rather than living in a scope paragraph. Grid and HTML tables are
recorded on the epic as out of scope with a note that either could return as its own item, since
the stakeholder ruled them out for their own documents rather than for all time.
