## Context

This is question 3 of 3 filed on EP-001 during intake, in one round, and it is the last one for
now — please treat all three as a single conversation.

"Pads columns" needs a definition of how wide a cell's text is, and for text that is not plain
ASCII there is more than one honest answer. A CJK character such as 表 is one character but
occupies two cells in a terminal or a fixed-width editor font. An emoji is often one code point
but two cells wide, and some are several code points joined together. An accented character may
be one code point or two (letter plus combining mark) depending on how the file was saved.

This decides whether the epic's success measure — "the column boundaries form straight vertical
lines when viewed in a fixed-width font" — is actually met for such documents, or only for
ASCII ones. It is the fourth escalation condition in `spec/question.md` §4: the record is silent
and either choice has visible consequences. It is also close to irreversible in the cheap
direction, because the width function is threaded through every layout decision in the tool, and
retrofitting display-width awareness afterwards means revisiting all of it and all of its tests.

## Question

How should the tool measure the width of a cell's text when that text is not plain ASCII?

## Options considered

- **A — Count Unicode code points.** Consequence: simple, fast, no lookup tables, and every
  table in a pure-ASCII document is laid out perfectly. A table containing CJK text or emoji
  will have visibly ragged columns in an editor, because the tool will have counted 表 as one
  column when it draws as two. The tool would still be internally consistent, just wrong on
  screen.
- **B — Measure display width** using the Unicode East Asian Width property, treating wide and
  fullwidth characters as two columns and combining marks and zero-width joiners as zero.
  Consequence: columns line up on screen for CJK and most emoji, which is the outcome your
  success measure actually describes. Costs a width table and a normalisation decision, and it
  is never perfect — emoji sequences and some scripts render differently in different fonts and
  terminals, so a small residue of misalignment survives in any implementation.
- **C — Declare non-ASCII table content out of scope.** Consequence: the tool counts code
  points as in A, and we write down explicitly in the vision and the acceptance criteria that
  tables containing non-ASCII text are not guaranteed to align. Honest, cheap, and it stops
  anyone later filing this as a bug against behaviour that was never promised.
- **Recommendation:** **B if your documents contain CJK text or emoji in tables, otherwise C.**
  We are not guessing between them: A and C produce the same code and differ only in whether the
  limitation is written down, and C is strictly better than A because it is the same behaviour
  without the false promise. The only thing we cannot answer for you is whether your tables have
  wide characters in them.

## Answer

[human] It has to line up on the screen. My tables have accented names and the odd emoji in
them, and if the columns go ragged the moment one appears then the tool hasn't done its job.
Measure what the character actually takes up in my editor, not how many of them there are.

**Recorded by answer-questions (architect).** The stakeholder chose the *property* in option
**B** — alignment is judged on screen — and did not choose a measurement rule, which is not
theirs to choose. The rule was decided here and recorded as `ADR-0002`: category `Mn`/`Me`/`Cf`
counts 0, East Asian Width `W`/`F` counts 2, everything else counts 1, ambiguous-width included.
Two consequences of the rule are worth flagging back: it is deliberately stated by general
category rather than by combining class, because the variation selector that makes many emoji
render wide has a combining class of zero; and it makes normalisation unnecessary, so the tool
still emits the author's bytes unchanged, which is what the epic's "spacing, not content" scope
requires. The residual imperfection the question warned about — joined emoji sequences, and
ambiguous-width characters in a terminal configured to draw them wide — survives, and ADR-0002
records it as a limitation to document rather than a bug to file.
