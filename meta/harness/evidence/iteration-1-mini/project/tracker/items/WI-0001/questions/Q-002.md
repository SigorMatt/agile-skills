## Context

You said the data must survive between runs, so there is a file somewhere. WI-0001's AC2 tests
that it survives; nothing yet says what happens at the two edges of that — the first run, when
the file does not exist, and a bad run, when the file exists but cannot be read (someone edited
it by hand, a disk filled up mid-write, it was truncated).

I am asking rather than assuming because one of the choices can lose data. If a damaged store is
treated as an empty one, the tool starts a fresh ledger and the group's history is gone with no
message — and the first anyone notices is that "who owes whom" says nobody owes anybody.

This is separate from EP-001/Q-003, which asks *where* the file lives. This asks how the tool
behaves around it.

Definition of Ready criteria this blocks: **R4** and **R10** — first-run and damaged-store
behaviour are two of this item's modes and neither is currently specified anywhere.

## Question

On the very first run, should the tool create its store silently, or should there be an explicit
"start a new group" step? And if the store exists but cannot be read or understood, should the
tool refuse to run, or carry on with an empty group?

## Options considered

- **A — Create on first use; refuse loudly on a damaged store.** The first `add person` writes
  the file with no ceremony. If the file exists and cannot be parsed, every command prints an
  error naming the file and exits non-zero, and writes nothing. Consequence: nothing to learn
  before you can use the tool, and a damaged store is a problem you are told about while the
  original file is still on disk to be rescued.
- **B — Create on first use; treat a damaged store as empty.** As A, but a file that cannot be
  read is ignored and overwritten by the next write. Consequence: the tool always works, and
  that is exactly the failure mode described above — silent data loss in a tool whose whole
  value is remembering things.
- **C — An explicit initialise step.** The group is created by a command you run once; every
  other command fails until then, with a message telling you to run it. Consequence: the "wrong
  directory" mistake in EP-001/Q-003 option B becomes impossible to make silently, because an
  uninitialised directory refuses to work rather than starting an empty ledger. The cost is one
  more thing to know before the tool does anything.
- **Recommendation:** **A**, unless your answer to EP-001/Q-003 is "one ledger per directory" —
  in which case **C**, because per-directory storage plus silent creation is the combination that
  quietly starts an empty ledger when you `cd` to the wrong place. If you answer Q-003 and not
  this one, I will treat that pairing as your answer here and record it as assumed.

## Answer

[human] Just create it automatically the first time, I don't want an extra setup step. If the
file's broken, tell me rather than quietly starting over with nothing.

**[answer-questions]** Recorded as **option A — create on first use; refuse loudly on a damaged
store**, both halves taken from the stakeholder's two sentences.

The conditional in this question's own recommendation does not fire. It said **C** (an explicit
initialise step) would be right *if* `EP-001/Q-003` came back as one-ledger-per-directory,
because per-directory storage plus silent creation quietly starts an empty ledger when you `cd`
to the wrong place. `EP-001/Q-003` came back *"One group — just me and my friends, no second
group I need this for"*, so the store is a single fixed per-user file and that trap does not
exist. Silent creation is therefore safe, and it is also what the stakeholder asked for directly.

"Tell me rather than quietly starting over with nothing" is stronger than it looks and is
recorded as such: a damaged store must be fatal to **writes** as well as reads. The failure mode
being guarded against is a write that treats an unparseable file as an empty group and renames a
fresh one over it — at which point the data is gone and no error was ever printed.

The stakeholder did not say where the file lives, and nothing in the record does; the item's own
Notes recorded it as undecided. That is an architect's decision and is recorded as
`docs/architecture/adr/ADR-0002-one-store-file-per-user.md`, which also settles the format
(JSON), the creation rule, the `EXPENSES_STORE` override for tests, and atomic writes — the last
so that an interrupted run cannot itself produce the damaged file AC6 has to report.
