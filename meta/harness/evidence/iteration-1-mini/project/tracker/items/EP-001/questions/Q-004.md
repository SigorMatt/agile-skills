## Context

You said Python and no external services, and this is a brand-new empty repository — there is no
existing code, no test suite, and `tracker/project.yaml` has no test, lint or build command in
it. Those commands are quality gates in this pipeline: with none set, the "tests pass" gate is
recorded as *skipped* on every item rather than passed, and nothing mechanical ever checks that
the arithmetic in "who owes whom" is right.

I would rather you tell me the constraint than have me invent one. "No external services" is
unambiguous about servers; it is ambiguous about whether a developer tool like pytest may be
installed locally.

**A note on this question's `blocking` field.** This question blocks the epic in substance:
nothing downstream should be designed or built on a guess about it. It is nevertheless recorded
as `blocking: false`, because the toolkit makes `blocking: true` impossible on an epic. In
`.claude/agile-skills/pipeline.yaml` the epic status `open` is `terminal: true`, and the only
transitions into `awaiting-answer` or `blocked` are `from: any-non-terminal` — so there is no
legal transition that suspends an epic. Meanwhile `scripts/validate-workspace` reports
`question.blocking.not-suspended` if an epic carries an open blocking question. The two rules
contradict each other, and `intake`'s own escalation instruction ("set the epic to
`awaiting-answer`") cannot be carried out. Being addressed to `human` is what actually stops the
pipeline here (`spec/question.md` rule 4, and `pipeline.yaml` `orchestrator.steps` step 2), and
that does not depend on `blocking`. The work items this question bears on carry their own
blocking questions and are properly suspended.

## Question

What must this fit into: which Python version can you rely on, and may the project install
developer dependencies such as pytest — or must it be standard library only, including its
tests?

## Options considered

- **A — Standard library only, tests with `unittest`.** Runs anywhere Python does; `python3 -m
  unittest` is the test command. Consequence: no install step at all, and the promise "installs
  nothing from the internet" holds for contributors too. `unittest` is more verbose than pytest,
  which costs a little test-writing effort and nothing else.
- **B — Standard library at runtime, pytest for development.** The tool itself imports nothing
  outside the standard library; the test suite needs `pip install pytest`. Consequence: nicer
  tests, but anyone running them needs network access once, which sits awkwardly next to "no
  external services".
- **C — No automated tests.** Consequence: I would have to record an ADR saying why the project
  has no test command, and every item would ship on manual checking alone. For a tool whose only
  job is arithmetic about people's money, I think this is the wrong trade, and I am naming it
  only so the option is on the record.
- **Recommendation:** **A**, plus the oldest Python version you actually have — if you do not
  know, "whatever is on my machine" is a fine answer and I will target 3.9 and note the
  assumption. A is the only option that keeps the no-installation promise end to end.

## Answer

[human] Whatever you think is best — you know this better than I do.

**[answer-questions]** The stakeholder delegated the choice rather than making it, so this is an
architect's decision and is recorded as one: `ADR-0001-python-baseline-and-no-dependencies.md`.

Recorded as **option A — standard library only, at runtime and in tests**, with CPython **3.9+**
as the baseline. The reason A rather than B is not taste: EP-001's own success measure says the
tool "runs on a machine with a Python interpreter and no network access, and installs nothing
from the internet", and `docs/product/vision.md` says the same. Option B would make that true of
the shipped tool and false of the repository, because nobody could run the tests on that machine.
Option C (no tests) is rejected outright — the product is arithmetic about people's money, and
EP-001's "amounts net to zero, to the last minor unit" measure is a property only a suite can
hold down.

3.9 is the floor because it is the oldest interpreter plausibly present on the machine described,
and nothing in the design needs anything newer. The ADR names the syntax and APIs that are
therefore off-limits.

Two consequences are deliberately left for `plan` to execute rather than done here, because
`spec/doc-header.md` §5 and `tracker/project.yaml`'s own comment assign them to that skill:
`commands.test` must be set to `python3 -m unittest discover -s tests -t .`, which clears the
`project.commands.test-null` warning `validate-workspace` currently reports; and `commands.lint`
stays `null`, so the `no-lint-errors` gate is legitimately skipped citing ADR-0001 §4 rather than
silently omitted.
