## Context

While answering EP-001/Q-002 you added a new request: *"Also, I want to import expenses from my
bank's CSV export instead of typing them in — can we add that too?"*

I have not built it and I have not refused it. It is recorded on the epic under
`## Requested, not yet scoped`, and the epic's old blanket exclusion of "importing from a bank, a
spreadsheet, or a chat export" has been narrowed to drop the bank case, because you have now
asked for it directly.

The reason it is not already a work item is a specific one, not caution. **A bank statement row
cannot say who shared the expense.** A row gives you a date, a description like
`CARD PURCHASE - TRATTORIA LUCE`, and an amount — and the account is yours, so the payer is
always you. But "who shared it" is the field this entire tool turns on: it is what turns 60.00
into "Bob owes you 20". Nothing in a CSV supplies it. So "instead of typing them in" is not
achievable as stated — some typing has to remain, and the question is *which* typing.

There is a second, smaller problem: there is no such thing as "bank CSV format". Every bank
exports different column names, a different date format, and either one amount column with a
sign or separate debit and credit columns. Whatever we build has to be told, once, what your
bank's file looks like — or has to guess, and guess wrong on somebody's statement.

I am asking rather than choosing because the options below are not variations on one feature.
They are different features with different amounts of work, and which one is right depends
entirely on how you would actually use it, which I have no way to observe.

**A note on this question's `blocking` field.** As with EP-001/Q-001..Q-005, it is recorded as
`blocking: false` because the toolkit makes `blocking: true` impossible on an epic: in
`.claude/agile-skills/pipeline.yaml` the epic status `open` is `terminal: true`, and the only
transitions into `awaiting-answer` are `from: any-non-terminal`, so there is no legal way to
suspend an epic. Being addressed to `human` is what actually stops the pipeline
(`pipeline.yaml` `orchestrator.steps` step 2). Nothing is being built on a guess about this.

## Question

What should importing a bank CSV actually do — given that the file can supply the date, the
description and the amount, but can never say who shared the expense?

## Options considered

- **A — Import as a draft, then confirm each row.** The tool reads the CSV and, for each row you
  pick, asks who shared it and records an expense with the amount, date and description already
  filled in. Consequence: the typing that remains is the part only you know; the tedious part
  goes away. It is the only option that honestly delivers "I don't want to type these in" without
  inventing data. Cost: a new interactive command, plus the column-mapping problem below. Roughly
  the size of WI-0002 again.
- **B — Import everything as shared by everyone.** Every row in the file becomes an expense paid
  by you and shared by the whole group. Consequence: one command, no questions, done in seconds.
  Cost: it is wrong for every row that was not a group expense — your own groceries, your rent,
  your train to work — so you would have to either pre-filter the CSV by hand or accept a ledger
  full of expenses your friends did not incur. There is currently no way to delete an expense
  (EP-001 `## Out of scope`), which makes a wrong import permanent.
- **C — Import only rows you mark, everything shared by everyone.** You edit the CSV first —
  delete the rows that were not group spending — and the tool imports the rest as shared by all.
  Consequence: much less work than A to build, and safe, because you have already decided what
  belongs. Cost: you do the filtering in a spreadsheet, and you cannot express "this dinner was
  just me and Bob" without going back and editing the expense afterwards, which the tool cannot
  currently do either.
- **D — Not now.** It stays recorded on the epic as a request and becomes its own epic once
  expenses and balances are working and you have used them for a trip. Consequence: WI-0001,
  WI-0002 and WI-0003 ship sooner, and by then you will know from real use whether most of your
  group spending is "shared by everyone" — which is the fact that decides between A and C.
- **Recommendation:** **D**, then **A**. You told me in Q-002 to "get expenses and balances
  working first", and this is a larger piece of work than any of the three items that would
  deliver that, so taking it now would push the thing you actually asked for further away. When
  it does come, A is the shape that matches what you said you wanted; C is the cheap version if A
  turns out to be more than it is worth.

  Two things would change my mind, and both are quick to say: if you are sitting on a backlog of
  expenses right now and cannot face typing them, say so and I will take **C** immediately, since
  it is small. And if most of your group spending really is shared by everyone, **B** stops being
  reckless and becomes reasonable — but I would want to add a way to delete an expense first,
  because an import that cannot be undone is a bad first experience of a tool about money.

  **Whichever you pick, please also attach or paste the first two lines of an actual export from
  your bank** — the header row and one data row, with the amount changed if you like. That single
  fact settles the column-mapping problem for free, and without it any of A, B or C starts with
  another round of questions.

**[answer-questions]** Recorded as **D now, A later**, which is what the answer says and is the
recommendation this question made.

Concretely, three things are now settled and one is outstanding.

1. **Bank-CSV import is out of scope for EP-001**, deferred to a later epic. It is not refused.
   EP-001's `## Requested, not yet scoped` section has been removed, because it existed only to
   hold this request while it was unshaped, and the request has moved into `## Out of scope` as a
   deferral — the same form the epic already uses for settling up (EP-001/Q-002), which the
   stakeholder deferred in the same words: *"get expenses and balances working first."*
2. **The shape it will take is option A**, not B or C. The stakeholder wrote "D then A", and "A"
   in this question is: read the CSV, and for each row the user picks, ask who shared it,
   recording an expense whose amount, date and description are already filled in. B and C are
   therefore closed off — a future epic should not re-litigate them, and specifically should not
   bulk-import rows as shared-by-everyone, which this question flagged as unsafe while there is
   no way to delete an expense.
3. **Nothing in EP-001 changes to accommodate it.** WI-0001, WI-0002 and WI-0003 keep exactly the
   criteria they have. Worth noting for the future epic, so it is not rediscovered: option A
   needs an expense to carry a date and a description, and EP-001 already gives it both
   (WI-0002/Q-001 — an optional description, and a settable date defaulting to today), so the
   store does not need reshaping.
4. **Outstanding: the export sample.** The stakeholder undertook to send the header row and one
   data row of a real export, which is the input that settles the column-mapping problem this
   question raised. It is recorded in the epic and the vision as the future epic's one
   prerequisite. No follow-up question has been filed for it, because filing one would stop the
   pipeline (`pipeline.yaml` orchestrator step 2) to chase something the stakeholder has already
   said they will send unprompted, and nothing in EP-001 waits on it.

No ADR was written. An ADR records a decision the architect made where the record was silent;
this decision was made by the stakeholder, and the authoritative places for it are the epic's
scope and the product vision, both of which now carry it.
