## Context

You said "my friend group", singular, so I have written the epic around a single shared ledger.
Before that hardens I want to check it, because it decides two visible things: whether every
command needs to know which group it is talking about, and where the data file lives.

If there is one ledger, the tool can keep one file in a fixed place and no command ever mentions
a group. If there can be several — the ski trip, the flat, the Tuesday football lot — then
either every command carries a group name, or the tool keys off the directory you run it in, and
"who owes whom" has to say which group it is answering for.

**A note on this question's `blocking` field.** This question blocks the epic in substance:
nothing downstream should be designed or built on a guess about it. It is nevertheless recorded
as `blocking: false`, because the toolkit makes `blocking: true` impossible on an epic. In
`.claude/agile-skills/pipeline.yaml` the epic status `open` is `terminal: true`, and the only
transitions into `awaiting-answer` or `blocked` are `from: any-non-terminal` — so there is no
legal transition that suspends an epic. Meanwhile `scripts/validate-workspace` reports
`question.blocking.not-suspended` if an epic carries an open blocking question. The two rules
contradict each other, and `intake`'s own escalation instruction ("set the epic to
`awaiting-answer`") cannot be carried out. Being addressed to `human` is what actually stops the
pipeline here (`spec/question.md` rule 4, and `pipeline.yaml` `orchestrator.steps` step 2), and
that does not depend on `blocking`. The work items this question bears on carry their own
blocking questions and are properly suspended.

## Question

Is this one ledger for one friend group, or must the tool keep several separate groups apart?

## Options considered

- **A — One ledger, one fixed file.** Every run reads and writes the same store. Consequence:
  simplest commands and nothing to get wrong; a second group means a second copy of the tool or
  manually moving the file.
- **B — One ledger per directory.** The store lives in the directory you run the tool in, so
  `~/trips/ski` and `~/flat` are separate groups for free. Consequence: no new command-line
  arguments, and separation is a filesystem fact rather than a feature — but running the tool
  from the wrong directory silently starts an empty ledger, which is a real way to lose data.
- **C — Named groups inside one store.** Commands take a group name, with a default.
  Consequence: explicit and safe against the "wrong directory" trap; costs a name on every
  command and a concept in the data model that you may never use.
- **Recommendation:** **A**, on your wording. But if you can already name a second group you
  would use this for, say so — B and C are much cheaper to choose now than to retrofit, and this
  is exactly the constraint people remember one week after the tool is written.

## Answer

[human] One group — just me and my friends, no second group I need this for.

**[answer-questions]** Recorded as **option A — one ledger, one fixed store**. Options B (one
ledger per directory) and C (named groups in one store) are both declined, and the group concept
stays out of the data model entirely.

This answer also settles the conditional attached to `WI-0001/Q-002`, whose recommendation was
"create the store silently *unless* this question comes back as one-ledger-per-directory". It did
not, so the dangerous pairing — per-directory storage plus silent creation, which starts an empty
ledger when you `cd` to the wrong place — cannot arise, and creating silently is safe.

What the stakeholder's words do not settle is **where** the one file lives, which WI-0001's Notes
record as undecided and which every one of WI-0001's, WI-0002's and WI-0003's persistence
criteria depend on. That is an architect's decision and it is recorded as
`ADR-0002-one-store-file-per-user.md`: a fixed per-user path
(`$XDG_DATA_HOME/expenses/store.json`, defaulting to `~/.local/share/expenses/store.json`),
overridable by `EXPENSES_STORE` for tests, JSON, created on first write, atomic writes, and a
damaged store fatal to every command. The ADR states explicitly that the override is not a
groups feature, so that it cannot be read as quietly reinstating option C.
