## Context

Your idea describes an expense as "paid by someone and shared by some or all" — an amount, a
payer and a set of sharers. That is enough to compute balances, and it is all WI-0002's criteria
currently require. But an expenses list of

    30.00  Alice  Alice, Bob, Carol
    22.50  Bob    Alice, Bob

is unreadable a fortnight later, and AC4 asks for a listing that a person can actually use. What
that listing needs is whatever an expense carries beyond the arithmetic — a description, a date —
and I do not want to invent required fields, because a required description makes recording an
expense slower at exactly the moment it happens (at the table, at the end of a meal), which is
the failure mode EP-001/Q-005 is about.

Definition of Ready criteria this blocks: **R4** for AC4 — I cannot say what the listing shows
until I know what an expense carries.

## Question

Besides the amount, the payer and the sharers, what must an expense record: a description, and
a date? For each, is it required, optional, or not there at all?

## Options considered

- **A — Description required, date recorded automatically.** Every expense has a label you type;
  the tool stamps the date itself from the clock. Consequence: the listing reads like a receipt
  and needs no extra typing for the date. The cost is that you can never record an expense
  without thinking of a word for it, and there is no way to enter one you forgot to log last
  Tuesday.
- **B — Description required, date optional and enterable.** As A, but you may give a date and
  otherwise today's is used. Consequence: covers catching up on a backlog of expenses, which is
  how a group actually uses a tool like this after a trip. Costs one more optional input and a
  date format to agree on.
- **C — Description optional, date recorded automatically.** The fastest possible entry; the
  listing shows a blank where you did not bother. Consequence: nothing slows down recording, and
  the listing degrades to the unreadable form above exactly to the extent that you skip
  descriptions.
- **D — Neither; amount, payer and sharers only.** Consequence: the smallest possible item, and
  the listing is the table above. Honest, but I think you would ask for descriptions within a
  week of using it.
- **Recommendation:** **B**. A description is what makes the listing worth reading, and being
  able to back-date is what makes the tool usable for the trip you are already halfway through.
  If speed of entry is your real concern, say so — that is EP-001/Q-005 — and I will record **C**.

## Answer

[human] A short description would help, and let me set the date myself since I'm usually
catching up days later. Don't force the description though, sometimes I just want to log it
fast.

**[answer-questions]** Recorded as a **hybrid of options B and C**, which is what the answer
actually describes: a description that is **optional** (from C and from "Don't force the
description though"), and a date the person recording can set, defaulting to today (from B, and
from "let me set the date myself since I'm usually catching up days later").

Neither B nor C alone fits. B required the description; C stamped the date from the clock with no
way to back-date. The stakeholder wants the entry-speed property of C and the back-dating
property of B, and there is nothing in the two that conflicts, so both are recorded rather than
one being forced to stand for the other.

The date format was not asked about and the record is silent on it. Fixed here as `YYYY-MM-DD`,
because an acceptance criterion saying "a date" is not decidable by someone with a terminal —
which is what the Definition of Ready requires — and because `YYYY-MM-DD` is the one format that
is unambiguous between the day-first and month-first conventions, sorts correctly as text, and is
what `datetime.date.fromisoformat` already parses on the 3.9 baseline of ADR-0001. Reversible: it
is one parse call and one help string.
