WI-0002 AC4 says a command lists the expenses recorded so far and what each row shows — the

come out in, and no answer you have given settles it. That fails the Definition of Ready's R4:

It matters here more than it usually would, because of your own answer to Q-001:

> *"let me set the date myself since I'm usually catching up days later"*

So the order you type expenses in and the order they happened in are routinely **different**. If

## Question

When you list the expenses, what order should they come out in — the order you entered them, or
the date each expense happened on (and if by date, oldest first or newest first)?

## Options considered

- **A — The order you entered them**, oldest entry first. Matches WI-0001's roster listing.
  Consequence: the list is a log of what you typed. Back-dated expenses appear where you typed
  them, not where they happened, so a catch-up session lands as a block at the end.
- **B — By the expense's date, oldest first**, with the entry order breaking ties between two
  expenses on the same day.
  Consequence: the list reads like a diary of the trip, which is how you would check it against
  your memory. An expense entered late slots into its right place. The cost is that the list is
  no longer a record of what you did most recently.
- **C — By the expense's date, newest first.** The same as B, reversed.
  Consequence: the thing you most likely just entered is at the top, which is handy on a long
  list. Reading a trip in order means reading bottom to top.
- **Recommendation: B.** It is the one that follows from what you told us about how you work —
  entering things days later — and it makes the tie-break rule (same day, entry order) an
  obvious extension of WI-0001's precedent rather than a new idea. A is the cheapest to build
  and would not be wrong; C is worth choosing only if you expect the list to get long enough that
  scrolling is the main cost.

**Also assumed while you answer, so you can correct it in the same breath:** listing expenses
when **none** have been recorded exits zero and prints a message saying there are none — the same
shape as WI-0001 AC4's *"Nobody in the group yet."* rather than failing or printing nothing.
That is written into the item as an assumption attributed to `refine`, not to you; say so if you
