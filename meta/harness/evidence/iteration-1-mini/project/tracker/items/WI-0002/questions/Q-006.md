## Context

Escalated because it depends on **intent no document records** — whether you want a guard rail
here at all is a preference, not something derivable from what has been written down
(`spec/question.md` §4, first condition).

WI-0002 AC7 says an expense may carry a date in `YYYY-MM-DD`, that an invalid calendar date is
rejected, and that today's date is used when you give none. It says nothing about a date that is
a perfectly valid calendar date but is in the **future**: `2027-01-01`, or the typo `2062-08-21`
for `2026-08-21`.

This is a live risk rather than a theoretical one precisely because you asked to type dates by
hand — *"let me set the date myself since I'm usually catching up days later"*. A hand-typed year
is the easiest field in the whole tool to get wrong, and a wrong year is invisible in the totals:
the arithmetic in WI-0003 is unaffected by the date, so nothing downstream would flag it. You
would only find it by reading the list.

Rejecting future dates costs you the ability to record something in advance — a deposit for a
trip next month, a booking someone has already paid for.

## Question

Should the tool accept a date in the future, or reject it?

## Options considered

- **A — Accept any valid calendar date, past or future, with no comment.** The current wording of
  AC7 by default.
  Consequence: you can pre-record a booking. A mistyped year is stored silently and you find it
  by reading the listing, if you ever do.
- **B — Reject a date later than today**, with a message saying the date is in the future.
  Consequence: the mistyped year is caught at the moment you type it, which is the only moment it
  is cheap to fix. You lose the ability to record something dated ahead — you would have to wait
  until the day, or record it with today's date.
- **C — Accept it, but print a note on stderr** saying the date is in the future, exit zero.
  Consequence: both are possible; the mistake is visible without being fatal. It is the same
  shape as the note WI-0002 AC8 already prints when the payer is not among the sharers, so it is
  a pattern the tool would already have. The cost is one more thing on stderr you might learn to
  ignore.
- **Recommendation: C**, weakly. It matches a guard the tool already has for a different
  "probably-a-mistake-but-legitimate" case, so it adds no new concept, and it does not take away
  a capability. **B** is the better answer if you are certain you will never record something
  dated ahead — it is the only one that actually stops the typo.
