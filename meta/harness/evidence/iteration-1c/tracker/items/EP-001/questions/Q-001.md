## Context

Intake has split your idea into four work items:

- WI-0001 — add and list the people who share expenses
- WI-0002 — record an expense paid by one person and shared by several
- WI-0003 — show who owes whom
- WI-0004 — import expenses from your bank's CSV export

Three of these have a forced order: expenses need people to exist, and the report needs
expenses to exist. The CSV import is the one with real freedom — it could be built third, so
that you stop typing expenses in as early as possible, or fourth, so that the report you asked
for exists first.

You did not state an order, and the orchestrator executes the priority field as if it were your
intent, so intake will not guess it. The items currently carry priorities that produce the order
WI-0001, WI-0002, WI-0003, WI-0004.

This question is filed `blocking: false`. Not because the answer is optional — it changes which
item is built third — but because an epic at `open` cannot be suspended: `open` is terminal in
`pipeline.yaml`, so no transition into `awaiting-answer` exists for it, while
`validate-workspace` reports an open blocking question on an `open` epic as an error. Marking it
non-blocking is also the honest reading: WI-0001 is first under every ordering, so nothing is
actually stopped by this question. The orchestrator stops the loop on any open human-addressed
question regardless of the flag.

## Question

In what order do you want these four items delivered — specifically, should the CSV import
(WI-0004) come before or after the "who owes whom" report (WI-0003)?

## Options considered

- **A — WI-0001, WI-0002, WI-0003, WI-0004.** The report is finished before the import starts.
  Consequence: you get the answer you actually asked for ("who owes whom") at the earliest
  point, and keep typing expenses in by hand until the last item lands.
- **B — WI-0001, WI-0002, WI-0004, WI-0003.** The import is finished before the report starts.
  Consequence: you stop retyping transactions sooner, and by the time the report arrives it has
  real data to run on; but until then the tool records expenses and tells you nothing.
- **C — something else**, including dropping or deferring an item entirely. Consequence: intake
  re-splits and the priorities change accordingly.
- **Recommendation:** A. The report is the part of the idea you stated as the outcome ("at any
  point show who owes whom"); the import is stated as a convenience about how expenses get in.
  Building the outcome first also means the import in WI-0004 can be checked against a working
  report rather than against a list.

## Answer

[human] Whatever you think is best, honestly. If I had to pick, get me the report working first — that's the bit I actually asked for. Import can come after.

**Read by `answer-questions` as option A**, and as the stakeholder's own choice rather than a
delegation: they opened by deferring, then picked, and gave the reason — the report is the thing
they asked for. That is a statement of intent, not a shrug, so it is recorded as their decision.
Route: recorded intent. The order is WI-0001, WI-0002, WI-0003, WI-0004.

**The order was written into the priority field, not only into prose.** WI-0004's priority went
from `high` to `medium`. Before this change the order the orchestrator would actually execute
came out right by accident: WI-0003 and WI-0004 were both `high`, both created in the same
second, and the tie fell to WI-0003 only because `WI-0003` sorts before `WI-0004`. Intent that
survives only as a tie-break is intent nobody can see and anybody can break — renaming or
re-creating an item would silently reverse it. `pipeline.yaml`'s selection key is
priority-rank, then `created`, then ID, so `medium` puts WI-0004 last on the field that means
it.

Nothing else moved. WI-0001 and WI-0002 stay `critical` and WI-0003 stays `high`; the first
three were forced by data dependencies before this question was asked and are unaffected by its
answer.
