## Context

AC3 says the tool "says so rather than failing silently" when a name is already registered, and
AC4 says listing when nobody is registered "produces a message saying so, and does not error".
Neither pins the words or the exit code.

That gap lands on `verify`, which judges this item against these criteria and is not allowed to
ask you anything. Faced with a tool that prints nothing after adding someone, it has to guess
whether silence is what you wanted. Exit codes matter for a second reason: they are what decides
whether you can ever use these commands inside a shell script or a `&&` chain.

There is also an ordering question hiding in AC1: with three people registered, "showing the
added name" does not say what order the names come out in.

## Question

For each of these four cases, what should the tool print, on which stream, and what should it
exit with — (i) adding a new person; (ii) adding someone already registered; (iii) listing when
several people are registered; (iv) listing when nobody is?

## Options considered

- **A — quiet on success, Unix style.** (i) prints nothing, exits 0. (ii) `Ana is already
  registered` on stderr, exits 1. (iii) one name per line on stdout, exits 0. (iv) `No one is
  registered yet` on stderr, exits 0. Consequence: composes perfectly with other commands. The
  silence after adding a person reads as "did that do anything?" until you list them.
- **B — confirm everything, and treat a duplicate as harmless.** (i) `Added Ana`, exits 0. (ii)
  `Ana is already registered` on stdout, exits 0. (iii) one name per line, exits 0. (iv) `No one
  is registered yet` on stdout, exits 0. Consequence: the friendliest thing to use by hand.
  Nothing in a script can tell a fresh add from a duplicate, because both say 0.
- **C — confirm everything, but a duplicate is an error.** (i) `Added Ana`, exits 0. (ii) `Ana is
  already registered` on stderr, exits 1. (iii) and (iv) as B. Consequence: readable by hand and
  usable in a script. You do see a non-zero exit for something that did no actual harm.
- **Recommendation:** C, and for (iii) listing the names in alphabetical order — it is stable, so
  the same data always prints the same way, which is what makes AC1 checkable. Say if you would
  rather see people in the order you added them.

## Answer

[human] Whatever you think is best here — this is exactly the kind of thing I'm paying you to decide.

**Read as a delegation, and decided by the architect. Route: decided, recorded as
`docs/architecture/adr/ADR-0005-output-streams-and-exit-codes.md`.** `answered-by` is
`answer-questions` for the same reason as Q-001: the stakeholder authorised the decision rather
than making it.

**The decision — option C, plus alphabetical listing, generalised into a project-wide
convention.** Concretely, for the four cases asked about:

- (i) adding a new person: `Added Ana` on stdout, exit 0;
- (ii) adding someone already registered: `Ana is already registered` on stderr, exit 1, nothing
  stored;
- (iii) listing several people: one name per line on stdout, exit 0, ordered by the trimmed
  case-folded name (ADR-0003 clause 4) and each displayed as first entered;
- (iv) listing when nobody is registered: `No one is registered yet` on **stdout**, exit 0 —
  "nothing to show" is a true answer to a fair question, not an error, which is what WI-0001 AC4's
  "does not error" asks for.

Around those, three conventions the whole epic now shares: a usage error exits 2 (`argparse`'s own
behaviour, adopted rather than overridden so that 2 means "impossible request" and 1 means
"understood and refused"); a refusal leaves the data file byte-for-byte unchanged; and messages
are plain sentences with no colour, emoji or `Error:` prefix, because the stream already carries
that information.

**Why C over A and B.** A's silence after adding a person is wrong for this user — they are a
person at a terminal, not a pipeline, and EP-001 has no other feedback channel. B makes a fresh
add and a duplicate both exit 0, so nothing in a script, and nothing in `verify`, can tell them
apart; that is precisely the "failing silently" WI-0001 AC3 forbids. C's one cost — a non-zero
exit for something harmless — is the correct behaviour when the duplicate was a mistake, which is
the case this item exists to catch.

**Why the ordering was decided here too.** AC1 said "showing the added name" without saying in
what order several names appear, so no listing could be checked by comparing output. Alphabetical
by the normalised name is stable, needs no stored insertion order, and reuses the sort key
ADR-0001 and ADR-0003 already define.
