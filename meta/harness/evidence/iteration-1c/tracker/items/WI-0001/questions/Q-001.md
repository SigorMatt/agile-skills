## Context

Three of WI-0001's four acceptance criteria say "a documented command". The Definition of Ready
(R4) requires every criterion to be decidable by someone with a terminal and no context, and
nobody can run "a documented command". Intake left the names deliberately unpinned and said
`refine` should settle whatever it needs; this is that.

It is worth answering once, now, rather than four times later. The same command surface is what
the next three items extend — recording an expense, printing the report, importing a CSV — so
whatever you choose here is what you will be typing for all of it.

One constraint from your own success measures: EP-001 SM4 says every command runs on a stock
CPython interpreter with no third-party package. All three options below satisfy that.

## Question

What is the tool called, and how do you want to invoke it — specifically, what exact words add a
person and what exact words list the people?

## Options considered

- **A — one script, run through the interpreter.** `python3 expenses.py add-person Ana` and
  `python3 expenses.py list-people`. Consequence: no setup step at all; you can copy the file
  anywhere and it works. You type `python3 expenses.py` every single time.
- **B — an executable on your PATH.** `expenses add-person Ana` and `expenses list-people`.
  Consequence: shortest to type and it reads like a real tool. Costs one documented setup step
  (make it executable, put it somewhere on your PATH), which the install instructions must
  spell out.
- **C — short subcommands instead of verb-noun ones.** `expenses add Ana` and `expenses people`.
  Consequence: fastest to type. The trouble arrives at the next item, where `add` has to mean
  either a person or an expense; disambiguating later means changing commands you have already
  learned.
- **Recommendation:** B. It gives the shortest thing to type that still survives the tool growing
  to five commands, and the one setup step is a line in the documentation rather than a
  dependency. If you would rather not put anything on your PATH, say so and we use A with the
  same subcommand names — that choice is reversible and changes nothing else.

## Answer

[human] Whatever you think is best, honestly — you know this better than I do.

**Read as a delegation, and decided by the architect. Route: decided, recorded as
`docs/architecture/adr/ADR-0002-command-line-surface-single-executable-with-verb-noun-subcommands.md`.**
`answered-by` is `answer-questions` rather than `human`: the stakeholder supplied the
authorisation to decide, not the decision, and the record must not credit them with a choice they
explicitly handed back. This follows the precedent set on WI-0003/Q-002.

**The decision — option D, a variant of the recommended option B.** The tool is one executable
file named `expenses` at the repository root, with a `#!/usr/bin/env python3` shebang and the
executable bit committed. Every acceptance criterion and every worked example invokes it as
`./expenses <subcommand> …` from the repository root; the README additionally documents copying
or symlinking it onto a directory in `PATH`, so the stakeholder can type `expenses add-person
Ana` from anywhere. Subcommands are lowercase, hyphenated and verb-noun: `add-person` and
`list-people` here, with `add-expense`, `list-expenses`, `report` and `import-csv` reserved for
the later items.

**Why not B exactly, given that B was the recommendation.** B makes every criterion in this epic
depend on a setup step having been performed. `verify` is not allowed to ask anyone anything, so
a criterion that fails because `expenses` was never put on `PATH` is indistinguishable, from
where `verify` stands, from a criterion that fails because the tool is broken. Option D keeps B's
ergonomics as documentation while making the criteria decidable by someone who has just cloned
the repository — which is exactly what the Definition of Ready R4 asks for. The stakeholder's own
typing experience is unchanged, because the optional `PATH` install is the same install B would
have required.

Option C's short subcommands were rejected on the ground the question already stated: `add`
cannot mean both a person and an expense by WI-0002, and renaming a learned command is the
expensive version of this choice. Option A was rejected because it welds `python3` into every
criterion and every line of documentation for the life of the tool.
