## Context

AC6 says that `add-expense` run without `--date` "stores the current date on the machine running
it, **so the rendered line begins with the output of `date -u +%F`**". The second half was added by
`refine` to make the criterion checkable. It contradicts the first half on any machine that is not
running UTC, and this machine is one of them:

```console
$ date
Sat Aug 22 01:11:38 AM IDT 2026
$ date +%F
2026-08-22
$ date -u +%F
2026-08-21
```

So right now, "the current date on the machine" is 2026-08-22 and `date -u +%F` is 2026-08-21.
Whichever way an implementation goes, one half of AC6 fails.

What the stakeholder actually asked for is in WI-0002/Q-002, in their own words: *"Yeah, give
expenses a date. If I don't type one, just use today's date."* They are one person recording
expenses on their own laptop (`docs/product/vision.md`, "Who it is for"), so "today" is the date on
that laptop's calendar, not the date in Greenwich. On a laptop in this timezone, a dinner recorded
at 1am on the 22nd would be dated the 21st under a UTC implementation — the day before it was
typed, and the day before the bank's own statement will show it (WI-0004).

`plan` cannot resolve this: only `refine` and `answer-questions` may amend an acceptance criterion,
and picking the reading that suits the implementation is exactly what this protocol exists to stop.
Nothing else in WI-0002's plan turns on it — one step and one criterion do.

## Question

Should an expense recorded without `--date` be stamped with the machine's **local** date or its
**UTC** date, and should AC6's check clause be amended to match?

## Options considered

- **A — local date; amend AC6's check clause to `date +%F`.** Consequence: matches the
  stakeholder's words and the laptop's calendar, and matches the date their bank statement will
  show for the same transaction. The criterion becomes exact on every machine, because `date +%F`
  and `datetime.date.today()` read the same clock and the same timezone. Costs one amended clause
  in AC6.
- **B — UTC date; leave AC6 exactly as written.** Consequence: nothing to amend, and the criterion
  is already exact. An expense typed after 21:00 in this timezone is dated the previous day, which
  the stakeholder will see as a bug and cannot correct, because editing an expense is out of scope
  for the whole epic.
- **C — store a full timestamp with an offset, and render only the date.** Consequence: no
  information is lost and a future feature could show times. It is more stored state than anything
  in the epic asks for, it changes the expense record shape that WI-0003 and WI-0004 will both
  build on, and it does not actually decide today's question — the rendered date still has to come
  from one clock or the other.
- **Recommendation:** A. The stakeholder's own sentence settles the substance, and the defect is in
  the criterion's check clause rather than in what was asked for. B is only attractive because it
  needs no edit, which is the worst reason to choose a behaviour the user would call wrong.

## Answer

**Option A — the machine's local date, and AC6's check clause is amended to `date +%F`.**

Route: **recorded intent**, not an architect's preference. The stakeholder answered this in
WI-0002/Q-002 in their own words — *"Yeah, give expenses a date. If I don't type one, just use
today's date"* — and `docs/product/vision.md` (v9, "Who it is for") establishes whose today it is:
one person, at a terminal, on their own laptop. Today on that laptop is the local date. No ADR was
written, because nothing here is the architect's decision to make; the substance was already
settled and the defect was in a clause `refine` added to make the criterion checkable.

**What was wrong, stated plainly.** `refine` wrote AC6's check as `date -u +%F` while its first
half said "the current date on the machine running it". On a machine in UTC those are the same
string, so the contradiction was invisible when it was written; on this machine, at the moment
`plan` read it, they were different days. `plan` was right to stop: an implementation that
satisfied one half would have failed the other at `verify`, and the failure would have looked like
a defect in the code rather than in the criterion.

**Why not B.** Leaving AC6 as written costs no edit, and that is its only merit. It would date an
expense typed at 1am in this timezone to the previous day — the day before the user typed it, and
the day before their bank statement will show the same transaction (WI-0004 AC2 takes the row's
own date, which is a local banking date, not a UTC instant). EP-001 excludes editing an expense, so
the user could not correct it. Choosing a behaviour the user would call wrong because the criterion
happens to be phrased that way is the arrow-and-target inversion this skill's own guidance warns
about.

**Why not C.** Storing a full timestamp with an offset is more stored state than any criterion
asks for, it changes the expense record shape that WI-0003 and WI-0004 both build on, and it does
not even answer the question — the rendered date still has to be taken from one clock.

**What implementation this fixes**, so that `plan` does not have to re-derive it: the default date
is Python's `datetime.date.today()`, which reads the same clock and timezone as `date +%F`. It is
**not** `datetime.datetime.now(timezone.utc).date()`. A `--date` value supplied by the user is
taken as given and no timezone conversion is applied to it, so an expense dated by hand and one
dated by default are the same kind of value — which is what AC6's "otherwise indistinguishable"
requires.

**Not escalated to the stakeholder**, and the reason is worth recording: none of `spec/question.md`
§4's conditions applies. The intent *is* recorded (Q-002), the choice is reversible (one function
call), it contradicts no ADR, and the record is not silent. Asking would have stopped the loop to
have them repeat a sentence they had already written.

## Consequences

- `tracker/items/WI-0002/item.md` — AC6's check clause amended: the default date is read from the
  machine's own clock and timezone and the rendered line begins with `date +%F`, with `date -u +%F`
  named explicitly as what it is not; `## Notes` gains a bullet under "Decided during refinement"
  recording the amendment, who found it and on what basis
- `tracker/items/WI-0002/artifacts/refinement-qa.md` — a new `[assumed]` entry recording that the
  original gloss was `refine`'s and was corrected here, so the Q&A does not read as though the
  stakeholder chose UTC
