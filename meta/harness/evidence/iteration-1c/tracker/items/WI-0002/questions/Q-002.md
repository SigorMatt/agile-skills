## Context

WI-0002 says an expense carries who paid, the amount, a description and who shared in it. It says
nothing about a date, because you did not mention one — intake flagged that in the item's notes
rather than inventing it.

Two things make this worth settling now rather than later:

- **The bank import throws it away otherwise.** Every row of a bank CSV export has a date on it
  (WI-0004). If an expense has nowhere to put one, the import discards the only piece of
  information in the file that says *when*.
- **It is part of the stored shape.** ADR-0001 records that the way amounts are stored is
  expensive to change once you have real data in the file. The same is true of adding a field to
  every expense — it means migrating a file that already has your group's history in it.

What this is *not* about: the report. WI-0003 nets everything ever recorded and filtering by date
is already out of scope there, so a date would not change a single number it prints. This is only
about what gets kept.

## Question

Should an expense carry a date, and if it should, what date does it get when you do not supply
one?

## Options considered

- **A — no dates at all.** Consequence: the smallest thing that works, and nothing to type. The
  date on every imported bank row is discarded, and when you look at the list in three months you
  cannot tell which trip an expense belonged to.
- **B — every expense has a date. A hand-entered one defaults to today; an imported one takes the
  date from its row; `--date 2026-08-14` overrides either.** Consequence: nothing is thrown away,
  the list of expenses reads in the order things happened, and it is free at the point of use
  because the default is what you would have typed anyway. Costs one more field to store and one
  more thing to parse from the CSV.
- **C — imported expenses get a date, hand-entered ones do not.** Consequence: avoids the typing
  and keeps the bank's information. Produces a list where some entries have dates and some do
  not, which reads as a bug and makes any future sorting or filtering ill-defined.
- **Recommendation:** B. It costs almost nothing now and it is the only option that does not
  either lose information or produce an inconsistent record; retrofitting a date onto expenses
  you have already stored is the expensive version of this decision.

## Answer

[human] Yeah, give expenses a date. If I don't type one, just use today's date.

**Read by `answer-questions` as option B, in the stakeholder's own words.** "Yeah, give expenses a
date. If I don't type one, just use today's date." Both halves of the question are settled: yes to
a date, and today is the default. Route: recorded intent — `answered-by` is `human`, because the
decision itself is theirs and not the architect's.

What follows, stated so that `plan` and `implement` are bound by it:

- **Every expense has a date.** There is no dateless expense and no "unknown" date, so option C's
  mixed record — some entries dated, some not — cannot arise, and any future sort or filter is
  well-defined even though none is in scope.
- **The default is the current date on the machine running the command**, not the date the data
  file was created or the date of any other expense. `--date YYYY-MM-DD` overrides it, and an
  expense recorded with `--date` set to today is indistinguishable from one recorded without the
  option. That is AC6.
- **A bad `--date` value is a refusal, not a fallback.** It prints on stderr, exits 1 and records
  nothing, per ADR-0005 clause 2. Quietly substituting today for an unparseable date would store a
  date the user never intended and never sees.
- **Imported expenses take the date from their own row**, which is the point the question made
  about WI-0004 throwing information away. WI-0004 AC2 now says so. Which column carries it and in
  what format cannot be settled here: it is part of the CSV sample the stakeholder has not yet
  supplied (WI-0004/Q-002).
- **The date is recorded information, not a query dimension.** Nothing in EP-001 filters or sorts
  by date — WI-0003's report is over the whole recorded history — so `plan` should store and print
  the date and build nothing else on it. Filtering the report by date is already out of scope on
  WI-0003.
