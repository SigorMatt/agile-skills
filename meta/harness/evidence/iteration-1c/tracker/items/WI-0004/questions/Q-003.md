## Context

WI-0004's out-of-scope list says the tool will not detect that an individual row has already been
imported, and then says explicitly that what happens when you re-import a whole file is *not*
decided and is refinement's to settle. This is that.

It matters more here than it would in most tools, because of something this epic does not have:
there is no way to delete or edit an expense. Editing and deleting are out of scope on EP-001. So
if an accidental second import doubles twelve expenses, the only remedy is to delete the data
file and start the group's ledger again from nothing.

Accidental re-runs are not exotic. Pressing up-arrow and Enter twice, or re-running the command
after it printed a warning about one bad row, both produce it.

## Question

If you import the same CSV file twice, what should the tool do?

## Options considered

- **A — import it again; every expense from the file appears twice.** Consequence: nothing to
  build and nothing to explain. One accidental re-run silently doubles what everyone owes, the
  report is confidently wrong, and the only way back is deleting the data file.
- **B — refuse a file whose contents the tool has already imported, naming when it was imported
  before.** Consequence: the accident is impossible. The tool has to remember a fingerprint of
  every file it has read, and if your bank ever emits two genuinely different statements with
  identical contents, or you really do want the same rows twice, you cannot have them.
- **C — import it again, but only after confirming.** The command notices the file has been
  imported before, says so, and stops unless you pass `--again` (or answer a prompt).
  Consequence: the accident is caught and the deliberate case is still possible. Costs the same
  remembering as B, plus one flag to document.
- **Recommendation:** C. B and C cost almost the same to build, and C is the one that does not
  make a decision you cannot get out of — which matters because the *other* direction, option A,
  is the one you cannot get out of at all while deleting expenses is out of scope.

## Answer

[human] I don't want it silently doubling up — warn me if I'm importing the same file again and make me confirm if I really mean it.

**Read by `answer-questions` as option C, in the stakeholder's own words.** "I don't want it
silently doubling up — warn me if I'm importing the same file again and make me confirm if I really
mean it." Both halves of C are there: the warning, and the confirmation that lets the deliberate
case through. Route: recorded intent — `answered-by: human`, no ADR, because the decision is
theirs.

What this fixes, and what it does not:

- **The accident is caught.** Re-running the same import reports that this file has been imported
  before, says when, imports nothing, and exits 1 (ADR-0005 clause 2). That matters more here than
  in most tools because EP-001 excludes deleting an expense: without this, the only remedy for a
  doubled import is deleting the data file and starting the group's ledger from nothing.
- **The deliberate case survives.** `--again` on the same command imports the file regardless, and
  the expenses genuinely appear twice. Option B — refusing outright — was rejected for exactly
  this: it makes a decision the user cannot get out of, and it costs the same to build.
- **"The same file" means the same contents, not the same path.** AC7 says so, which makes it
  checkable: a renamed or moved file is still recognised, and a file with one row added is a new
  file. `plan` chooses what identifies the contents — a hash is the obvious candidate — and records
  it.
- **Duplicate detection stays per file.** Detecting that an individual *row* has already been
  imported remains out of scope, and the out-of-scope entry now says that plainly rather than
  leaving the file-level case undecided beside it.
- **This adds stored state.** The data file must remember which files have been imported and when
  — the first thing this epic stores that is not derivable from the expenses. The item's `## Notes`
  flags it for `plan`, because it changes the shape of the stored data rather than only the
  behaviour of one command.

## Consequences

- `tracker/items/WI-0004/item.md` — **AC7 added**, stating the warning, the exit code, the `--again`
  confirmation, and that "already imported" is a property of the file's contents; the `## Out of
  scope` entry that said re-import behaviour was undecided is replaced by one that decides it and
  keeps only row-level detection out; `## Notes` records the answer and flags the new stored state
  and the meaning of `--again` for `plan`
- `docs/product/vision.md` — v8 to v9; records that a repeat import warns and requires `--again`,
  and why that is the only safeguard in a tool that cannot delete an expense
