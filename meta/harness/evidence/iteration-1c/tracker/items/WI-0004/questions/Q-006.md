## Context

You have now been asked for a sample of your bank's CSV export five times — Q-001, Q-002, Q-004 and
Q-005 — and five times the answer has been that it is coming later. Nobody is complaining about
that; it is your file and your time. But the fifth asking deliberately made the ask as small as it
could go (the header line and **one** row, or just the path to the file, with the amounts and

That is evidence worth acting on: the obstacle is not the size of the ask, so asking a sixth time in

Your instruction stands and is not in question. You said *"I'd rather you wait for my actual file
than guess"*, and nothing has been guessed: there is no importer, no invented column list, no
plausible-looking layout standing in for your file.

What this question asks is different, and it has never been put to you. **There is a way to build
the import without anyone guessing anything and without the sample: the tool can take the file's
shape from you at the moment you import, instead of knowing it in advance.** You would tell it,
once per import, which column holds the date, which holds the amount and which holds the
description, and what the date looks like. Nothing about your bank is assumed by the tool, because
nothing about your bank is in the tool — the facts come from you, at the keyboard, about the file in
front of you.

That is a trade, not a free lunch, which is why it is yours to decide and not ours: it costs you
four options typed at the import, in exchange for having the feature now instead of whenever the
sample arrives.

Where things stand meanwhile: WI-0001, WI-0002 and WI-0003 are built, verified, reviewed and merged,
so adding people, recording expenses and the who-owes-whom report all work today. WI-0004 is the
only thing left, and EP-001 stays open until it is done, because you said you would not sign off a
version without the import.

`spec/question.md` §4.1 applies — the answer depends on intent no document records. Whether typing a
column mapping at each import is acceptable to you, or worse than waiting, is a fact about what you
want that nothing in the record can settle.

## Question

Would you rather the tool learned your file's shape **from you at import time** — you name the date,
amount and description columns and the date format on the command line, so the import can be built
and finished now — or would you rather we keep waiting for the sample and build it against your
bank's real layout?

## Options considered

- **A — keep waiting.** Nothing changes. The standing request holds: whenever you get to it, paste
  the header line and one row here, or the path to the file. Consequence: WI-0004 stays at `draft`
  and EP-001 stays open until the file arrives; the tool you have today is everything you get until
  then. This is what you have chosen five times and it is still available — choosing it again is a
  legitimate answer, not a failure.
- **B — you state the shape at import time.** The command becomes, for example:

  ```console
  $ ./expenses import-csv statement.csv --paid-by Ana --shared-by Ana,Ben,Cass \
      --date-column "Transaction Date" --amount-column Amount \
      --description-column Description --date-format "%d/%m/%Y"
  ```

  Consequence: the three criteria that are stuck become checkable immediately, because they stop
  depending on a format anyone has to know — reading the file (AC1) and dating each expense from its
  own row (AC2) work against the columns *you* named, and refusing a file that is not in the expected
  format (AC5) becomes refusing a file whose header does not contain the columns you named, which is
  a real check rather than an invention checking itself. Costs: four extra options per import; we
  would settle separately, as a design detail, whether the tool remembers them so you only type them
  once. One thing this route does **not** settle is what to do with a row whose amount is negative or
  sits in a separate "money in" column — under B that would be recorded as an assumption you can
  correct later (proposed: a row that is not a positive charge is skipped and reported by line
  number, which is what AC4 already does for any row the tool cannot use), rather than a guess baked
  into the code.
- **C — both: B now, your bank later.** Build B, and when the sample eventually arrives add a named
  shortcut for your bank so you stop typing the options. Consequence: identical to B today — the
  same decision, the same command — and the sample stays worth sending whenever you get to it.
  Nothing is thrown away either way.
- **D — B, but with the mapping in a small file** you write once (`bank.ini` or similar) instead of
  on the command line. Consequence: the same as B, with the typing moved from every import to one
  setup step. Mentioned because it is the obvious refinement of B; if B appeals but the typing does
  not, say so and this is what you get.
- **Recommendation: C.** It ends the wait without guessing anything, keeps your file useful when it
  turns up, and is reversible — if you dislike naming the columns, the sample-based version can be
  layered on top later without changing anything already built. Choose **A** if you would genuinely
  rather have no import at all for now than type four options; that is a real preference and this
  question exists to let you state it.

Two things are deliberately **not** being asked again, because you have already decided them:
whether the import could be dropped or deferred to a later epic (you refused, Q-002), and where the
payer and the sharers come from (the command line, Q-001). Neither is reopened by any option above.

## Answer

[human] Let's do C — build it against the columns I name now, and I'll still send the sample when I get to it so you can add the shortcut for my bank later. Typing four options each time is fine.

**Answered by the stakeholder, not from the record** — the record could not have settled it, which
is why it was escalated (`spec/question.md` §4.1, intent no document records). Read as three
decisions and one non-decision:

1. **Option C.** The import is built now, against the columns named on the command line, and the
   sample remains welcome for a per-bank shortcut later. AC1, AC2 and AC5 are rewritten against the
   stated mapping and are decidable without anyone knowing the bank's layout.
2. **Option D is refused.** *"Typing four options each time is fine"* is a direct answer to the
   option that offered to move the mapping into a config file. So the four options are required on
   every import (new AC10), and a remembered or file-based mapping is now out of scope rather than
   an open design question — `plan` does not have to decide it.
3. **The sample stops being a precondition.** It is still coming and still wanted, but what it buys
   is a shortcut, filed as a **new item** when it arrives. Nothing waits for it, and nobody should
   ask for it again.
4. **One thing was not decided by them and is recorded as an assumption**, exactly as option B said
   it would be: a row that is not a positive charge is skipped and reported by line number, like any
   other unusable row. They did not overturn that proposal, and silence is not agreement, so it is
   written as `[assumed]` in `artifacts/refinement-qa.md` and flagged inside AC4 itself as
   correctable.

**No ADR was written for this**, deliberately. An ADR records a decision taken here for reasons that
would otherwise be lost; this decision was the stakeholder's, taken in their own words, and those
words are in this file, in `item.md` and in `vision.md` v11. The *architectural* consequence — the
parser takes a column mapping and the tool contains no bank format — is recorded in
`docs/architecture/overview.md` v4, where `plan` will read it. The remaining design choices for the
import are `plan`'s to make and to record as ADRs when it runs.
