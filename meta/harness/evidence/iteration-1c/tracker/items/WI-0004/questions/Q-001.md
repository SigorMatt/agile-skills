## Context

You asked to "import expenses from my bank's CSV export instead of me typing them in". Nothing
in the record says what that file looks like, and "bank CSV export" is not a format — every bank
emits different columns, different date formats, different sign conventions for money in and
money out, and some emit a preamble before the header row.

There is a second, larger gap. A bank row knows that money left your account for a named
merchant. It does not know **who shared in it** — which is the fact the whole tool is built
around. So an import cannot produce a usable expense without a rule for supplying the payer and
the sharers from outside the file.

Intake could invent a format, and the tool would then import a file that does not exist. It is
also not a reversible guess: WI-0004's acceptance criteria, its sample fixture, and the parsing
code all follow from the answer.

## Question

What does your bank's CSV export actually look like, and how should a row in it become an
expense — specifically, who is the payer and who are the sharers?

Please paste the header line and two or three representative rows (amounts and merchant names
can be altered; the shape is what matters), and say which answer below matches how you want to
use it.

## Options considered

On the format itself, there is no choice to make — it is a missing fact, and only you have it.
On how a row becomes an expense, there is:

- **A — Every imported row is paid by you and shared by everyone registered.** You pass no extra
  arguments: `import statement.csv`. Consequence: the simplest possible import, and correct for
  the case where you are the one who pays for the group; wrong for any row that was a personal
  purchase, so you would need to prune the file first or delete expenses afterwards — and
  deleting expenses is currently out of scope for this epic.
- **B — The import command takes the payer and the sharers as arguments, applied to every row.**
  `import statement.csv --paid-by Ana --shared-by Ana,Ben,Cass`. Consequence: one command per
  group of rows that belong together; you split the statement by hand if a file mixes group and
  personal spending. Small addition to WI-0004; no new concepts.
- **C — The import is interactive: it shows each row and asks who shared in it.** Consequence:
  handles a mixed statement in one pass; slowest to use, hardest to verify automatically, and it
  makes WI-0004 substantially larger.
- **D — The import only proposes expenses, writing them to a file you edit and then load.**
  Consequence: full control and an audit trail; two steps instead of one, and it is close to
  the retyping you said you wanted to avoid.
- **Recommendation:** B, with a stated default of "shared by everyone registered" when
  `--shared-by` is omitted. It is the smallest thing that produces correct data, and it does not
  depend on being able to delete a wrongly-imported expense — which this epic does not offer.
