## Question

`WI-0001`'s close fails `claims-are-sourced` on `docs/product/vision.md:67`, a sentence inside a
`## Engagement state` section that no skill may write before the engagement ends, and `ADR-0004`'s
bounded override names `implement` and the `in-progress → verifying` transition only. **How does
`WI-0001`'s `in-review → done` close proceed?**

## Options considered

- **A — amend `ADR-0004` to extend the same bounded override to `review-close`'s
  `in-review → done` transition on `WI-0001`, under conditions of the same shape.**
  Consequence: the close is made with `--force`, and the item's history carries a second
  `[gates forced]` row. The conditions transfer almost unchanged — a full `run-gate --all
  --resolving 'WI-0001:in-review->done'` first with every verdict recorded, `claims-are-sourced`
  the only hard gate failing, exactly one error matching v2's four properties (code
  `claim.unsourced`, file `docs/product/vision.md`, section `## Engagement state`, sentence
  *"Three questions are open with them, all filed at intake"*), and the history reason naming the
  ADR. The cost `ADR-0004` already priced applies again and is larger here: `--force` is
  all-or-nothing, so the ten other verdicts on the most consequential transition this item makes
  would rest on the caller's word. It is mitigated the same way and no better.

- **B — extend the override to every skill and every transition on any item whose plan names a
  document with an unsourced absolute in its `## Engagement state` section.**
  Consequence: `WI-0002` and `BUG-0001` inherit it without anyone re-deciding, which is honest
  about the general shape — `ADR-0004`'s own `## Consequences` says *"Any item whose plan names a
  document with an unsourced absolute in its `## Engagement state` section meets this, whatever
  that item changed."* Risk: it is an override that grows to cover whatever happens to be
  failing, which is the thing `ADR-0004` `## Decision` point 3 names as *"the gate being switched
  off"*. Refusing to bound it per transition removes the only evidence that anyone looked.

- **C — clear the claim at its source by ending nothing and citing nothing: ask `intake` or
  `answer-questions` to repair the sentence after all.**
  Consequence: the gate goes green everywhere at once and stays green for `WI-0002`. Refused for
  the reason `ADR-0004` `## Options` B gives: the sentence is about the engagement, the engagement
  is not over, and the prohibition exists because a real run had two executions correct such
  sentences, both declared, both defensible, and both authorised by nothing.

- **D — block `WI-0001` and let the engagement's ending clear the claim first.**
  Consequence: deadlock, and a worse one than `ADR-0004` `## Options` D described. An engagement
  reaches rest only when every child is terminal; `WI-0001` cannot become terminal without this
  close; so the ending that would clear the claim can never arrive. `WI-0002` depends on
  `WI-0001` and would never start. Refused as unexecutable.

- **E — escalate to the stakeholder.** Refused, and for the same reason `ADR-0004` `## Options` E
  refused it: this is a collision between two of the toolkit's own rules, not the stakeholder's
  intent, not an irreversible product commitment, and not a contradiction with anything they
  decided. Spending their attention on it is the failure the routing test exists to prevent.

- **Recommendation: A.** It is the option that keeps the bound per transition, which is the
  property `ADR-0004` `## Decision` point 3 identifies as the whole point of the override; B
  abandons exactly that. The general statement B is reaching for is worth recording — it already
  is, in `ADR-0004` `## Consequences` — but recording a general shape and authorising a general
  override are different acts, and only the second is irreversible in the record. If the architect
  takes A, the amendment should also say plainly whether a future item meeting the same shape gets
  its own decision or inherits this one, so the next execution does not re-file this question.

## Answer

**Option A, with one correction to the reasoning behind it. `ADR-0004` is amended to v3 and
authorises `review-close` to make `WI-0001`'s `in-review → done` transition with `--force`, under
four conditions of the same shape as the first override's.** Route 3 of the preference order: no
document settled it, so the architect decided it and wrote it into the ADR that already owns this
subject. Not escalated — none of `spec/question.md` §4's four conditions applies, exactly as the
question's own option E argues: this is a collision between two of the toolkit's rules, reversible
at no cost, touching nothing the stakeholder decided.

The four conditions are in `ADR-0004` `## Decision` point 4. They are point 3's, re-aimed at the
other skill and the other transition: a full `run-gate --skill review-close --item WI-0001 --all
--resolving 'WI-0001:in-review->done'` first, with every verdict it produces recorded in the
journal entry; `claims-are-sourced` the only hard gate reported failing; exactly one error, and
that error matching v2's four properties — code `claim.unsourced`, file `docs/product/vision.md`,
section `## Engagement state`, sentence *"Three questions are open with them, all filed at
intake"*; and the history reason naming the ADR.

**Two bounded overrides, not one widened one.** Option B was refused on the ground the question
itself identified: point 3 of this ADR already says that an override which grows to cover whatever
happens to be failing *"is not an override, it is the gate being switched off"*. Each
authorisation names its skill and its transition, and that is what leaves the record able to show
that somebody looked twice rather than once.

**The correction, and it is the part worth reading.** The question inherited `ADR-0004`
`## Context`'s account of *why* the file is in scope — that `WI-0001`'s plan names
`docs/product/vision.md`, so `--plan-documents` pulls the whole file into the gate's window. That
is true of `implement`'s gate and false of this one. `review-close`'s gate runs
`lint-claims --context work-item --changed-since main`, with no `--plan-documents` at all
[src: toolkit: skills/review-close/references/contract.md Quality gates "`lint-claims --context {{item.type}} --changed-since {{trunk}}`"].
What puts `vision.md` in its window is that the file **differs from the trunk**, which the run
states in its own scope line: *"3 document(s) in 3 path(s) differ from main (6788e55) under
docs"*.

And `vision.md` differs from the trunk because **point 1 of this same ADR ordered the `:42`
repair**. The repair that cleared the first unsourced claim is what dragged the file into a later
gate's scope, where the second claim — the one point 2 deliberately leaves standing — was waiting.
This second failure is a consequence of `ADR-0004` itself, not an independent collision, and v3
says so in a new point 4a rather than leaving the next reader to derive it.

That also bounds it, which is the answer to the question's closing request. Once `WI-0001` merges,
`vision.md` matches the trunk, so a later item's branch that does not itself edit the file leaves
it outside the `--changed-since` window `review-close`'s gate uses. `implement`'s gate would still
reach it through `--plan-documents`, and then only for an item whose plan names the file. So **a
later item meeting this shape gets its own decision**, and is likely never to need one.
