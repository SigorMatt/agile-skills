## Answer

**Yes, the authorisation applies — and option C was right for a stronger reason than it gave.
`ADR-0004` is amended to v2; `implement` may force the transition on its next dispatch.**

Route: decided here, from the toolkit's own source. Not escalated: `spec/question.md` §4's four
conditions are the same four `ADR-0004` option E already walked through, and none of them has
become true. Nothing about droll changes, the stakeholder has never seen this ADR, and this
amendment does not supersede a decision they took.

**The line number is not a property of the claim, so condition 3 should never have been anchored
on it.** `lint-claims` rule 2 iterates `paragraphs(text)` and reports at `start` — the chunk's
first line — and `paragraphs` *"deliberately does **not** split on bullets"*
[src: toolkit: scripts/lib/record.py paragraphs() "deliberately does **not** split on bullets"]. The whole
`## Engagement state` bullet list is therefore one chunk, and what the gate prints is that list's
offset in the file. It moved from `:66` to `:67` because the execution that wrote `ADR-0004` v1
rephrased `## What it is for` from two lines to three in the same execution [src: commit b545273];
`## Engagement state` was at line 64 then and is at 65 now.

So this is not a case of a disqualifier being read away. It is a case of a bound written against a
coordinate that belongs to the file's layout rather than to the failure, by an execution that moved
the coordinate itself. The question was right to stop: `implement` had no way to tell the two apart
from the outside, and deciding it in its own favour is exactly what it is not for.

**What v2 does.** Condition 3 now admits an error by four properties — code `claim.unsourced`,
file `docs/product/vision.md`, section `## Engagement state`, and the sentence *"Three questions
are open with them, all filed at intake"*, reported as an absolute `'all'` about `'EP-001/Q-001'`.
That is a **narrower** bound than v1, not a wider one: v1 never said which sentence it admitted,
and any claim whose paragraph happened to start at line 66 would have satisfied it. The
disqualifier list keeps *"a second error appears"* and *"another gate fails"* and replaces *"the
error moves"* with *"a different claim fails"*. The decision, its scope and conditions 1, 2 and 4
are untouched.

**`implement` also did the other half correctly.** `document-writes-are-declared` failed because
`ADR-0004` was written on this branch by this skill and declared in neither section of the plan.
That was **this skill's** omission at 22:19:26Z — step 6a requires the row and it added one for the
file it edited while missing the file it created. `implement` appended the row rather than
escalating it, which is what its own escalation rule directs, and the gate now exits 0. Condition 2
holds.

**One thing for whoever reads this upstream.** The near-miss is worth more than the fix: an ADR
bound written in good faith was falsified by its own author's edit, in the same execution, and
nothing would have caught it except a downstream skill refusing to round a mismatch off. The
general lesson is that a bound handed to a later reader should be anchored on what the tool reports
about the *thing*, not on where the thing currently sits.
