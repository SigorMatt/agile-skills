## Context

Whether an expense has a **date** was parked at intake on the expectation that `EP-001/Q-002` —
the question about your bank's CSV — would settle it, since every bank row carries a date. That
question came back as "I'll send you a sample later", so it settled nothing.

Meanwhile `EP-001/Q-001` did settle that the CSV import ships as part of this epic and is not
optional. So the import is definitely coming, its rows definitely have dates, and this item is
being built now, before the sample arrives. If expenses have no date field, the import will
either throw the date away or force a change to the store after there is already data in it.

I am not willing to decide this by inference from a file I have not seen. It is a one-line
question with a permanent consequence for the data you accumulate.

## Question

Should a recorded expense carry a date — the day the money was spent — and if so, what happens
when you record an expense without giving one?

## Options considered

- **A — yes, with today's date as the default.** You may state a date; if you do not, the tool uses
  today. Consequence: the import keeps the bank's date for each row, the expense list can show
  when things happened, and nothing extra to type in the common case. Costs one more field to
  validate (a rejected malformed date is one more criterion).
- **B — yes, and always required.** Consequence: the record is never ambiguous about when. More
  typing on every single hand-entered expense, which is the thing you said you wanted less of.
- **C — no date at all; expenses are just an ordered list.** Consequence: the least to build now.
  The import must then discard the one piece of information the bank is most certain about, and if
  you later want to ask "what did we spend on the weekend away" the answer is not in the data.
  Adding a date afterwards means migrating a file that already has your real expenses in it.
- **Recommendation:** **A.** It costs almost nothing now, it is the only option that does not
  throw away information the import will hand us for free, and it keeps the door open for
  filtering by date later without a migration. I would not choose C: the import is confirmed, so
  "no dates" is a decision to discard data we are definitely about to receive.

## Answer

[human] Yeah, keep a date on it — default to today if I don't type one.

**Recorded by `answer-questions`:** this selects **option A** — a date on every expense,
defaulting to today when none is typed, and a malformed date refused.

One extension the answer does not state: the same rule now applies to **repayments** (`item.md`
AC11, AC12). The stakeholder was asked about expenses and answered about expenses. The architect
extended it rather than asking, because `ADR-0001` deliberately settled both record kinds before
any data exists in order to avoid retrofitting the second one, and adding a date to repayments
after the store holds real money is a migration. The costs are asymmetric, so this was not a coin
flip — but it is the architect's call, not the stakeholder's, and it is flagged in `item.md` and
in the refinement Q&A so `refine` can put it back to them.
