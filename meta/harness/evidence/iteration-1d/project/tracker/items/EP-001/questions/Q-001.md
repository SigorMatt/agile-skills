## Context

Intake split your idea into three work items under `EP-001`:

- **WI-0001 — record people and shared expenses that survive between runs.** Add people, record
  an expense (who paid, how much, what for, who shared it), list both, and have all of it still
  be there next time you run the tool.
- **WI-0002 — show who owes whom** across everything recorded.
- **WI-0003 — import expenses from your bank's CSV export** instead of typing them.

WI-0001 has to come first: the other two operate on the expenses it records, so both now declare
`depends-on: WI-0001`. That much is forced by the work itself and is not what this question is
about.

What is not forced is the order of the other two, and the pipeline will execute my guess as if it
were your intent. Your idea mentioned the CSV import with some feeling ("instead of me typing
them in"), which reads like it matters a lot — but "at any point show who owes whom" is the thing
the tool is *for*. I am not willing to infer your priority from tone.

Each item runs a full design → build → verify → review cycle, so the order is also the order you
see working software in.

## Question

After WI-0001 is delivered, which should be built next — WI-0002 (who owes whom) or WI-0003
(import from your bank CSV)? And is either of them something you would be willing to ship the
first version without?

## Options considered

- **A — WI-0002 next, then WI-0003.** Consequence: the tool answers "who owes whom" as early as
  possible and is genuinely useful after two items, with hand-entered expenses. You would be
  typing expenses in for a while, which is the thing you said you did not want to do.
- **B — WI-0003 next, then WI-0002.** Consequence: you can load your bank export early and get a
  realistic volume of data in, which also exercises the storage properly. But until WI-0002 lands
  the tool only lists expenses — it cannot yet answer the question it exists to answer.
- **C — treat one of them as optional for a first version.** Consequence: fewer round trips and a
  smaller first release. If it is WI-0003 that is dropped, the tool works but you type everything;
  if it is WI-0002, the tool is a list and not an answer, which does not look like what you asked
  for.
- **Recommendation:** A — WI-0002, then WI-0003. "Show who owes whom" is the outcome you named
  first and the one that makes the tool worth having; import is a way of getting data in faster,
  which is valuable but only once there is something to do with the data. I would not drop either
  from the epic.

## Answer

**The stakeholder answered, verbatim:**

> Do WI-0002 next, that's the point of the tool. And no — neither one is optional, I'm not
> shipping a version without the import. Build it last if that's easier, but it ships as part of
> this.

This is option **A** with an explicit refusal of option C. The delivery order is WI-0001 →
WI-0002 → WI-0003, and every one of the three ships in this epic.

Recorded by `answer-questions` as the propagation of that answer: the orchestrator has no
"delivery order" field. `pipeline.yaml`'s `selection_key` is priority rank, then `created`, then
id — so order is expressed through `priority` and `depends-on` or it is not expressed at all.
WI-0001 (`critical`) and WI-0002 (`high`, created before WI-0003) were already in the right
order. WI-0003 was lowered from `high` to `medium` to encode "built last", and `depends-on:
WI-0002` was added to it because its AC2 — imported expenses count towards the same who-owes-whom
report — cannot be verified before that report exists. The lowered priority is a scheduling
mechanism, not a judgement about importance, and both item and epic say so in those words so that
a later reader does not mistake it for the stakeholder deprioritising the import.

## Consequences

- `tracker/items/WI-0003/item.md` — `priority` lowered `high` → `medium`; `depends-on` extended
  with `WI-0002`; `## Notes` gained an **Ordering** paragraph stating that the import ships, is
  built last, and that `medium` encodes order rather than reduced importance
- `tracker/items/EP-001/item.md` — `## Notes` gained a decisions section recording the order
  WI-0001 → WI-0002 → WI-0003 and that neither WI-0002 nor WI-0003 is optional
