## Context

You asked for a tool that shows **who owes whom**. You did not say anything about what happens
after that — when Ben actually hands you the €40.

This is a scope question and it is worth asking now rather than discovering later, because it
changes WI-0001's storage (a repayment is a second kind of record, not an expense), it changes
WI-0002's report (debts should shrink as they are paid), and it may add a fourth work item to the
epic. Right now I have written it into the "out of scope" list of both items and marked it as
pending this question, so nothing downstream depends on my guess.

I am asking rather than deciding because "who owes whom" is only a durable answer if settling up
is part of the picture — and only you know whether your group settles up inside a tool or just
tells each other they did.

## Question

Should the tool be able to record that someone has repaid someone — so that the who-owes-whom
report shrinks as debts are settled — in this epic? Or is showing the debts enough, with settling
up handled outside the tool?

## Options considered

- **A — repayments are in scope for this epic.** Consequence: adds a fourth work item (record a
  repayment, and net it into the report). The tool stays truthful over months rather than only
  over one trip. Cost: one more full build-and-verify cycle before the epic closes, and it makes
  WI-0002's report definition slightly more involved.
- **B — repayments are out of scope for now; the epic delivers people, expenses, the report and
  the import.** Consequence: smaller epic, delivered sooner. The report is only correct until the
  first person pays someone back, after which you would either work around it (by recording the
  repayment as an expense in reverse, which is confusing) or start a fresh set of books each trip.
- **C — out of scope, but designed for.** Consequence: I record now that repayments are expected
  later, so the storage WI-0001 chooses does not make them painful to add, and a future item picks
  it up. Costs nothing in this epic beyond a written constraint.
- **Recommendation:** C. Your stated goal stops at "show who owes whom", and I should not widen
  it on my own; but a shared-expenses tool that can never register a repayment goes wrong the
  first time somebody pays up, and that is cheap to allow for now and expensive to retrofit. If
  you tell me your group settles up per trip and starts fresh, B is the honest answer and I will
  record that.

## Answer

**The stakeholder answered, verbatim:**

> Hadn't thought about it, but yes — let us log that someone paid, so the report doesn't go
> stale. Doesn't need to be fancy, whatever's simplest to build.

This is option **A**: repayments are in scope for this epic. The second sentence is a constraint
on how, and it was taken literally — plain who-paid-whom-how-much, no settlement plans, no
partial-payment schedules, no history of settlements beyond the list itself.

`Q-003`'s option A described the consequence as "a fourth work item". `answer-questions` did not
create one, for a reason worth stating plainly rather than hiding in a commit: **only `intake` may
create a work item.** `pipeline.yaml` and `spec/ids-and-statuses.md` §4 make `— → draft` legal
solely for the actor `intake`, and the other route into `intake` — a request under
`tracker/requests/` — is by `spec/request.md` §2 authored only by the human. An architect can
therefore widen an epic's scope but cannot open the item that widening implies.

What was done instead: because WI-0001 and WI-0002 are both still at `draft`, their acceptance
criteria are not yet frozen, and the work was added there — WI-0001 records and persists a
repayment (AC7, AC8), WI-0002 nets it into the report (AC5, AC6). `ADR-0001` records that
decision, the two options rejected (a repayment as a negative expense; deferring to an item
nobody could create), its reversibility, and the methodology gap above.

The one genuinely architectural point, decided here rather than left to `plan`: a repayment is
its **own kind of record**, not an expense with the signs flipped. Modelling it as a negative
expense would make `list expenses` show entries nobody spent and would put a sign convention into
every consumer of that list.
