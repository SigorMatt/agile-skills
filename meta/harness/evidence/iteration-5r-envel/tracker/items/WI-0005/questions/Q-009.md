All three were **correct when written**: `git show main:envel/cli.py` line 165 is `if

Non-blocking: `WI-0005` closes on it, and nothing waits.

## Question

Should the three stale `envel/cli.py:165` citations be repaired in place to `envel/cli.py:217`,
and if so, does `ADR-0011` take a `## Corrections` row and a version bump for the repair, or is a
citation-only fix below the threshold that `spec/doc-header.md` §4b sets for an accepted ADR?

## Options considered

- **A — Repair all three to `:217`, and give `ADR-0011` a `provenance` correction row, a
  change-log row and a version bump to 2.** Consequence: the ADR's own record says why the number
  moved and who moved it, which is what `## Corrections` is for; the two `plan.md` occurrences
  are tracker artifacts and need no ceremony. Costs one `answer-questions` execution. The
  assertion is unchanged, so nothing supersedes `ADR-0011` and no code has to change to satisfy
  the new text.
- **B — Repair all three to `:217` with no version bump**, treating a line number as below the
  bar `doc-header.md` §4b sets. Consequence: cheaper, and the next reader of `ADR-0011` sees a
  document whose text changed with nothing in its change log saying so — which is the habit the
  change-log rules exist to prevent.
- **C — Repair the two `plan.md` occurrences only, and change `ADR-0011` to cite the symbol
  rather than the line**, e.g. `[src: envel/cli.py]` naming `main`'s save branch in words.
  Consequence: the ADR stops being able to go stale this way at all, at the cost of a citation a
  reader has to search for rather than jump to. It also raises a question this item should not
  settle alone: whether `path:line` is the right citation form for a claim about a statement that
  will keep moving.
- **D — Leave all three.** Consequence: three citations that resolve and do not support, in a
  workspace whose own rule is that *"a citation that does not resolve is the appearance of
  evidence, which is worse than none"* — and one that resolves to the wrong line is the same
  failure with better camouflage. Nothing mechanical will ever surface it again.
- **Recommendation:** **A**, and it is the team's preference rather than a decided thing. It is
  the one option that leaves both the citation and the reason it changed in the record, and
  `ADR-0002` has taken exactly this shape three times already (v2, v3 and v4) for repairs of the
  same size. **C**'s second half is worth asking separately if the pattern recurs; this question
  should not carry two decisions.

## Answer

**Option A, and the spec decides it rather than a preference.** All three citations are repaired
in place to `envel/cli.py:217`, and `ADR-0011` takes a `provenance` row in an append-only
`## Corrections` section, a `## Change log` row, and a version bump to 2.

`spec/doc-header.md` §4b names exactly two legal repairs to an ADR at `status: accepted`, and this
is the first of them almost word for word
[src: toolkit: doc-header.md section 4b "add a citation to an existing sentence"], whose condition is that the sentence's assertion is unchanged, only its source is new, and the new citation resolves.
Both of its conditions hold here. The assertion is unchanged: `ADR-0011` `## Decision` 5 still says
that a refusal returns the caller's document untouched and that `envel/cli.py` writes nothing, and
`verify` measured the store file after every refusal on this item without one of them writing. And
the new citation resolves **and supports** — `envel/cli.py:217` is `if result.changed:`, which is
the statement the sentence is about.

The line §4b calls non-negotiable is the one that decides between a correction and a rewrite:
*"if a reader would have to change any code to satisfy the new text, it is a new decision"*. No
reader has to change anything. `ADR-0011` is not superseded, and the version bump is 1 → 2 rather
than a new ADR.

**B is refused** for the reason it names against itself: a document whose text changed with
nothing in its change log saying so is the habit the change-log rules exist to prevent, and §4b
requires *"a matching `## Change log` row and a `version` bump"* for every correction entry
without exception. **D is refused** because this workspace's own rule is that a citation which
does not resolve is the appearance of evidence, and one that resolves to the wrong line is that
failure with better camouflage — nothing mechanical would ever surface it again. **C** is not
taken **as a repair**, but its second half is a real question and it is recorded below rather than
answered here, because this question may carry only one decision.

### The invalidation set was deliberately not touched, and this is why

The skill's step 6a says a document changed on an item's branch belongs in that item's
invalidation set. It was **not** applied here, and the reason is measured rather than asserted: a
probe row for `ADR-0011` was added to `plan.md`'s set and
`lint-documents --rule invalidation-set-is-disposed --item WI-0005` was run, which failed with
*"docs/architecture/adr/ADR-0011-… is in WI-0005's invalidation set and has no row in
verify-report.md's `## Invalidation set`"*. The probe was reverted and the gate is green again at
*"29 invalidation entr(y/ies) against 29 row(s)"*.

That gate checks the plan's set against the **verification report's** disposition table, and the
verification report is written by `verify`, which has already run and cannot run again on a `done`
item. So after an item closes, step 6a cannot be executed: adding the row to one side of a
correspondence whose other side is frozen turns a cosmetic defect into a failing gate. Step 6a is
written for edits made mid-flight on a live branch, which is where every other execution of this
skill makes them.

Nothing is lost by the omission. `review-close` already recorded the same fact where a reader will
find it — `review.md`'s *"Did this change falsify a document the set does not name?"* names
`ADR-0011`, explains that the set structurally could not name it, and points at this question.
