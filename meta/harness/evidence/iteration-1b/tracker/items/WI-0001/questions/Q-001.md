## Context

"A command-line tool" is stated, but that phrase covers two quite different products, and every
acceptance criterion in this epic has to name an actual thing to run. `refine` cannot make a
criterion decidable — "someone with a terminal and no context reaches the same verdict" — without
knowing whether the thing to type is `expenses add-person Alice` or a prompt inside a running
session.

This is not a question I can settle from any document: there is no existing code, no existing
convention in this repository, and the choice is about how you actually want to use it. It also
propagates: it fixes the shape of the acceptance criteria on all three current work items, and it
is awkward to change later because every criterion and every test would be rewritten.

It is filed on WI-0001 rather than on the epic because it applies to all three items and WI-0001
is the first that needs it; the answer must be propagated to WI-0002 and WI-0003 as well.

## Question

Should the tool be invoked as one-shot commands that do a thing and exit — `expenses add-person
Alice`, `expenses who-owes-whom` — or as an interactive session that starts, prompts you for
commands until you quit, and saves as it goes?

## Options considered

- **A — One-shot subcommands.** Each invocation does one thing and exits. Consequence: scriptable,
  trivially testable (a criterion is literally a command and its expected output), composes with
  shell history and other tools, and matches how `git` or `pip` behave. Slightly more typing for
  a burst of entries, since each expense is a full command line.
- **B — Interactive session.** One invocation opens a prompt; you add several people and expenses
  in a row and quit. Consequence: pleasanter for entering a batch of expenses after a trip. Harder
  to write decidable acceptance criteria for — a criterion becomes a scripted transcript — and
  not usable from a shell script.
- **C — Both.** Subcommands, plus a session mode when invoked with no arguments. Consequence: the
  nicest to use, and roughly a third more work and two interfaces to keep consistent, for a first
  version.
- **Recommendation:** **A.** It is the smallest thing that satisfies "command-line tool", it makes
  every acceptance criterion in this epic a command someone can run and compare output against,
  and B can be added later on top of A without rewriting anything. I would only pick B if you know
  you will mostly be entering many expenses at once.

## Answer

The human declined to choose and delegated it:

> [human] Whatever you think is best, you know this better than I do.

That is a delegation, not a silence, so `answer-questions` decided it rather than escalating
again. Re-asking would spend their attention on a question they have already handed over, and
`spec/question.md` §4 does not admit "they gave a vague answer" as a condition for escalation.

**Decision: option A — one-shot subcommands**, recorded as `ADR-0001`. The ADR carries the
reasoning and the alternatives; the part the criteria rely on is:

1. Invoked as `python3 -m expenses <subcommand> [arguments]`. One subcommand per invocation; it
   does its work and exits. It never prompts and never reads standard input.
2. Exit status `0` when the subcommand did what was asked, non-zero when it did not.
3. A refusal prints a stated message on standard error and exits non-zero. It never prints a
   Python traceback — which is what "a stated error rather than a traceback" means in the four
   criteria across this epic that say it.
4. Everything a person is meant to read goes to standard output.

Option B was rejected because a criterion against a prompt is a scripted transcript, which is
harder to check by hand and needs a pseudo-terminal to test; option C because A can be extended
into it later without rewriting anything, so paying for two interfaces now buys nothing that
cannot be bought later.

`ADR-0001` deliberately does **not** fix the names of the subcommands or their arguments. Those
belong to the item that introduces each one and are pinned by `refine`, against the ADR. This
answer therefore unblocks refinement; it does not do refinement's job.
