## Context

AC1 and AC4 both talk about "a person" and "a name" without saying what a name may be, so neither
is decidable as written: a verifier cannot tell whether `python3 -m expenses add-person "Anna Karin"`
is supposed to work.

One half of this is cheap now and expensive later. WI-0002 has to let you name several sharers on
one command line, and the usual way to do that is a separated list — `--shared-by alice,bob,carol`.
Whatever character does the separating cannot then appear inside a name. `ADR-0002` also admits an
explicit amount per sharer, which needs a second reserved character, most naturally `=`
(`--shared-by alice=5,bob,carol`). Reserving both while the group is empty costs nothing.
Discovering the clash after somebody called `Anna,Karin` has been recorded means renaming a person,
which this epic has no command for.

The other half is a fact about your group that no document records: whether the people in it go by
a single first name, or whether you need full names to tell two of them apart.

I have decided one part of this myself rather than asking, because no reasonable answer differs: a
name that is empty or only whitespace is refused, with a message on standard error and a non-zero
exit status, and nothing is added.

## Question

May a person's name contain spaces — and is it acceptable that the comma and the equals sign are
reserved, so that no name may contain either?

## Options considered

- **A — Single word, no spaces; comma and `=` reserved.** Names look like `alice`, `bob`,
  `anna-karin`. A name containing a space is refused. Consequence: nothing ever needs quoting at
  the shell, and every command line stays short. If two people in the group share a first name you
  need a convention — `sam-o`, `sam-w` — which the tool will not help with.
- **B — Any text, with the comma and `=` reserved.** `Anna Karin` and `Sam Okafor` are fine, quoted
  at the shell where the shell needs it: `add-person "Sam Okafor"`. A name containing `,` or `=` is
  refused with a message saying so. Consequence: handles two Sams without a nickname convention,
  at the cost of quoting on entry and slightly longer lines when several sharers are named.
- **C — Any text at all, nothing reserved.** WI-0002 names sharers with a repeated flag —
  `--shared-by alice --shared-by bob` — so no character has to be reserved. Consequence: the most
  permissive rule and the only one that never refuses a real person's name; the price is a
  noticeably longer command line every time an expense is shared by more than two people, which is
  most of them.
- **Recommendation: B.** Groups do collide on first names, and being able to write `Sam Okafor`
  solves it without inventing a nickname scheme; reserving `,` and `=` is free, because nobody's
  name contains them. Choose A if everyone in your group goes by one first name and you would
  rather never quote anything. Choose C only if you would rather type `--shared-by` once per person
  than accept any restriction on names at all.

## Answer

The human chose **option B**, in their own words:

> [human] Go with B — allow spaces. We've actually got two people who go by the same first name,
> so full names matter.

A name is any text, after leading and trailing whitespace is stripped, and may contain spaces:
`Sam Okafor` is a name, quoted at the shell where the shell needs it. A name is refused — stated
message on standard error, non-zero exit, nothing recorded — when it is empty or only whitespace,
or when it contains a comma or an equals sign. Those two characters stay reserved, which is the
half of the question the human was asked to accept and did: a sharer list is written
`alice,bob,carol` and an explicit amount `bob=5` (`ADR-0002`), so neither may appear inside a name.

The second sentence of their answer is the load-bearing one and is now recorded in
`docs/product/prd.md`: the group contains two people who share a first name. That is the fact
option A would have failed on, and it is worth keeping because it also explains why the reserved
characters are affordable — a nickname convention is not available as a fallback here.

Recorded as `ADR-0005`, together with `Q-002`, because what a name may be and when two names are
the same person are one rule; separating them would let a later reader change one without seeing
what it does to the other.
