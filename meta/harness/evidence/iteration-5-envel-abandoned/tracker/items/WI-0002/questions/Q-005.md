## Question

Should `answer-questions` repair the four citations in place — `ADR-0005` and `ADR-0007` through
append-only `## Corrections` entries of kind `erratum`, and `docs/process/ways-of-working.md`
through an ordinary update with a version bump — and add `ADR-0005` and `ADR-0007` to WI-0002's
invalidation set so D7's closing question is answered on the record; or is a different disposition
right?

## Options considered

- **A — `answer-questions` repairs all four, and the invalidation set gains the two ADRs.**
  `ADR-0005` and `ADR-0007` each take a `## Corrections` entry of kind `erratum` moving the
  citation to the line that now holds the referent (`envel/cli.py:100`, `envel/store.py:79`);
  `ways-of-working.md` goes to version 4 with both citations corrected (`envel/store.py:79` and
  `:28`) and a change-log row; the plan's invalidation set gains a row per ADR and the
  `ways-of-working.md` row's false `verified-still-true` sentence is replaced by what was actually
  read. WI-0002 then resumes at `verifying`, `verify` re-checks the four citations and the item
  goes to `in-review`. Consequence: the assertion in every one of the four sentences is unchanged
  — `spec/doc-header.md` §4b's `erratum` kind is for exactly this, a pointer that no longer points
  — so nothing about what the code must do is reopened, and no criterion moves. Cost is one
  `answer-questions` round and one repeated `verify`. It is the only option under which D7 is
  answered truthfully **and** the false `verified-still-true` claim is corrected by the actor the
  spec permits.

- **B — send WI-0002 back to `in-progress` and let `implement` repair them.** Consequence: the
  ordinary route for a document this item's change falsified, and it is **blocked by
  `spec/doc-header.md` §5** — `implement` is not an updater of `ways-of-working.md` and may not
  write an ADR's document half. It would either violate §5 or come straight back as another
  question, and the second is the likely one: `implement` already filed `Q-004` rather than edit
  `ADR-0006` and `ways-of-working.md`, on this same item.

- **C — accept all four as gaps in `review.md` and close the item.** Consequence: cheapest now
  and it puts four sentences into the record that point a reader at the wrong code, in two ADRs
  that are the standard later items are judged against. `ADR-0005` is `BUG-0001`'s own decision
  document and `BUG-0001` is the next item to open `envel/cli.py`; a maintainer following
  `envel/cli.py:82` finds `return OK` and no reason to doubt it. `spec/doc-header.md` also says an
  unresolvable citation *"is worse than none: it is the appearance of a source"*, and a citation
  that resolves to the wrong line is worse again, because nothing flags it. `D11` would also need
  each accepted gap to carry a dispatchable owner, which is option A wearing a different hat.

- **D — repair only the two ADRs, and leave `ways-of-working.md` to `review-close`.**
  Consequence: §5 does name `review-close` as an updater of `ways-of-working.md`, so this is
  legal, and it defers two of the four to a skill that will run on this item anyway. But it splits
  one finding across two rounds, and it leaves the false `verified-still-true` claim standing
  through `verify`'s own re-run — the claim is in the *plan's* invalidation set, which
  `review-close` does not own. Half the finding would be fixed and the half about the record's
  truthfulness would not.

- **E — treat citation drift as out of scope for an item and file it as a toolkit finding only.**
  Consequence: the honest observation underneath it is real and belongs in the retrospective —
  `lint-claims` bounds a `path:line` citation by the file's length and never checks what the line
  holds, so this class of drift is invisible to every gate and was caught here only by a
  by-hand audit of all 25 `path:line` citations in `docs/`. But an observation about the toolkit
  does not make this item's record true, and D7 and D12 are this item's.

- **Recommendation:** **A**, and it is the narrow reading rather than the generous one. What is
  wrong is four pointers, not four claims, which is precisely the `erratum` case §4b provides for,
  so the repair changes no assertion and reopens no decision. It is also the only option that
  reaches both halves of the finding — the two undeclared ADRs *and* the false
  `verified-still-true` sentence — and it puts each edit with the actor `spec/doc-header.md` §5
  names. Worth adding to the retrospective either way, per option E: this drift passed
  `claims-are-sourced`, passed `implement`'s own document audit, and passed a re-disposition, and
  the only thing that found it was reading all 25 citations against the branch head by hand.
