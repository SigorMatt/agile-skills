## Question

Do `ADR-0006`'s option-B label and `ways-of-working.md`'s *"If no dispatchable item opens that
code"* each owe a `[src: ...]` citation under `spec/doc-header.md` §4a — and if not, is
`claims-are-sourced`' `--plan-documents` window the thing to change, so that a document an item
disposes `verified-still-true` is read for what that item wrote rather than for everything in it?

## Options considered

- **A — the sentences owe citations; `answer-questions` adds them.** `spec/doc-header.md` §5 makes
  `docs/process/ways-of-working.md` `answer-questions`' and `review-close`'s to update, and an
  ADR's document half takes an append-only `## Corrections` entry (§4b). Cost: two small edits by
  the skill that owns both files, and one round of the loop. Consequence: the gate goes quiet for
  WI-0002 and for WI-0003 to WI-0005, which will name the same documents for the same reasons.
  Risk: it treats a symptom. Neither sentence is *"an absolute claim about named code"*, which is
  what §4a's rule says the obligation attaches to — option B's label describes an option that was
  weighed, and the `ways-of-working` sentence states a condition of a convention. Adding a
  citation to a sentence that does not owe one teaches the next reader that the gate is the rule.
- **B — the window is the thing that is wrong.** `--plan-documents` exists so that a document an
  item *delivers* is examined even when the branch's own diff would not reach it (F-076). Applying
  it to every document in the invalidation set charges an item for prose it correctly disposed as
  untouched. Cost: a change to `scripts/lint-claims`' scope, outside this workspace. Consequence:
  an item is answerable for what it wrote, which is the obligation `spec/dor-dod.md` D12 states.
  Risk: narrowing a claims gate is the direction that lets a real claim through, and the deliverable
  case F-076 was written for must keep its full window.
- **C — record it as a limitation and force on, item by item, as this one did.** Cost: none now; every
  later item meeting it re-walks the four conditions. Consequence: the convention already carries
  the engagement-state instance this way and says plainly what that costs. Risk: two findings of
  different shapes get the same treatment, and the second one — which has an owner who *can* fix it
  — quietly stops being fixed.

**Recommendation: A for `ways-of-working.md` and B for the general case, with `ADR-0006` left
alone.** The `ways-of-working` sentence is one edit by a skill that owns the file and is cheap
whatever the answer to the wider question is. `ADR-0006`'s is inside `## Options considered`,
which is a record of what was weighed rather than a statement about the product, and editing it to
satisfy a gate would change the record of a decision to make a linter quiet.

## Answer

**Yes, both owed a citation, and both now have one — option A, made by the two routes the spec
provides.** The second half of the question is a real finding and is recorded below, but it is not
this workspace's to fix and nothing waits on it.

**Why they owed one, from the record.** `spec/doc-header.md` §4a states the obligation exactly:
*"A paragraph that makes an **absolute claim** — `no`, `none`, `never`, `always`, `only`, `every`,
`all`, `nothing`, `cannot`, `exactly`, `impossible`, `guaranteed` — about something named as code
(a backticked identifier, call, constant, or a path) MUST carry at least one citation."* The
question's own framing — that an option label and a conditional are not claims about named code —
is right about the *emphasis* of each sentence and wrong about the rule, which attaches to the
**paragraph**, not to the clause the gate happens to quote:

- `ADR-0006`'s `## Options considered` is one unbroken list block, so the paragraph runs from
  option A to option C. It contains `always` and `every` (option B), and the backticked constants
  `340`, `12.5`, `12.50` and `340.00`. Under §4a as written, that paragraph owes a citation. It is
  also now trivially citable, which it was not when the ADR was written: option B is the option
  that was taken, and one function implements it.
- `docs/process/ways-of-working.md`'s *"What it is not"* paragraph contains `no` — *"If no
  dispatchable item opens that code"* — and the backticked path `review.md`. The sentence restates
  a rule that lives elsewhere and cites nothing, which is precisely the shape §4a was written
  against: the paragraph two above it already cites
  `.claude/skills/answer-questions/SKILL.md` for a weaker statement.

**Why the recommendation to leave `ADR-0006` alone was refused.** The question recommended not
editing `## Options considered`, on the ground that it records what was weighed rather than what
is true. That reasoning is sound about **supersession** — §4 protects what was decided, and
nothing here changes it — but `spec/doc-header.md` §4b exists for exactly this gap and was written
from a run in which a reviewer read three true-but-unsourced claims in a standing ADR, could not
add citations, and left a permanent known lint error behind (F-067). §4b's `provenance` kind
permits adding a citation to an existing sentence when *"the sentence's assertion is **unchanged**
— only its `[src: ...]` is new — and the citation resolves"*, through an append-only
`## Corrections` entry with a version bump and a change-log row. That is what was done. No reader
would have to change any code to satisfy the new text, which §4b names as the boundary between a
correction and a rewrite.

**The `--plan-documents` finding stands, and it is the toolkit's rather than this item's.** The
question is right that `claims-are-sourced` charged `WI-0002` for prose it correctly disposed as
untouched: `--plan-documents WI-0002` widened the window from *what this branch changed under
`docs/`* to *every claim in every document the plan named*, and WI-0002's plan named five
documents because its invalidation set is honest about what it reopened. An item that reopens more
documents is therefore audited harder than one that reopens fewer, which inverts the incentive the
invalidation set exists to create. `scripts/lint-claims` is toolkit machinery and no skill in this
pipeline may edit it, so this is recorded as a finding for the retrospective and nothing more. The
two edits above are worth making on their own merits, whatever is decided about the window.

**The third error is unchanged and is not this question's.** `docs/product/vision.md:85` is inside
that document's `## Engagement state` section. `spec/doc-header.md` §4a gives every such sentence
to `review-close` at the ending, `spec/dor-dod.md` D12 puts them outside the audit obligation
altogether, and `WI-0001/Q-003` has already diagnosed this exact instance. This execution did not
read it, tidy it or repair it. After the two edits above, `lint-claims --changed-since main
--plan-documents WI-0002` reports **1 error**, which is that sentence — so `implement`'s next
execution meets the forced-gate convention's second condition cleanly, on one finding with no
available actor, rather than on three of two different kinds.
