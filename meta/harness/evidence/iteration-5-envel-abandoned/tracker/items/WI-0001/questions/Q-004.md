## Context

WI-0001's review. All eleven acceptance criteria pass, the change merges cleanly, and this item
is closing. Two gaps in the **test suite** — not in the behaviour — turned up while reading the
diff and `verify`'s report, and the review is accepting both rather than sending a green item
back. This question is what makes that acceptance dispatchable: an accepted gap that names an
owner and lives only in `review.md` is inert, because the orchestrator dispatches on open
questions and on item status and on nothing else (`spec/dor-dod.md`, "An accepted gap is
dispatchable or it is nothing").

Both gaps are the same shape — a decision somebody recorded that no test exercises — and both are
cheap to close. Neither is a defect: the behaviour was demonstrated by hand during review and is
correct.

**Gap 1 — two of the three branches of `store_path` have no test at all.** `ADR-0003` fixes the
resolution order as `$ENVEL_FILE`, then `$XDG_DATA_HOME/envel/store.json`, then
`~/.local/share/envel/store.json`, and calls `ENVEL_FILE` *"a published interface"* whose renaming
*"breaks anyone's habits and every test at once"*. Every one of the 24 tests reaches the store
through the `ENVEL_FILE` branch, because that is what makes the criteria observable at all
(`tests/test_cli.py:27`). The XDG branch and the home branch are read by nothing. The cost of
covering them is near zero and it is already designed for: `store_path(environ=None)` takes an
environment mapping precisely so a caller can pass a fake one (`envel/store.py:27`), so a unit
test needs no real home directory and no temporary `HOME`.

**Gap 2 — nothing end-to-end creates an envelope from a name with surrounding whitespace.**
`verify`'s mutation M3 exposed it: removing the `strip` from `display` broke only the two unit
tests in `tests/test_envelopes.py` and no case in `tests/test_cli.py`. AC7 uses `Groceries`, which
has no surrounding space; AC11 passes `"  groceries  "` as a **duplicate**, so `add` raises before
`display` is reached. The behaviour itself is right — this review ran `envel new "  eating out  "`
on a fresh store and got `eating out` in the listing and `"name": "eating out"` in the store file
— and `test_add_stores_the_trimmed_name_as_typed` is sensitive to it at the unit level. What is
missing is one end-to-end case, which is the half of AC11 a person at a terminal would actually
type.

Neither gap can be closed by this skill. `review-close` writes no tests, and its only creation
authority is a `bug` at `ready` (`pipeline.yaml`), which neither of these is — nothing is broken.

## Question

Do these two test-coverage gaps become work — a new item, which `answer-questions` may create
from an answer that implies work no item records — or are they accepted as recorded limitations
of WI-0001's suite, to be picked up by whichever later item next touches the code they cover?

## Options considered

- **A — File one small work item under EP-001 for both.** It would carry two criteria: a unit
  test that pins `store_path`'s XDG and home branches by passing a fake `environ`, and an
  end-to-end case that creates an envelope from a name with surrounding whitespace and asserts the
  stored and listed form. Consequence: both gaps close, on their own item, with their own
  verification. Cost: a whole pipeline round — refine, plan, implement, verify, review — for what
  is perhaps fifteen lines of test. It also queues behind nothing, so it would be dispatched
  ahead of WI-0002 if it were `critical` and after it otherwise.
- **B — Fold them into WI-0002's plan as a precondition.** WI-0002 records income and spending
  against envelopes by name, so it touches both `store_path` and the trimming rule directly, and
  its plan can carry the two cases as steps. Consequence: no extra item, and the tests land beside
  code that exercises them for real. Cost: WI-0002's diff then contains hunks that trace to
  WI-0001's criteria rather than its own, which is exactly what `no-unplanned-scope` asks about —
  unless its plan names them, which is why this has to be decided now rather than noticed then.
- **C — Accept both as limitations and record nothing further.** Consequence: honest, and cheap,
  and the smaller of the two risks is real: a regression in the XDG branch would send a person's
  store to the wrong path and no test would say so. This is the option the accepted-gap rule
  exists to make somebody choose deliberately rather than by default.
- **Recommendation:** **B**, with a bias to A if WI-0002's refinement turns out to be large. Gap 2
  is genuinely WI-0002's neighbourhood — it will be creating envelopes by name constantly — and
  gap 1 is one unit test that belongs wherever `store_path` is next opened. A separate item for
  fifteen lines of test spends a full round on process rather than on the stakeholder's tool,
  which is the trade `plan`'s own preference order is built to avoid. What must not happen is C by
  omission: if C is chosen, it should be chosen, and this question is where that is recorded.

## Answer

**B, with the host item corrected: the two gaps are carried by `BUG-0001`, not by `WI-0002`.**

Option B is right about the shape — a gap of this size belongs beside the code it covers, on an
item that is already going to open that code, rather than on a round of its own. It named the
wrong item, and the record says which one is right.

`WI-0002` opens neither piece of code. It records income and spending against envelopes that
already exist, and its seven criteria never create one (`tracker/items/WI-0002/item.md` AC1–AC7);
it reaches the store through `load` and `save` and has no reason to touch `store_path`
[src: envel/store.py:27]. Folding the gaps there would put them in a plan whose steps have
nothing to do with them, which is precisely the cost this question's option B recorded and then
accepted.

`BUG-0001` opens both, and it is at `ready` with no plan written, so this is decided in the same
window option B needed:

- it is `found-in: WI-0001` and its AC4 re-verifies all eleven of WI-0001's criteria by name, so
  WI-0001's suite is already its subject (`tracker/items/BUG-0001/item.md`);
- its AC2 requires a regression test that runs `envel new` end-to-end with an awkward name under a
  child environment of the test's own choosing — which is the same test, in the same file, in the
  same shape as gap 2's missing case (`tracker/items/BUG-0001/item.md` AC2);
- the defect it fixes is inside `envel/store.py`'s `save` [src: envel/store.py:58], the module
  `store_path` lives in [src: envel/store.py:27], and there is no `tests/test_store.py` today —
  whoever plans the fix is the first person with a reason to create one, which is where gap 1's
  unit test belongs.

So the disposition is: **`BUG-0001`'s plan carries both cases as steps**, and its `## Notes` now
say so, with this question as the reason. Concretely — a unit test that pins `store_path`'s XDG
and home branches by passing a fake `environ`, and an end-to-end case that creates an envelope
from a name with surrounding whitespace and asserts both the listed form and the stored form.

Two boundaries on that, because the difference between this and scope-creep is thin:

- **They are plan steps, not acceptance criteria.** `BUG-0001`'s criteria stay about the defect.
  Widening an existing item's criteria to swallow work found elsewhere hides the change from the
  board, and this skill is forbidden to do it (`SKILL.md` step 3b).
- **If `BUG-0001`'s plan declines to carry them, it says so and re-files.** A plan may decide the
  cases do not belong in its steps; what it may not do is drop them silently, because then the
  disposition recorded here would be C by omission — the outcome this question was filed to
  prevent.

Not A, because a full round — refine, plan, implement, verify, review — for roughly fifteen lines
of test spends the stakeholder's pipeline on process while four of the six things their tool is
for are still unbuilt [src: docs/product/vision.md]. Not C, because gap 1's risk is real and is
about to become live: a regression in `store_path` sends a person's store to the wrong path
silently, and `BUG-0001` is the item that opens that file.

**This still satisfies the rule the question was filed under.** An accepted gap must be
dispatchable, and the orchestrator dispatches on item status and open questions and nothing else.
The gaps are now attached to `BUG-0001`, which is at `ready` and is dispatched by `next` as an
ordinary candidate — not to a `review.md` table and not to this file.

**Where the decision is recorded.** In `docs/process/ways-of-working.md`, as a convention, rather
than as an ADR. That document exists for exactly this class of decision and was created by this
skill for `WI-0001/Q-003`; an ADR would additionally enter every later plan's `binding-adrs`
question and every later `verify`'s per-ADR conformance verdict, which is machinery for decisions
about how the product is built, not about where a test lands.
