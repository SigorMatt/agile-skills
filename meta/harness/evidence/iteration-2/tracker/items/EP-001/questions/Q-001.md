## Context

This is question 1 of 4 on EP-001, all raised during intake, all part of the same ask. You stated
the idea — a tool that organises a messy folder by type and age, with a dry run and configurable
rules — and intake turned it into an epic (EP-001) and three work items (WI-0001, WI-0002,
WI-0003). Normally intake would have put these four questions to you in conversation; you are not
in this session, so they are on paper instead. Nothing will be designed or built until they are
answered.

This repository is empty apart from the tracker: there is no source code, no test command, no
build file, nothing that says what this is written in. `tracker/project.yaml` has `commands.test`,
`commands.lint` and `commands.build` all set to `null`, which is honest but means the pipeline
currently has no way to run a test.

This is not a question intake can answer from the record, because the record is silent and any
choice is a coin flip with material consequences — it fixes how the tool is invoked, what "run it"
means in every acceptance criterion, and what a reviewer can check.

## Question

What should this tool be built with, and how will you run it? Specifically: which language and
runtime, and is it a command you type in a terminal, or something else?

## Options considered

- **A — Python 3, single command-line tool, standard library only.** Consequence: runs anywhere
  Python 3 is already installed, which on a Linux or macOS machine is everywhere; no install step,
  no dependency management; tests via `python3 -m pytest` or `unittest`. Cost: startup is slower
  than a compiled tool, which does not matter for this workload.
- **B — A shell script (bash).** Consequence: nothing to install at all. Cost: date arithmetic and
  configurable rules are painful in shell, and the preview/apply split is easy to get subtly wrong;
  this is the option most likely to produce a tool nobody trusts.
- **C — A compiled language (Go, Rust) producing a single binary.** Consequence: fast, one file to
  copy to another machine. Cost: needs a toolchain installed to build, and is more work for a tool
  of this size.
- **D — Something already in use where you work**, which intake cannot see from here.
- **Recommendation:** A. The tool is I/O-bound and small; the awkward parts are date handling and
  reading a rule file, and Python's standard library covers both without adding a dependency. Say
  so if you have a target environment we cannot see, and we will take D instead.

## Answer

[human] Whatever's easiest for you to build and test — you know this better than me. Python's
fine if that's your call. Yeah, a terminal command is fine, nothing fancier needed.

**Decided by the architect under that delegation** (`answer-questions`, 2026-08-27), because the
reply hands the choice back rather than making it: **Python 3.9 or newer, one command-line entry
point, standard library only, tested with `unittest`.** The full reasoning, the three alternatives
that were rejected, and what would have to change to reverse it are in ADR-0001. The two things
the stakeholder did settle themselves — that Python is acceptable, and that a terminal command is
the right shape — are recorded there as the basis for the rest.

Option **A** as filed, narrowed on two points the options did not cover: no third-party packages
at all (so `unittest` rather than `pytest`, and no YAML for WI-0003's rule file), and an
interpreter floor of 3.9.
