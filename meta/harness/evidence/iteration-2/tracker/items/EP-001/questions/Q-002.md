## Context

This is question 2 of 4 on EP-001, part of the same intake ask as Q-001; see that file for the
frame.

Intake asks "what would make this a failure even if it worked?" For a tool that moves files in
bulk, there is one obvious answer and you did not state it, so it needs to be your decision rather
than ours: what happens when the tool wants to move `report.pdf` into `documents/` and there is
already a `report.pdf` in `documents/`. In a genuinely messy folder this will happen, probably on
the first run.

This is not reversible in the sense that matters: if the tool overwrites, the losing file is gone,
and this epic has already ruled undo out of scope. It also shapes the epic's success measures — one
of them currently says "no file present before the run is absent after it", which is a promise that
only holds if you pick a non-destructive answer.

## Question

When the tool wants to move a file to a destination where a file of that name already exists, what
should it do?

## Options considered

- **A — Never overwrite; rename the incoming file** (e.g. `report (2).pdf`) and report the rename
  in both the preview and the real run. Consequence: nothing is ever lost, and the preview tells
  you a collision is coming before it happens. Cost: you can end up with near-duplicates you then
  have to sort out by hand.
- **B — Never overwrite; skip the file**, leave it where it is, and report it as skipped.
  Consequence: nothing is lost and nothing is silently duplicated; the folder is left partly
  untidied and you deal with the leftovers. Cost: repeated runs never converge on a tidy folder.
- **C — Overwrite the existing file.** Consequence: the folder always ends up in the state the
  rules describe. Cost: data loss, silently, at scale — this is the option that makes the tool
  dangerous, and it contradicts the epic's current success measures.
- **D — Stop the whole run on the first collision** and change nothing. Consequence: strongest
  possible safety guarantee. Cost: one collision blocks tidying hundreds of files.
- **Recommendation:** A. It is the only option that both leaves the folder tidy and loses nothing,
  and the preview makes the renames visible before they happen, which is what the preview is for.
  B is a reasonable second if you would rather never see a generated filename.

## Answer

[human] Never overwrite, full stop — that's the one thing I actually care about here. If there's
a clash just rename the incoming one, report.pdf (2) or whatever you want to call it. I don't
want to ask about this again.

Recorded as given: **option B's guarantee with option A's mechanism — never overwrite, rename the
incoming file, report the rename.** The stakeholder's own words settle it, including the shape of
the suffix ("report.pdf (2) or whatever you want to call it"), which leaves the exact form to the
implementer.

This is now an **invariant of the tool, not a rule the user supplies.** "I don't want to ask about
this again" is a decision about the product, so making the behaviour configurable in WI-0003 would
re-open a question the stakeholder closed; it is on WI-0003's out-of-scope list for that reason.
