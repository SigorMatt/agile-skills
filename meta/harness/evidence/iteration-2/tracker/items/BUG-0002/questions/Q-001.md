## Context

Reviewing BUG-0002 at `in-review`, before merging `wi/BUG-0002` into `main`. This is question
1 of 2 from that review; both are about sentences in `docs/` that the merge makes untrue, and
`review-close` may not edit `docs/architecture/` itself (`spec/doc-header.md` §5). The code and
the tests are sound — the Definition of Done fails on D12 alone, and only on documents.

`docs/architecture/overview.md` v4 was written by `plan` for this item, before the code existed.
Its third paragraph about the move path reads:

> Read that as the *primary* path rather than the only one. Where a filesystem refuses hard links
> — some network mounts, exFAT and FAT32 — `apply.py` falls back to `_move_without_a_link`, which
> checks `os.path.lexists(destination)` and then calls `shutil.move`; the promise still holds
> there, but it holds by a check-then-act with a race window rather than by the kernel
> [src: ADR-0003; src: tidy/apply.py]. **That path is unreachable from the test suite, which is
> what let a defect survive in it: a run using the fallback exits 1 even when every file moved**
> [src: BUG-0002].

Both halves of the bolded sentence are false the moment this branch merges, checked by opening
what it points at rather than by remembering:

- **"unreachable from the test suite"** — `tests/test_apply.py:120` and `:144` and
  `tests/test_cli.py:413` and `:447` each enter it with
  `mock.patch("tidy.apply.os.link", side_effect=OSError(18, ...))`. Four tests reach it, and
  `python3 -m unittest tests.test_apply.HardLinkFallbackTests tests.test_cli.FallbackExitStatusTests -v`
  shows all four `ok` on the merge result, none skipped.
- **"a run using the fallback exits 1 even when every file moved"** — `tidy/cli.py` now ends
  `return 1 if any(outcome.kind == "failed" for outcome in outcomes) else 0`, and the item's own
  reproduction prints `EXIT: 0`.

The very next paragraph of the same document says BUG-0002 brings "the first regression test that
reaches the fallback branch at all", so after the merge the section contradicts itself as well as
the code. `scripts/lint-claims` passes on it — the citation resolves — which is precisely the case
D12 exists to catch and a program cannot.

## Question

How should `docs/architecture/overview.md` be brought into line with the merged code: by rewriting
the stale sentence to say what is now true, by re-framing the paragraph as explicit history, or by
some other edit you prefer? The document is yours to update (`spec/doc-header.md` §5 names `plan`
and `answer-questions`), and BUG-0002 cannot close until it is true.

## Options considered

- **A — rewrite the sentence in place, in the present tense, and bump to v5.** Replace it with
  what is now the case: the fallback is reached by the test suite (naming the two test classes),
  and a run that uses it exits 0, with the defect that BUG-0002 fixed cited as history. Cost: one
  paragraph and a change-log row. Consequence: the section reads as the current state, which is
  what an architecture overview is for, and the following paragraph stops contradicting it. The
  sentence about the race window and the check-then-act stays — that part is still true.
- **B — mark the sentence as history explicitly.** Keep it, prefixed with "Before BUG-0002 …",
  and leave the rest. Cost: a few words and a change-log row. Consequence: the narrative order
  (problem, then decision) survives, but the overview accumulates per-item history that
  `tracker/` already holds, and the next reader has to date every sentence they read.
- **C — leave it, on the grounds that a document records what was believed when written.** Cost:
  none now. Consequence: `spec/doc-header.md` §4 says that of **ADRs**, deliberately; the overview
  carries `status: current` and is the document `plan` reads first when designing the next change.
  BUG-0003 and BUG-0004 are both open in `apply`/`cli` territory, so the next `plan` execution
  would read that the fallback is untested when four tests now cover it. This also leaves D12
  failing, so BUG-0002 could not close.
- **Recommendation: A.** It is the only option that leaves the document true without turning it
  into a second changelog, and the material for it is already in the paragraph that follows.

## Answer

**Option A: the sentence is rewritten in place, in the present tense, and the document goes to
v5.** Answered from the record rather than decided freshly — three documents settle it between
them, and none of them is silent:

- `spec/doc-header.md` §2 gives `overview.md` `status: current`, and §1 calls `docs/` "a record of
  *conclusions*" that "a skill that needs a decision looks here first". A `current` document that
  describes the code as it was before the branch in front of it is not a conclusion; it is a
  stale premise the next `plan` execution would build on. That rules out option C on the document's
  own terms, without needing D12 at all.
- `spec/doc-header.md` §4's "an ADR records what was believed at its date" — the basis option C
  leans on — is written about **ADRs**, deliberately and by contrast. It does not extend to the
  overview, which has no supersession mechanism and one current version.
- `spec/doc-header.md` §3 supplies the audit trail that makes an in-place rewrite safe rather than
  quiet: every content change bumps the version and adds a change-log row saying what changed.
  Option B's worry — that history is lost — is answered by the change log, which is where per-item
  history belongs, alongside `tracker/`. The overview does not need to carry it in prose.

So the paragraph now says what is true after the merge, and keeps the defect as history rather
than as the present tense: no test reached the fallback until BUG-0002, which is how the defect
survived; it is reached now, by `tests/test_apply.py` and `tests/test_cli.py`, each patching
`tidy.apply.os.link`. The sentence about the check-then-act race window is untouched — it was and
remains true.

One thing beyond what was asked, and worth naming: the **next** paragraph said "BUG-0002 carries
that change into the code", written by `plan` before the code existed. Once merged, a
present-tense "carries" reads as pending work. It is now past tense, in the same edit and the same
change-log row.

Nothing here changes a decision, so no ADR was written: ADR-0007 already decided what the two
routes report, and this is the overview being brought into line with the code that implements it.
