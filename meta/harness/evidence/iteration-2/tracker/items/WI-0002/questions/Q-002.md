## Context

**WI-0002, round 1, question 2 of 2: what counts as old.** (This is the last one for now — Q-001
asked about the shape of the folder tree; this one asks where the age boundaries go. Answer them
together and WI-0002 can be made Ready.)

Your story for this item says you want "old files separated from recent ones, so that the things
I am still working with stay easy to find and the rest is put away". "Old" is the word the whole
item turns on and nothing in the record defines it. We are not asking you to pick a number you do
not believe — a rough sense of your own folder is enough, and we will turn it into a boundary.

Two things we have decided ourselves rather than asking you, both reversible, both stated here so
you can overrule them if either is wrong:

1. **Age is measured from when the file was last modified** — the "Date modified" your file
   manager shows. On Linux, with the standard library we are limited to [src: ADR-0001], this is
   the only timestamp that means what a person means by a file's age: the alternative field is
   not a creation date, it is when the file's permissions or name last changed, and a true
   creation date is not recorded by most Linux filesystems at all. **If you meant "when it
   arrived in this folder" rather than "when I last changed it", say so** — for a downloads
   folder those are different, and it would change which files land where.
2. **A file exactly on a boundary counts as the older side.** Nobody notices this, and it has to
   be decided so that a test can check it.

## Question

How many age bands should there be, and where do the boundaries fall?

## Options considered

- **A — Two bands: `recent` and `old`, split at one year.** Consequence: the simplest thing
  that answers your story; one boundary to explain, one to remember. Cost: within a downloads
  folder that turns over quickly, a year is a long time and almost everything lands in `recent`.
- **B — Two bands, split at 90 days.** Consequence: matches how a downloads or desktop folder
  actually behaves — three months without touching something is a fair signal you are done with
  it. Cost: files you return to seasonally get put away between visits.
- **C — Three bands: `recent` (under 30 days), `this-year` (30 days to 1 year), `archive`
  (over 1 year).** Consequence: the most useful separation for a folder that has genuinely built
  up over years, which is how you described it. Cost: three folders per type instead of two, and
  a folder with few files looks over-organised.
- **D — By calendar year: `2024/`, `2025/`, `2026/`.** Consequence: no boundary to argue about,
  and it matches how people talk about old files. Cost: a file from last December is "old" on the
  1st of January, which surprises people; and the folder count grows forever.
- **E — A number of days you name.** Say "anything I haven't touched in N months is old" and we
  will use it.
- **Recommendation: C**, if you meant a folder that has built up over years, which is what your
  story says — it separates "this week's work" from "this year's" from "genuinely archived", and
  each band is a thing you would act on differently. **B** if you would rather have one boundary
  and be done with it. We would advise against D: it makes a file's band depend on the date you
  run the tool rather than on how old the file is.

## Answer

[human] Keep it simple — two bands, recent and old, split at a year. Anything I haven't
touched in a year is old.

Recorded as given: **option A — two bands, `recent` and `old`, one boundary at one year.** The
recommendation was C, three bands; it was not taken, and the record says so plainly rather than
quietly keeping the extra band. Two bands is what is being built.

**The two calls stated in this question were not overruled, and they remain assumptions rather
than the stakeholder's decisions.** Neither was contradicted, and a thing nobody objected to is
not a thing anybody agreed to:

1. **Age is measured from the last-modified time (`st_mtime`).** The question asked directly to be
   told if they meant "when it arrived in this folder" instead, and they did not say so. Their own
   phrasing — "anything I haven't **touched** in a year" — reads naturally as last-modified, but it
   does not distinguish last-modified from last-*accessed*, so it is weak support rather than a
   decision. `st_mtime` stands, on the reasoning already recorded [src: WI-0002/Q-002 `## Context`;
   src: ADR-0001], and it stays cheap to reverse: one call site in the planner plus the tests that
   fix timestamps.
2. **A file exactly on the boundary is `old`.** Unmentioned, so it stands. A file whose
   last-modified time is exactly one year before the run is `old`.

**What this answer does not settle, and nobody needs to be asked about:** what "one year" is
measured as — 365 days, 366 in a leap year, or twelve calendar months. Either reading is inside
what the stakeholder said, and the difference is a single day in a boundary nobody can perceive,
so this is not escalated and it is deliberately not decided here either: `refine` runs next and
AC4 cannot be made decidable without pinning it, so it is `refine`'s to pin — as an assumption
under its own routing test, in the same paragraph as its other three. It is named in WI-0002's
`## Notes` so that it cannot be missed.

The band names `recent` and `old` are the stakeholder's own words in both questions and are taken
as the folder names, which is also what makes the preview readable: the band is visible in the
destination path, so AC1's reporting requirement is met by the path itself.
