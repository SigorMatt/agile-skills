## Context

**BUG-0004, review round 1, question 1 of 2.** Both are from the D12 audit of a review that has
otherwise passed: the code is right, all four criteria are ticked with evidence, and the branch is
not yet merged. Both questions are about sentences in `docs/architecture/adr/` that this merge
affects, and `review-close` may not edit an ADR — `spec/doc-header.md` §5 lists that class as
"superseded only". This one is about ADR-0006; Q-002 is about ADR-0009, and they are separate
because the two documents are wrong in different ways and the remedies are not the same.

ADR-0006 decided that a failure to list the target folder is reported at the CLI boundary. Its
`## Consequences` names a cost, written when `cli.py`'s `except OSError` was the only handler
anywhere in the path:

> A cost worth naming: a genuine defect inside `build_plan` that surfaced as an `OSError` would
> now be reported as an unusable target rather than crashing loudly. `build_plan` reads the
> filesystem and composes strings, so the class of such defects is small, and the operating
> system's own reason in the message is what would give it away.

That was true when written and this item makes it partly false. After BUG-0004, an `OSError`
raised between `try:` and the `band = band_for(...)` line — which is where `entry.is_dir()` and
`entry.stat()` live — no longer reaches `cli.py` at all. It becomes that entry's `leave` line and
the run continues with exit 0 [src: tidy/planner.py:47; src: tidy/planner.py:57]. So a defect in
that region is now reported more quietly than the paragraph says, not as an unusable target; the
sentence remains correct only for an `OSError` from `os.scandir` or from anywhere outside the
guard.

Verified by reading the merged code rather than by inference: the same fixture that exited 2 with
`tidy: <folder> cannot be read: ...` on `main` exits 0 on this branch with
`leave  broken.pdf   [cannot be examined: No such file or directory]`
[src: BUG-0004; src: tidy/planner.py].

Nothing in ADR-0006's **decision** is disturbed — the target-level boundary works exactly as
BUG-0001 left it, confirmed by running all three of its cases during this review, each still
exit 2. What has gone stale is one consequence paragraph. ADR-0009 records the two boundaries
correctly and cites ADR-0006, but a reader who opens ADR-0006 directly — which is what a future
`plan` judging "may I widen this guard?" would do — gets the pre-BUG-0004 picture with nothing
signalling that it moved.

## Question

ADR-0006's `## Consequences` says a defect inside `build_plan` surfacing as an `OSError` would be
reported as an unusable target, which BUG-0004 makes untrue for the guarded region. How should the
record be corrected — is this the same clerical-correction latitude that BUG-0002/Q-002 established
for a factual clause inside an ADR, or does ADR-0006 stand as written with the correction recorded
only in ADR-0009?

## Options considered

- **A — correct the paragraph in place and bump ADR-0006 to v2, with a change-log row naming what
  changed.** The sentence becomes something like: an `OSError` from `os.scandir` is still reported
  as an unusable target, while one raised while interrogating a single entry is now that entry's
  `leave` line (ADR-0009), so a defect in that region surfaces quietly and the operating system's
  reason in the `leave` text is what would give it away. Consequence: both ADRs describe the same
  system, and a reader arriving at ADR-0006 first is not misled. This is exactly the remedy
  BUG-0002/Q-002 chose for ADR-0007's false clause, and the reasoning it recorded — §4's "never
  edited" is about the *decision*, while §3 requires every content change to bump the version —
  applies here unchanged [src: BUG-0002/Q-002].
- **B — leave ADR-0006 exactly as written, and rely on ADR-0009 and `overview.md` v7 to carry the
  correction.** Consequence: a `status: current` ADR keeps a consequence paragraph the code
  contradicts, and the reader it misleads is precisely the one who did the right thing and went to
  the decision record. This is the propagation path `spec/doc-header.md` §4a exists to close, and
  BUG-0002/Q-002 rejected it for that reason.
- **C — supersede ADR-0006 with a new ADR that restates the decision with the paragraph fixed.**
  Consequence: every existing citation of ADR-0006 — in ADR-0009, `overview.md`, `cli.py`'s
  comment, three plans — points at a superseded record, and nothing was decided differently. §4
  asks for supersession when a *decision* moves, and none has.
- **D — add one forward-pointing sentence to ADR-0006 without changing the paragraph**, e.g. "since
  ADR-0009, this applies only outside the per-entry guard". Consequence: cheaper than A and keeps
  the original wording visible as history, but leaves a paragraph whose first sentence is read
  before its qualification, which is the shape that misleads a skimming reader.
- **Recommendation: A.** It is the precedent this project already set for a factually stale clause
  in a current ADR, the decision is untouched, and the change-log row is what keeps the edit
  honest. D is a reasonable fallback if the architect wants the original wording preserved verbatim.

## Answer

**Option A: the paragraph is corrected in place and ADR-0006 goes to v2, with a change-log row
naming what changed.** Answered from the record; no escalation, and none of the four conditions in
`spec/question.md` §4 applies — no intent is needed that the record does not hold, a paragraph edit
with a change-log row is reversible in one commit, no ADR is contradicted (ADR-0006's decision is
untouched and ADR-0009 already cites it), and the record is not silent: this project settled the
same question five items ago.

What settles it is BUG-0002/Q-002, which asked whether a factual clause inside a `status: current`
ADR may be corrected and answered yes, on grounds that apply here word for word:
`spec/doc-header.md` §4's "never edited to change its decision" is about the **decision**, while
the same spec's §3 requires *every* content change to *every* document under `docs/` to bump the
version and add a change-log row — "a document class that could never be edited would have no use
for that rule" [src: BUG-0002/Q-002]. ADR-0007 was corrected on exactly that basis and is
`version: 2, updated-by: answer-questions` today [src: ADR-0007].

Nothing in ADR-0006 moves. Its decision — the target folder failing is reported at the CLI
boundary, one line on stderr, empty stdout, exit 2 — is what this project still does, re-run
during BUG-0004's review across all three of its cases, each exit 2 [src: BUG-0004]. What was
stale is one paragraph of `## Consequences`, and the correction states the two halves the cost has
become rather than deleting it: an `OSError` from `os.scandir` or from outside the guard still
arrives at the CLI handler and is reported as an unusable target; one raised while interrogating a
single entry becomes that entry's `leave` line and never reaches it. The sentence now says
explicitly that a defect in the guarded region surfaces **more** quietly than before, because that
is the fact a future reader judging "may I widen this guard?" most needs and the version this
review found had inverted.

Options B and D were rejected for the same reason B was rejected in BUG-0002/Q-002: they leave a
`status: current` ADR asserting something the code contradicts, and the reader they mislead is the
one who did the right thing and went to the decision record. C supersedes an ADR whose decision
never moved, which would point ADR-0009, `overview.md`, `tidy/cli.py`'s comment and three plans at
a superseded record for no gain.

**One correction to the review that raised this.** `review.md` `## Verdict` predicted that
answering these questions would move `main`, and it does not: this project's precedent puts a
document correction on the item's own branch — BUG-0002's ADR-0007 v2 landed in `d0a7ebd` on
`wi/BUG-0002` — so both edits are commits on `wi/BUG-0004` and the trunk is untouched at `73bb1f4`.
The resumed review can trial-merge normally.
