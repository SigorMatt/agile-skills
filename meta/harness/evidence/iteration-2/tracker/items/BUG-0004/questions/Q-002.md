## Context

**BUG-0004, review round 1, question 2 of 2, and that is all of them for now.** See Q-001 for the
frame: both come from the D12 audit of a review that has otherwise passed, both are about ADR
sentences this merge affects, and `review-close` may not edit an ADR (`spec/doc-header.md` §5).
Q-001 is about a consequence paragraph in ADR-0006 that becomes false; this one is about citations
in ADR-0009 that stay true but stop pointing at what they name.

ADR-0009 was written by `plan` for this item, against `main`, before the code existed. It cites
`tidy/planner.py` by line number six times, at four distinct lines. Checked by opening the file at
each cited line rather than by reading the sentence around it:

| cited | what the sentence says is there | on `main`, before the change | on `wi/BUG-0004`, after it |
|-------|--------------------------------|------------------------------|----------------------------|
| `tidy/planner.py:47` (twice) | `entry.is_dir()`, the call a symlink loop raises from | `if entry.is_dir():` ✓ | `try:` — the call is one line down |
| `tidy/planner.py:55` (twice) | `entry.stat()`, the call the item's fixture raises from | `band = band_for(now - entry.stat()...)` ✓ | `continue` — the call is one line down |
| `tidy/planner.py:85` | `os.path.lexists` / `os.path.isdir` in the collision helpers | `if os.path.lexists(path) and not os.path.isdir(path):` ✓ | a docstring line inside `_blocking_component`; the call is at 94 |
| `tidy/planner.py:114` | the same, in the other collision helper | `return destination in reserved or os.path.lexists(...)` ✓ | inside `_free_destination`; the call is at 133, nineteen lines away |

The guard adds nine lines above them all, so every citation drifts by exactly the amount the fix
inserted. The *claims* are all still true — the guard does cover those two calls and nothing else,
and the collision helpers do use functions that return rather than raise — and `lint-claims` passes
(exit 0), because §4a's table makes a path citation resolve when **the file** exists, not when the
line supports the sentence.

So no gate fails. What fails is the procedure D12 §9a prescribes: open the thing the sentence cites
and decide from what you read there. Doing that here lands on `try:`, on `continue`, and in the
wrong function. The general shape is worth a decision rather than a fix, because it is not specific
to this ADR: an ADR whose subject is a change to a file will cite that file, and the change it
describes is what invalidates its own line numbers. Every future item of this shape inherits it.

The two ADRs that predate this convention are not affected the same way: ADR-0008's
`[src: tidy/cli.py:52]` and ADR-0009's `[src: tidy/cli.py:67]` and `[src: tidy/cli.py:93]` were
re-checked during this review and all three still point at exactly what they name, because this
item does not touch `cli.py`.

## Question

ADR-0009's six line-number citations into `tidy/planner.py` were correct against `main` and point
at the wrong lines once BUG-0004 merges. Should they be repaired for this ADR, and should the
project adopt a rule about how ADRs cite code they are about to change?

## Options considered

- **A — repair ADR-0009's six citations to the post-merge line numbers, bump to v2 with a
  change-log row, and change nothing else.** Consequence: this ADR is accurate today and drifts
  again the next time anything above those lines in `planner.py` changes — which WI-0003 will do,
  since it rewrites where the rule tables come from. Cheap, and buys accuracy until the next edit.
- **B — replace the line numbers with bare file citations, `[src: tidy/planner.py]`, keeping the
  named symbols in the prose.** Consequence: the citation cannot go stale while the function
  exists, and the sentence already names `entry.is_dir()`, `entry.stat()`, `os.path.lexists` and
  `os.path.isdir` in backticks, so a reader has an exact search term. It loses the precision of a
  line number for a file of 140 lines, which is the smaller loss. Still a v2 with a change-log row.
- **C — leave ADR-0009 as written.** Consequence: the ADR records what was true when the decision
  was taken, which is §4's stated purpose ("the point of the file is to preserve what was believed
  at the time"), and the drift is discoverable by anyone who reads the surrounding prose. Costs
  nothing now; every future reader following a citation pays a few seconds and some doubt.
- **D — B for this ADR, plus a line in `docs/process/ways-of-working.md` saying that a document
  citing code an item is about to change cites the file and the symbol, not the line.**
  Consequence: fixes the class rather than the instance, and `ways-of-working.md` is a document
  `review-close` may update (§5) — but it does not exist yet in this project, so this option
  creates it, which is a larger step than one ADR needs and is properly the architect's call.
- **Recommendation: B, and D if the architect judges the class worth a standing rule.** The
  sentences are already self-sufficient through the symbols they name, and a citation that cannot
  rot is worth more here than one that is precise for one commit. A is the least disruptive if
  line-level precision is considered load-bearing; C is defensible on §4 grounds but leaves the
  D12 procedure landing on `continue`.

## Answer

**Option B: ADR-0009's six `tidy/planner.py:NN` citations become file-level citations, the named
symbols in the prose carry the precision, and the ADR goes to v2 with a change-log row.** Answered
from the record and from one decision that is mine to take; no escalation, and none of
`spec/question.md` §4's conditions applies — the change is reversible in one commit, contradicts no
ADR, needs no intent the record lacks, and is not a coin flip.

The record settles more of this than the question assumed. `spec/doc-header.md` §4a's citation
table makes `[src: path]` resolve when **the file exists**, and lists `path` and `path:line` as the
same form with the same test — so a line number was never what made a citation valid, and dropping
it costs nothing a gate was measuring. What §4a asks of a confident sentence is that a reader can
get from it to the evidence "in one hop", and every one of these sentences already names its
subject in backticks — `entry.is_dir()`, `entry.stat()`, `os.path.lexists`, `os.path.isdir` — which
is a search term that survives every edit above it. The line number was the least durable part of
each citation and the least load-bearing.

Option A was rejected on the evidence in the question itself: it buys accuracy until the next edit,
and WI-0003 is already scoped to change where the rule tables come from, which will move these
lines again. C — leave it, on §4's "preserve what was believed at the time" — misreads that clause,
which protects the **decision** and the reasoning, not the accuracy of a pointer; and it leaves the
D12 §9a procedure landing on `continue`, which is the one failure mode this project has already
paid for twice (ADR-0007's false clause, ADR-0004's stale test count).

**D is not taken, and the reason is a rule rather than a judgement.** `spec/doc-header.md` §5 says
`process/ways-of-working.md` is *created by* `plan`; `answer-questions` may only update it, and it
does not exist in this project yet. So the standing convention cannot be minted here without
exceeding what this skill may write. Instead the class-level reasoning is recorded where it will be
read by the next person to do this: a new bullet in ADR-0009's `## Consequences` states that the
citations name files and symbols rather than lines, and why — "an ADR about a change to a file
cites that file, and the change is what moves its own line numbers". An ADR is the document a
future `plan` reads before writing the next one, so the convention propagates by example, and a
`plan` execution that wants to make it binding can lift it into `ways-of-working.md` at the cost of
one paragraph.

**Scope of the edit, stated so the next reader does not think something was missed.** Only the six
citations into `tidy/planner.py` were changed. ADR-0009's `[src: tidy/cli.py:67]` and
`[src: tidy/cli.py:93]` were re-checked line by line during BUG-0004's review and both still point
at exactly what they name, because this item does not touch `cli.py`; the same is true of
ADR-0008's `[src: tidy/cli.py:52]`. Rewriting citations that are currently exact and that no
open question named would widen this answer past what was asked.
