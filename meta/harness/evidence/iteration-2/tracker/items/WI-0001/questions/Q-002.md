## Context

This is question 2 of 2 filed on WI-0001 in this round, and that is all of them for now. Both were
found before any code was written, and both are places where `artifacts/plan.md` under-determines
behaviour; Q-001 is the other.

`WI-0001/item.md` `## Notes` lists this case under **"Deliberately unconstrained, per DoR R10,
left so by `refine`"**:

> What happens if a destination folder name in AC5 is already taken by a **file** at the top level
> — e.g. a file literally called `images` sitting beside `photo.jpg`. No criterion constrains it.
> It is rare, it does not affect any other criterion, and pinning it now would be inventing a
> requirement; `plan` should decide it and record the decision, and it is a candidate bug item if
> it turns out to matter.

`plan` did not decide it. `grep` over `artifacts/plan.md` for this case returns nothing: it is
absent from `## Approach`, from all eight steps, from the five entries under `## Assumptions`, and
from `## Risks`. The plan's step 4 does specify error handling for `os.link` — `FileExistsError`
means the folder changed underneath the run, other `OSError` falls back to `shutil.move` — but the
failure here happens one line earlier, in `os.makedirs(dest_parent, exist_ok=True)`, which raises
`FileExistsError` when the path exists and is not a directory. No plan step catches it.

What falls out today with no decision taken: a top-level file named `images` has no extension, so
`folder_for` returns `None` and it becomes a `leave` action — it is not itself moved. But
`photo.jpg` beside it plans a move to `images/photo.jpg`, PREVIEW prints that move line, and APPLY
then raises an uncaught `FileExistsError` out of `makedirs` and the process dies with a traceback
partway through the action list.

This is user-visible behaviour that no acceptance criterion covers, so under `implement`'s
escalation rule it is not mine to choose. It also interacts with a criterion that *is* constrained:
under any option that lets PREVIEW print a move APPLY cannot perform, PREVIEW and APPLY no longer
produce the same set of (file, destination) pairs, which is what AC8 asserts.

## Question

When a destination folder named by AC5 is already occupied by a regular file at the target
folder's top level, what should the tool do with the files that would have been moved into it?

## Options considered

- **A — Handle it at apply time as a per-file failure.** Catch the `FileExistsError` from
  `os.makedirs`, leave that file where it is, add a message to `apply_plan`'s returned failure
  list, carry on with the remaining actions, and exit 1 — the same shape plan step 4 already uses
  for a move that could not be made. Consequence: no traceback, no data loss, and the rest of the
  folder is still tidied. But PREVIEW printed a move line for a move that did not happen, so the
  set of pairs APPLY produced differs from the set PREVIEW printed, which is the equality AC8
  asserts over an unchanged folder. It would turn a criterion that is currently structural into
  one with an exception.
- **B — Handle it at plan time.** In `build_plan`, before emitting a `move`, check whether the
  destination's parent exists and is not a directory; if so emit `Action(kind="leave", reason=...)`
  for that file instead. Consequence: PREVIEW and APPLY agree by construction, so AC8 stays
  structural [src: ADR-0002]; the user is told in PREVIEW, before anything moves, that these files
  will be left alone and why; the run exits 0 because nothing failed. The cost is one extra
  filesystem check per distinct destination folder inside the planner, which plan step 3 already
  establishes as acceptable — it stats destination paths there to resolve collisions.
- **C — Leave it unhandled, and let the traceback stand.** Consequence: zero code, and the case is
  genuinely rare. But it is the one outcome that is unambiguously worse than the others: the run
  dies partway through the action list, so the folder is left half-tidied with no report of what
  was done, and the user sees a stack trace rather than a message. The item's own framing — "a
  candidate bug item if it turns out to matter" — anticipated a decision, not a crash.
- **Recommendation:** **B.** It is the only option that keeps AC8 true by construction rather than
  by exception, it puts the information in front of the user during PREVIEW where this item's whole
  premise says it belongs, and it reuses a check the planner is already specified to make. If the
  architect would rather keep `build_plan`'s filesystem access confined strictly to what plan step
  3 names, A is the fallback and the AC8 exception should then be recorded explicitly rather than
  discovered by `verify`.

## Answer

**Option B. Decide it in `build_plan`: a file whose destination folder name is already occupied by
a non-directory at the top level becomes a `leave` action, with the reason naming the clash.** This
follows from ADR-0002, which is the decision the question has to fit inside rather than a fresh
choice.

ADR-0002 `## Decision` is explicit that `tidy/planner.py` computes, "for every entry directly inside
it, one `Action` describing what would happen", and that `tidy/apply.py` "executes an action list it
is given and computes nothing". Its `## Consequences` states the property this buys: "AC8 and AC10
become properties of the structure rather than things to test for separately". Option A puts a
decision — this file cannot be moved after all — inside `apply.py`, which is exactly the thing
ADR-0002 says that layer does not do, and it would make AC8 true only with an exception. Option B is
the only option that leaves ADR-0002's guarantee structural.

The filesystem check this needs is already sanctioned: plan step 3 has `build_plan` stat destination
paths to resolve collisions, and ADR-0002 forbids the planner *writing*, not reading. Checking
whether `<folder>/` exists and is not a directory is the same kind of read, once per distinct
destination.

Option C was rejected outright. `implement` is right that it is the only option strictly worse than
the others: `os.makedirs` raising out of the middle of the action list leaves the folder half-tidied
with no report of what was done, which contradicts the product promise that a user can see what
happened [src: docs/product/vision.md].

Two things this answer deliberately does **not** do. It does not add an acceptance criterion:
`refine` recorded that "pinning it now would be inventing a requirement", and that judgement stands
— the behaviour is recorded in the plan, with a named test, and stays out of the criteria. And it
does not mint an ADR, because it decides nothing ADR-0002 had not already decided; it applies
ADR-0002 to a case the plan overlooked.

The overlooked case is itself worth recording: `refine` routed this decision to `plan` in the item's
`## Notes`, and `plan` did not take it — `grep` over `plan.md` for the case returned nothing across
`## Approach`, all eight steps, `## Assumptions` and `## Risks`. `implement` filing a question rather
than picking the reasonable-looking branch is the protocol working. The gap is noted in the journal
as a `plan` defect worth fixing in the skill.
