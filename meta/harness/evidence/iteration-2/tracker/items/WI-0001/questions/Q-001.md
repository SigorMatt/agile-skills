## Context

This is question 1 of 2 filed on WI-0001 in this round, before any code was written. Both are
places where `artifacts/plan.md` under-determines behaviour the criteria constrain, and both
affect `tidy/cli.py`, so they are being asked together.

Plan step 5 specifies the CLI's output rule as:

> Otherwise call `build_plan`. If the plan contains no `move` action, print the single "Nothing to
> do" line and return 0 (AC15). Otherwise print the banner to stderr and one line per action to
> stdout in the forms above (AC3, AC6, AC10).

Read literally, "no `move` action → print only the single line" suppresses the `leave` lines. That
is fine for the four situations AC15 enumerates — empty, only subfolders, only hidden files, only
already-tidy content — because none of them produces a `leave` action either. It is not fine for a
folder whose entries are *all* unrecognised or extensionless, e.g. a folder holding only
`notes.xyz` and `README`. That folder has no `move` action, so step 5 prints one line and nothing
else; but AC6 says such a file "In both modes ... is reported on a line that names it and says it
is being left alone". AC6's own suggested check is to put exactly those two files in a folder.

So the plan as written fails AC6 in a case AC6 names, and the two criteria pull in opposite
directions for a folder that AC15's leading clause ("a folder with nothing to move") covers but
its enumeration does not. I have not written `cli.py` yet, and I will not choose between two
acceptance criteria — I am not permitted to change either, and guessing here is a user-visible
output decision.

## Question

Over a folder that contains at least one `leave` action and no `move` actions, what must stdout
contain — the `leave` lines, the single "Nothing to do" line, or both?

## Options considered

- **A — Print the `leave` lines, and then also the "Nothing to do" line.** Consequence: AC6 holds
  in the case it names. AC15's four enumerated situations are unaffected, because each produces
  zero `leave` lines, so stdout there is still exactly one line stating there is nothing to do.
  The only reading of AC15 that this breaks is the maximally broad one, under which *any* folder
  with nothing to move must emit exactly one stdout line total. The user gets both facts: what was
  left alone, and that nothing will move.
- **B — Follow plan step 5 literally: whenever there is no `move` action, stdout is the single
  "Nothing to do" line and nothing else.** Consequence: AC15 holds under every reading. AC6 fails
  for a folder of only-unrecognised files, which is exactly the fixture AC6 tells a verifier to
  build, so `verify` should be expected to reject the item.
- **C — Print the `leave` lines only, and suppress the "Nothing to do" line whenever any action
  exists.** Consequence: AC6 holds; AC15's four situations are unaffected. A user pointing the
  tool at a folder of unusual extensions sees the files listed as left alone but is never told in
  so many words that nothing will move — which is the outcome the item's `## Notes` assumption 3
  already flags as the one most likely to read as the tool being broken.
- **Recommendation:** **A.** It is the only option that satisfies AC6 and AC15 simultaneously on
  every fixture either criterion actually names, and it is the most informative to the user in the
  case the item already identified as the confusing one. It costs one extra line of output in a
  situation no criterion forbids extra lines in.

## Answer

**Option A. Print the `leave` lines, then the "Nothing to do" line after them.** This is answered
from intent already recorded during refinement, not decided fresh — the two criteria were written
in the same round, from two separate agenda items, and `artifacts/refinement-qa.md` states what
each was for.

`refinement-qa.md` **Q3** is where AC6 comes from: *"It is left exactly where it is, and both modes
report it on a distinct line saying so."* That reporting is stated unconditionally, and the reason
given is that leaving a file untidied silently is the outcome most likely to read as the tool being
broken — the same worry the item's `## Notes` assumption 3 records. Nothing in Q3 makes the line
contingent on some other file moving.

`refinement-qa.md` **Q5** is where AC15 comes from, and it names its own scope: *"Why asked: DoR
R10 — the empty and no-op cases are combinations of the modes this item introduces."* Its rationale
is anti-silence: *"a line rather than silence because silence is indistinguishable from a crash."*
AC15 exists so stdout is never empty. It was not written to suppress anything, and reading it that
way inverts the reason it was written.

So the criteria never actually conflicted; **plan step 5 introduced the conflict** by turning
"print a line when there would otherwise be none" into "print only that line". Option A restores
both intents: AC6's line is unconditional, and AC15's line still appears whenever nothing will
move. On each of AC15's four named fixtures — empty, only subfolders, only hidden files, only
already-tidy content — no `leave` action arises either, so stdout is that one line and nothing
else, exactly as AC15 says.

Option B was rejected because it fails AC6 on the fixture AC6 itself names. Option C was rejected
because it drops the anti-silence guarantee that is Q5's whole stated reason for AC15.

AC15 has been amended to say this explicitly rather than leaving a verifier to adjudicate two
criteria against each other. The amendment adds no behaviour: it records which criterion governs
the overlap, and it was made before any code existed, from the refinement record rather than from
an implementation.
