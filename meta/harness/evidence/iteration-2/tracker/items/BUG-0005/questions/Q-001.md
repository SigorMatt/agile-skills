## Context

I am reviewing BUG-0005 at `in-review`. The change itself is sound: eleven of the twelve
Definition of Done criteria pass, the diff is one clause of `README.md` plus one regression test,
verification is fresh, and all four commits on `wi/BUG-0005` name the item. **D12 fails**, and it
fails on an artifact this item produced rather than on the change.

D12 asks whether every claim in `docs/` about the behaviour this item touched is still true,
checked by opening what the claim cites rather than by reading the sentence. Doing that to
`ADR-0012` — `status: current`, `version: 1`, `updated-for: BUG-0005`, written by `plan` for this
item — turns up a factual claim that the code refutes. It appears twice, and the second time it is
load-bearing.

**In `## Consequences`:**

> A script that wants to distinguish "nothing moved" from "some moved" must count the
> `could not be moved` lines on stderr rather than read the exit status.

**In `## Options considered`, option B's risk**, as part of the reason for rejecting a fourth exit
status:

> the case for it is weaker here, because a script that cares can count the `could not be moved`
> lines on stderr

`tidy/apply.py` appends five distinct `Outcome("failed", …)` messages, and only **one** of them
contains the string `could not be moved` — the `shutil.move` failure at `tidy/apply.py:86`. The
other four are `could not create the folder for %s: %s; %s was left where it is` (line 46),
`%s appeared while tidying; %s was left where it is` (line 55), `%s was copied to %s but the
original could not be removed: %s` (line 67), and `%s already exists; %s was left where it is`
(line 80). `grep -c "could not be moved" tidy/apply.py` returns `1`.

The all-fail run ADR-0012 was written about takes the `os.makedirs` path, so it emits **none** of
them. Run during this review:

```
$ python3 -m tidy .harness/rv/allfail --apply 2>err.txt; echo "EXIT: $?"
EXIT: 1
$ grep -c "could not be moved" err.txt
0
$ cat err.txt
tidy: moving files. Nothing will be overwritten.
tidy: could not create the folder for recent/documents/doc.pdf: [Errno 13] Permission denied: …; doc.pdf was left where it is
tidy: could not create the folder for recent/images/photo.jpg: [Errno 13] Permission denied: …; photo.jpg was left where it is
```

A script following the ADR's advice counts **0** in the run where **nothing** moved, and concludes
"some moved" — the exact inverse of the truth, in precisely the scenario the ADR exists to
describe. This is the failure mode D12's own rationale in `spec/dor-dod.md` §3 names: a wrong
factual justification for a decision, which every later document re-quotes rather than re-checks.

I am not entitled to fix it. Correcting a factual clause of a `status: current` ADR in place is
established practice here — BUG-0002/Q-002 settled that — but the second occurrence sits inside
option B's rejection rationale, and weakening a rejected option's counter-argument touches the
reasoning behind decision A, which is the architect's, not the reviewer's. The decision itself
(three statuses, not four) is not in question and I am not asking for it to be reopened. The
README clause this item delivered is unaffected either way: it says nothing about stderr.

The item is suspended at `awaiting-answer` with `resume-to: in-review`. Nothing is merged;
`main` is unmoved.

## Question

ADR-0012 twice tells a reader to count `could not be moved` lines on stderr to tell an all-fail
run from a partial one, and in the all-fail run it describes there are none — how should the two
sentences be corrected, and does the correction weaken option B's rejection enough to need
anything more than a version bump?

## Options considered

- **A — Correct both sentences in place to name the observable that exists, at ADR-0012 v2 with a
  change-log row.** The honest replacement is the count of `tidy:` failure lines on stderr, or the
  presence of any `move` line whose file is no longer at the top level; the simplest true form is
  "count the failure lines tidy prints on stderr — there is one per file that could not be
  moved". Consequence: the ADR states something a reader can act on, decision A stands unchanged,
  and option B's rejection keeps a real workaround rather than an imaginary one. Cost: one ADR,
  two clauses, a version bump and a change-log row. This is exactly the shape of the BUG-0002/Q-002
  correction, and of the ADR-0008 correction made for WI-0003.
- **B — Correct `## Consequences` only, and rewrite option B's risk clause to drop the workaround
  entirely**, conceding that the case against a fourth status rests on contract stability alone
  (ADR-0006's "the contract grows faster than the tool") rather than on a stderr workaround.
  Consequence: the ADR is honest about a weaker argument, which is more accurate than repairing
  the workaround if the architect judges per-line counting to be an unreasonable thing to ask of a
  script. Cost: same edit size; it slightly weakens the recorded case for the decision, which is
  itself worth recording. Risk: if the case for A is genuinely weaker than written, someone may
  reasonably reopen B later — which is an argument for saying so, not against.
- **C — Treat it as out of BUG-0005's scope: file it as a separate bug against ADR-0012 and close
  this item.** Consequence: BUG-0005 merges now. Cost: D12 is a hard gate on *this* item and the
  claim is in *this* item's own ADR, `updated-for: BUG-0005` — closing over it is the "accepted gap
  that exists only inside a report" this skill is warned about, and the epic would then close with
  a known-false clause in a `status: current` ADR.
- **D — Leave it: read `could not be moved` as naming a class of line rather than a literal.**
  Consequence: no work. Cost: the ADR renders it in backticks, which in this project's documents
  means a literal string, and the four other failure messages do not share a common substring, so
  even the generous reading has no observable behind it. The advice does not become true under any
  reading.
- **Recommendation: A.** It is the smallest edit that makes the ADR true, it leaves decision A
  and BUG-0005's delivered README clause untouched, and it keeps the rejection of option B resting
  on an argument that actually holds. If the architect judges the workaround unreasonable to ask
  of a script even when correctly described, B is the honest fallback and the two differ by one
  sentence. C and D both end with a `status: current` ADR saying something the code refutes, which
  is what D12 exists to stop.

## Answer

**Option A, with the replacement observable changed — because the one the review proposed is
false in the same way the sentence it replaces is.** ADR-0012 is corrected in place at **v2** with
a change-log row, both sentences, and no supersession: a version bump is enough, and the answer to
the second half of the question is **no, nothing more than a version bump is needed**.

Decided here, not escalated. None of the four conditions in `spec/question.md` §4 applies: the
decision is not being changed (three exit statuses, and `README.md`'s corrected clause, both
stand), nothing irreversible is being committed, no ADR is contradicted, and the record is not
silent — `spec/doc-header.md` §3 requires *every* content change to bump the version and add a
change-log row, and §4's "never edited" rule is about the **decision**. BUG-0002/Q-002 settled
exactly this and gave the reasoning; ADR-0007 v2 and ADR-0008's WI-0003 correction are the
precedents.

**Why not the review's own wording for the replacement.** The recommendation proposed "count the
failure lines `tidy` prints on stderr — there is one per file that could not be moved". Checked
rather than read, that is not something a script can do either, for a second reason the review did
not test:

- No phrase runs through all five of `apply_plan`'s failure messages. `was left where it is` is in
  three of them (`tidy/apply.py:46`, `:55`, `:80`) and `could not` is in three (`:46`, `:67`,
  `:85`), and the two sets are not the same three. There is nothing to grep for.
- Whatever a script does grep for, the failure lines are not alone on stderr. Forcing the mixed
  case here — one `os.makedirs` denial and one injected `os.link` refusal in the same run —
  produced three `tidy: ` lines: the banner, one failure, and one **success**, ADR-0003's
  fall-back notice (`photo.jpg was moved to recent/images/photo.jpg without a hard link…`), while
  `photo.jpg` had in fact moved and `doc.pdf` had not. A line count returns 3 for a run in which
  one of two files moved.

Repairing the ADR with a second uncountable count would have left D12 exactly where it found it.

**What the corrected sentences say.** `## Consequences` now names the observable that exists:
stdout carries one `move` line per intended move, printed *before* anything is attempted, so a
script reads those lines and then looks at the folder — every source named in a `move` line that
is still where it was is a file the run did not move away, and if that is all of them, nothing
moved. Confirmed on the all-fail run this ADR is about: exit 1, a `move` line for each file, both
sources still at the top level. The one case that reading does not separate is `tidy/apply.py:67`
— a copy reached the destination and the original could not be removed — and the ADR now says so
rather than leaving it to be discovered.

**What that does to option B's rejection, and why it is still only a version bump.** The
workaround was never the load-bearing argument. The primary one is ADR-0006's, quoted correctly
in the same clause and verified here at `ADR-0006:51-52`: a fourth number in a contract
`README.md` and ADR-0006 both bound to 0, 1 and 2, and "the contract grows faster than the tool".
That argument is untouched by this correction, so decision A does not move and no new ADR is
needed. What *has* changed is the secondary argument's weight: the workaround is a per-file check
against the filesystem, not a number to read, which is dearer than v1 implied. Option B's risk
clause now says that in terms, and says explicitly that this is a weaker case against B than v1
recorded — so that if someone later judges a per-file check too dear to ask of a script, they can
reopen B on that ground honestly, rather than discovering the ground was never there. Recording a
weaker argument as weaker is the correction; hiding the weakening would be the second defect.

Option B in the review's list — dropping the workaround entirely — was rejected because a
workaround does exist and a reader who needs it should be told what it is. C leaves a
`status: current` ADR contradicting the code, on this item's own artifact, which is what D12 is
for. D was already answered by the review: the four other failure messages share no substring, so
the generous reading has no observable behind it either.

BUG-0005's acceptance criteria are unchanged and nothing in `README.md` or `tidy/` is touched: the
delivered clause says nothing about stderr. The item returns to `in-review`, its recorded
`resume-to`, and `review-close` re-runs D12 against ADR-0012 v2.
