## Question

ADR-0008's two `[src: run: …]` citations record an observation — "five imports: argparse, os,
sys, .apply, .planner" — that WI-0003's merge makes unreproducible, while the claim they support
stays true. What should happen to them, so that a reader performing D12's audit on ADR-0008
arrives at something that supports its sentence?

## Options considered

- **A — Amend both citations in place to the anchored check, and bump ADR-0008 to v2.** Replace
  the recorded grep and its five-import output with the form that actually decides the claim:
  `[src: run: grep -nE "^(from|import).*\brules\b" tidy/cli.py → exit 1, no output]`, with a
  change-log row naming WI-0003. Consequence: the citation stops being a snapshot of a file that
  will keep changing and becomes a test of the claim itself — it stays true when a seventh import
  is added, and it *fails* precisely when someone imports the rules module, which is the event
  the ADR exists to prevent. Cost: one document, one version bump; a reader has to know what
  `\b` does. This also fixes the second occurrence, which A must not forget — the stale string
  appears twice and repairing one is worse than repairing neither, because the two would then
  disagree.
- **B — Supersede ADR-0008 with a new ADR that restates the decision with durable evidence.**
  Consequence: the strongest signal, and the honest move if the *decision* had changed — but it
  has not. The help text is still prose, the test still guards it, and nothing about option A, B
  or C in that ADR is now weighed differently. Superseding an ADR whose decision still stands
  makes the record harder to read, not easier, and future readers must chase two documents to
  learn one unchanged thing.
- **C — Change nothing, and record the general rule instead: a `run:` citation is a dated
  observation, not a live claim.** Consequence: cheapest, and there is something to it — a
  recorded command output is evidence of what was true *when it was recorded*, which is what
  makes it worth writing down. But `spec/doc-header.md` §4a admits `run:` as a citation form for
  absolute claims without dating them, so nothing in the record tells a reader which citations
  are live and which are historical, and D12 tells them to decide from what they open. Taking C
  means amending `spec/doc-header.md` — the toolkit, which is outside EP-001's scope — or leaving
  every `run:` citation in this project permanently ambiguous. It also leaves the misleading
  `rules`-prefixed import sitting under the one claim most likely to be got wrong.
- **D — Fix it as part of BUG-0006 instead**, widening that item's AC2 from `path:line` citations
  to every citation form in `docs/`. Consequence: one document touched once rather than twice,
  and BUG-0006 is already `ready` and already about ADR-0008's citations. But it widens a
  refined, planned-for item's scope after the fact, and it leaves WI-0003 suspended on an item
  that has not been planned yet — WI-0003 would wait for BUG-0006's whole pipeline rather than
  for one edit.

- **Recommendation: A**, with the second occurrence at line 76 amended in the same edit and a
  change-log row naming WI-0003. It is the only option that leaves the ADR's stated checkable
  condition actually checkable, it is one edit to one document, it does not touch `tidy/`, and it
  unblocks WI-0003's merge immediately. If A is taken, BUG-0006 should be told: its AC2 sweep
  should be widened to `run:` citations too, or it will pass while the class of defect it names
  survives elsewhere — but that is BUG-0006's `refine`/`plan` to decide, not a condition on this
  answer.

## Answer

**Option A: both `[src: run: …]` citations in `## Decision` are amended in place to the anchored
check, and ADR-0008 goes to v2 with a change-log row naming WI-0003.** Answered from the record;
no escalation, and none of the four conditions in `spec/question.md` §4 applies — the edit is
reversible in one commit, it contradicts no ADR (ADR-0008's decision is untouched and is still
what the code does), it needs no intent the record does not hold, and the record is not silent:
this project has now settled the same class of question twice.

**What settles the permission.** `spec/doc-header.md` §5 puts ADRs in the "superseded only"
class, and BUG-0002/Q-002 asked whether that forbids correcting a factual clause inside a
`status: current` ADR. It answered no, on grounds that apply here word for word: §4's "never
edited to change its decision" is about the **decision**, while §3 requires *every* content change
to *every* document under `docs/` to bump the version and add a change-log row — "a document class
that could never be edited would have no use for that rule" [src: BUG-0002/Q-002]. ADR-0007 was
corrected on that basis and ADR-0006 after it; both are `updated-by: answer-questions` today
[src: ADR-0007; src: ADR-0006].

**What settles the choice between A and the rest.** BUG-0004/Q-002 faced the same defect one
citation-form over — six `tidy/planner.py:NN` pointers that the next edit would move — and chose
the durable form over the accurate-until-next-edit one, on the reasoning that "an ADR about a
change to a file cites that file, and the change is what moves its own line numbers"
[src: BUG-0004/Q-002]. A `run:` citation whose recorded output enumerates a file's imports has the
same defect in a different dress: it is a snapshot of something the project keeps editing, so it
decays on a schedule set by unrelated work. The anchored form
`grep -nE "^(from|import).*\brules\b" tidy/cli.py` is a *test of the claim*: it returns exit 1
and no output today, it will still do so when a seventh import is added, and it fails exactly when
someone imports the rule table — which is the event ADR-0008 exists to prevent. Re-run on the
branch head before this answer was written, it gives exit 1 with no output, and the six-import
listing that replaced the recorded five is what makes the old citation unreproducible
[src: run: grep -nE "^(from|import).*\brules\b" tidy/cli.py → exit 1, no output].

B was rejected on the question's own ground and on this project's precedent: superseding an ADR
whose decision still stands makes a reader chase two documents to learn one unchanged thing, and
BUG-0004/Q-001 rejected the same move for the same reason. C leaves a `status: current` ADR whose
stated checkable condition cannot be checked, with a `rules`-prefixed import sitting under the one
claim this project singled out as the quietest way to get wrong; taking it properly would also
mean amending `spec/doc-header.md` §4a, which is the toolkit and outside EP-001. D widens a
refined item's scope after the fact and would hold WI-0003's merge behind BUG-0006's whole
pipeline.

**Scope of the edit, stated so a later reader does not think something was missed.** Three things
were left alone deliberately.

1. **The third `run:` citation, in the Reversibility bullet.** `grep -rn "epilog\|description="
   tidy tests --include=*.py` still gives exactly the recorded outcome — exit 0, two hits, both
   `tidy/cli.py` — so it is reproducible and nothing asks it to change
   [src: run: grep -rn "epilog\|description=" tidy tests --include=*.py → exit 0, two hits, both
   `tidy/cli.py`].
2. **`[src: tidy/cli.py:52]` at ADR-0008 line 48.** That is BUG-0006, which is `ready` and states
   the defect precisely; fixing it inside this answer would resolve an item that has not been
   planned and would leave BUG-0006 describing work already done. The edit made here is entirely
   below line 48, so BUG-0006's summary and reproduction steps still land where they say they do
   [src: BUG-0006].
3. **The generalisation into `spec/doc-header.md` §4a** — that a `run:` citation is a dated
   observation and the spec does not distinguish live claims from historical ones. That is a
   finding about the toolkit, not about EP-001, and this skill may not edit the spec. Following
   BUG-0004/Q-002's precedent, the class-level rule is recorded instead in ADR-0008's
   `## Consequences`, where the next `plan` will read it: cite an absolute claim with a command
   that tests it, not with one whose output happened to be true on the day.

**A note for BUG-0006, which is not a condition on this answer.** BUG-0006's AC2 sweeps
`src: <file>:<line>` forms only, so the class of defect it names survives in `run:` citations
elsewhere. Whether to widen that criterion is `plan`'s to weigh when BUG-0006 is designed; it is
recorded here rather than in BUG-0006 because amending another item's criteria is not this
skill's to do.

**No scope was widened and no defect was found.** ADR-0008's decision, WI-0003's twelve criteria
and everything under `tidy/` are untouched by this answer, so no new item is filed. WI-0003
returns to `in-review`, the `resume-to` its suspending row records, with the D12 failure removed
and the branch still unmerged for `review-close` to finish.
