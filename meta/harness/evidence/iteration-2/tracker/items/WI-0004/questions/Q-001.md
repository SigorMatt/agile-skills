When you signed off the tool you accepted it and asked for one thing on top: *"I don't want to
pass `--rules` every single time, so give the rule file a default spot it just picks up on its
own."* [src: EP-001/Q-005] That is now a work item, WI-0004, and this question is the one thing in
it that is yours rather than ours.

Everything else about it has been decided without troubling you, under your standing "whatever's
easiest for you to build and test" [src: EP-001/Q-001]: `--rules PATH` will still work and will
beat the default when you use both; a broken rule file at the default spot will be refused in one
line rather than silently ignored; and a run will say which rule file it used. That last one is
worth a sentence, because it is your protection: when the tool was built we deliberately decided
*not* to have a default location, and the reason was that a file you did not name could change
what a run does without appearing anywhere you looked [src: ADR-0010]. You have overruled that,
which is your call — so the tool will now name the rule file it is using, and that line is part of
the preview you read before anything moves.

What we cannot decide for you is **which kind of place** the file lives in, because the two
candidates differ in one way you would care about: whether a folder somebody else handed you can
carry rules that change what happens to your files. That is the same instinct as "never overwrite
anything", which you told us was the thing you actually cared about [src: EP-001/Q-002], so we are
not going to guess it.

You are not being asked what to call the file. Whatever you pick, we will choose the exact name
and spelling; the names below are only there so the options are easy to picture.

## Question

**Where should `tidy` look for a rule file when you have not named one on the command line?**

## Options considered

- **A — In the folder being tidied.** A file called something like `.tidyrules` sitting in the
  folder you point the tool at. Consequence: different folders can have different rules without your
  typing a flag — your `~/Downloads` sorts one way, a project folder another — and the rules travel
  with the folder if you move or copy it. The cost is the one ADR-0010 was worried about: a folder
  somebody else gave you, or one you copied off a drive, can carry a rule file you did not write,
  and it will shape the run. You would see it — the run names the file it used, and the preview
  still shows you every move before anything happens [src: docs/product/vision.md] — but you would have to be reading.
- **B — In your own config directory.** One file that is yours, at something like
  `~/.config/tidy/rules.ini`, used for every folder you tidy. Consequence: nothing in a folder can
  change what the tool does, ever; the only rules that apply are the ones you wrote in your own
  home directory. The cost is that per-folder rules go back to needing `--rules`, and a mistake in
  that one file affects every run until you fix it.
- **C — Both, the folder's file first and yours as the fallback.** Consequence: the most
  flexible — a per-folder file when you want one, your own file the rest of the time. The cost is
  that there are now two places a rule file can hide, so when a run does something you did not
  expect there are two files to check rather than one. (The run would still name which one it
  used.)
- **Recommendation: B.** It is the closest to what you actually said — "give *the* rule file a
  default spot", singular, meaning the file you wrote — and it is the only one of the three where
  a folder you were handed cannot change what happens to your files. A is a real feature and we
  would build it if you want it, but it reintroduces exactly the surprise this tool has spent nine
  items avoiding. C can be added later on top of either, so choosing B now does not close it off.

## Answer

[human] B. My own file, not one sitting in the folder — I don't want rules riding along in a
folder someone hands me. Go with your recommendation.

**What that settles.** The default location is a file in the user's own config directory — one
file, used for whichever folder is being tidied — and **not** a file in the folder being tidied. Nothing inside a target
folder can change what a run does [src: WI-0004/Q-001]; option A is not built and option C is not
built. The exact
filename and path spelling remain ours, as this question said they would — `refine` and `plan` fix
them, and `~/.config/tidy/rules.ini` is a picture rather than a decision. `--rules PATH` still
works and still wins when both are present, and a run still says which rule file it used.

The three things this does **not** settle, because they were never in the question: whether the
config directory is located by `XDG_CONFIG_HOME` or by a fixed `~/.config`; what a run prints when
there is no rule file anywhere; and whether `--rules ""` falls back to the default. The first two
are `refine`'s round 2, the third is `plan`'s [src: WI-0004].
