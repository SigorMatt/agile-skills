## Context

All six criteria pass; this is not about the delivered behaviour, which is correct and stays
correct whatever the answer.

While checking ADR-0008's reasoning rather than only its decision, I measured the option it
rejects. ADR-0008 `## Options considered` says of option B (`sys.stdout.reconfigure(errors=
"surrogateescape")`):

> Risk: it only fixes the surrogate case. A name that is valid UTF-8 but unencodable in the
> *terminal's* encoding — `café.txt` under `LC_ALL=C` — still raises, so the bug returns in a
> different costume.

**The example does not reproduce.** Under `LC_ALL=C`, CPython enables UTF-8 mode (PEP 540), so
`sys.stdout.encoding` is `utf-8` and option B handles `café.txt` without complaint. Measured by
building both variants and running each under two settings:

```
stdout encoding:  LC_ALL=C -> utf-8        PYTHONIOENCODING=ascii -> ascii

option A (chosen, bytes)
  undecodable name, LC_ALL=C : exit=0  b'3  bad\xff.txt\n2  good.txt\n5  total\n'
  cafe.txt,         LC_ALL=C : exit=0  b'4  caf\xc3\xa9.txt\n4  total\n'
  undecodable name, ascii io : exit=0  b'3  bad\xff.txt\n2  good.txt\n5  total\n'
  cafe.txt,         ascii io : exit=0  b'4  caf\xc3\xa9.txt\n4  total\n'

option B (reconfigure)
  undecodable name, LC_ALL=C : exit=0  b'3  bad\xff.txt\n2  good.txt\n5  total\n'
  cafe.txt,         LC_ALL=C : exit=0  b'4  caf\xc3\xa9.txt\n4  total\n'
  undecodable name, ascii io : exit=0  b'3  bad\xff.txt\n2  good.txt\n5  total\n'
  cafe.txt,         ascii io : exit=1  b''  UnicodeEncodeError
```

So the ADR's **conclusion is right** — option A is strictly more robust, and option B does fail
exactly as described — but its **example is wrong**: the failure needs a genuinely non-UTF-8 stdout
(`PYTHONIOENCODING=ascii`), not the `LC_ALL=C` the ADR names. On this platform `LC_ALL=C` is
precisely the case where option B survives.

This matters because the ADR is the record of *why* the tool writes bytes. A future reader who
tries the stated example will find it working, conclude the reasoning was mistaken, and may
"simplify" the write back to `print` — which the last line of the table shows would reintroduce
the bug for anyone with a non-UTF-8 stdout.

Filed non-blocking: nothing about the code, the criteria or this verification depends on the
answer, and the item is at `verifying` with everything demonstrated.

## Question

ADR-0008 rejects option B using an example (`café.txt` under `LC_ALL=C`) that does not reproduce,
though the risk it illustrates is real under `PYTHONIOENCODING=ascii`. How should the ADR be
corrected — and is correcting an ADR's *rationale*, without touching its decision, an amendment or
a supersession?

## Options considered

- **A — amend ADR-0008 in place**: replace the `LC_ALL=C` example with the measured
  `PYTHONIOENCODING=ascii` one, bump it to v2, and add a change-log row saying the decision is
  unchanged and only the evidence for it was corrected. Consequence: the ADR keeps one identity,
  and `spec/doc-header.md`'s rule — "An ADR is **never edited to change its decision**" — is
  respected, because the decision does not change. The version bump and change-log row are what
  make the edit visible.
- **B — supersede ADR-0008 with a new ADR** that repeats the decision with corrected reasoning.
  Consequence: heavier, and it implies the decision was revisited when it was not; a reader
  comparing the two would look for the change in the decision and find none.
- **C — leave the ADR and record the correction only here.** Consequence: the misleading example
  stays in the document people actually read, and the correction lives in a question file nobody
  will open. This is how a rationale rots.
- **Recommendation: A.** The decision stands, the evidence for it is stronger after the
  correction than before, and `doc-header.md` §4 forbids only changing a decision by edit. The
  measurement above is ready to paste in.

## Answer

**Option A: amended in place, at v2, with the wrong claim left visible.** ADR-0008's option B now
names `PYTHONIOENCODING=ascii` as the case that breaks, and carries a `**Correction, v2**` block
holding the measurement table from this question and stating what v1 believed.

On the second half of the question — whether correcting a rationale is an amendment or a
supersession — the rule decides it. `spec/doc-header.md` §4: "An ADR is **never edited to change
its decision**. It is superseded by a new ADR that cites it… The point of the file is to preserve
what was believed at the time." Two things follow, and they pull in opposite directions only until
you read them together:

- The **decision** is untouched — the report is still written as `os.fsencode`d bytes to
  `sys.stdout.buffer` — so the sentence forbidding edits does not apply. Superseding would imply
  the decision was revisited, and a reader comparing v1 and v2 would hunt for a change that is not
  there.
- "Preserve what was believed at the time" is why the correction **adds** rather than replaces.
  Deleting the `LC_ALL=C` claim would erase the fact that the decision was made on a partly wrong
  premise, which is exactly the kind of thing this record exists to keep. So v2 says what v1
  claimed, what was measured, and which of the two is right.

The measurement makes the decision **stronger**, not weaker: option A is the only one of the two
that is independent of stdout's encoding, and there is now a command that shows it —
`PYTHONIOENCODING=ascii` on `café.txt`, exit 0 against exit 1. A future reader who tries the
example will now find it reproducing, which is the whole point of fixing it.

`verify` was right to file this rather than let it pass or edit the ADR itself: it does not write
to `docs/`, and a rationale a reader can disprove in one command is an invitation to undo the fix.

**Not escalated to the human.** None of `spec/question.md` §4's four conditions applies: the intent
is in the ADR and unchanged, the edit is reversible, it contradicts no decision, and the
measurement settled it rather than a preference.
