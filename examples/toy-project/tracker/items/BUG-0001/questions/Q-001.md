## Context

BUG-0001 is planned: the triggers were reproduced, the root cause was confirmed at the
interpreter, `artifacts/plan.md` and ADR-0006 are written, `docs/architecture/overview.md` is at
v3, and `scripts/transition BUG-0001 --to planned --actor plan` ran with every gate passing.

The transition applied and then left the workspace invalid:

```
$ python3 .claude/agile-skills/scripts/validate-workspace .
tracker/items/BUG-0001/history.md:6: ERROR [history.order] timestamp 2026-08-16T22:44:02Z is
    earlier than the previous row (2026-08-17T01:30:00Z)

    (2026-08-16T22:44:02Z) is earlier than created (2026-08-17T01:30:00Z)
```

Neither error is about the plan, the bug, or anything a skill decided. **Two clocks disagree.**

```
$ date -u   → UTC now: 2026-08-16T22:45:58Z
$ date      → local now: 2026-08-17T01:45:58 IDT
```

The independent regression pass stamped everything it wrote — `BUG-0001`, `BUG-0002`,
`BUG-0003` and `EP-001/questions/Q-001.md` — `2026-08-17T01:30:00Z`, which is this machine's
**local** time (IDT, UTC+3) labelled as `Z`. `scripts/transition` writes
`datetime.datetime.now(datetime.timezone.utc)`, which is true UTC. Every row this pipeline writes
for the next ~2h45m is therefore "earlier" than the rows those items were created with, and
`validate-workspace` — correctly — rejects the history as out of order.

This is not confined to BUG-0001. The same failure will happen on the **first transition of every
one of the three bug items**, and it happened silently in a place where it did not yet break
anything: `EP-001`'s reopening row is stamped `2026-08-16T22:40:08Z` while the question that
caused it says `created: 2026-08-17T01:30:00Z`, so the epic's record already reads as though it
was reopened three hours before the question was asked.

`plan` cannot repair it. The row is written; `history.md` may not be edited by hand — the
adapter's hook denies exactly that, deliberately — and `scripts/transition` has no `--when`, so
re-running it produces the same value. Nothing in the item is wrong, and no gate refused
anything.

**Filed `blocking: false`, and that needs explaining.** In substance this blocks everything, not

## Question

Two clocks in one workspace disagree by three hours: the independent regression pass wrote local
time labelled `Z`, and `scripts/transition` writes true UTC. How should the pipeline record time
so that a history row written now is not "before" an item created three hours in the future — and
what repairs the row that is already there?

## Options considered

- **A — make `scripts/transition` write `max(now(), last_row + 1s)`.** The clock is still the
  source of truth; when it disagrees with the record, the record's own last row wins by one
  second. Consequence: no history can ever be out of order, the disagreement is self-healing, and
  it cannot be used to backdate — the value only ever moves forward. It does mean a row may carry
  a timestamp slightly ahead of true UTC, which is the lesser of the two lies. Repairs the
  existing row only if the row is rewritten too, so it needs to be paired with C or D.
- **B — a `--when` flag on `scripts/transition`.** Consequence: the caller chooses, which is
  exactly the power the append-only rule exists to withhold from an agent under pressure. It
  would repair this row and open a hole in every future one.
- **C — correct the four artifacts the regression pass stamped** (three bug items' `created` and
  history rows, and `EP-001/questions/Q-001.md`) to true UTC, then re-run this transition.
  Consequence: the record becomes internally consistent and honest about UTC — but it means
  rewriting `history.md` files, which no skill may do, so it is a human's or a tool's job, not
  mine.
- **D — loosen `history.order` to allow a tolerance.** Consequence: rejected, and named only so
  that it is on the record as considered. Timestamp order is how a reader reconstructs what
  happened; a validator that tolerates rows in the wrong order stops being able to report the
  case where something really did happen out of sequence.
- **E — wait ~2h45m for true UTC to pass `01:30:00Z` and re-run.** Consequence: every timestamp
  stays honest and nothing is edited, but it is not a fix — the next run against a differently
  skewed filer repeats it — and it leaves the workspace invalid meanwhile.
- **Recommendation: A for the future, C for this row.** A is one expression in `transition`'s
  `now()` and makes the pipeline immune to a filer whose clock is ahead; C is the only thing that
  makes the *existing* four artifacts honest, and it needs a hand that is allowed to rewrite a
  history file. If only one is possible, A alone still unblocks every future transition — but this
  item's row stays out of order until something rewrites it.

## Answer

Recommendation A was taken at the methodology level, and it is in the installed tooling. The
answer has three parts, because the question had two and the record turned out to hold a third.

### 1. The append side is fixed, and this failure cannot recur

`scripts/transition` no longer stamps a row with the bare clock. Read at
`.claude/agile-skills/scripts/transition`:

```python
def monotonic_now(history_text):
    stamp = now()
    previous = last_when(history_text)
    if previous and previous >= stamp:
        parsed = datetime.datetime.strptime(previous, "%Y-%m-%dT%H:%M:%SZ")
        bumped = (parsed + datetime.timedelta(seconds=1)).strftime("%Y-%m-%dT%H:%M:%SZ")
        return bumped, previous
    return stamp, None
```

and, at the call site, the clamp is announced rather than swallowed:

> `transition: the previous history row is stamped {clamped_after}, which is not earlier than
> this machine's clock ({now()}). Using {timestamp} so the record stays orderable. Check that
> earlier artifacts were stamped in UTC.`

Its docstring states the reasoning: "one bad timestamp cannot poison the whole item's record, and
the clamp is announced rather than silent, because a clock that needs clamping is itself worth
knowing about." That is exactly the `max(now(), last_row + 1s)` rule this question recommended,
plus the announcement, which is better than what was asked for: a skewed clock is now *visible*
at the moment it is worked around instead of being inferred later from a validator error.

`spec/journal-and-history.md` §1 still carries the two rules that make this checkable — `when`
"MUST be ≥ the previous row's `when`" and "Timestamps MUST be non-decreasing". One discrepancy,
recorded because a record that is silently different from what it is believed to say is worse
than one that is wrong out loud: **§1 does not contain a sentence assigning monotonicity to the
appending tool.** The behaviour is in the script and its docstring; the spec still states the
invariant without naming who enforces it. Whoever amends the spec next should add it there.

BUG-0002 and BUG-0003 demonstrate the fix works: their only history row is stamped
`2026-08-17T01:30:00Z`, ahead of this machine's clock, and their next transition will be clamped
to `2026-08-17T01:30:01Z` and announced. Neither is frozen.

### 2. The skewed artifacts: corrected where correcting them helps, left where it would split an event

The four artifacts are wrong — they claim `2026-08-17T01:30:00Z` for a moment whose true UTC was
`2026-08-16T22:30:00Z`. But they are not free-standing: each sits beside a **history row stamped
with the same wrong value**, and history rows may not be touched. Correcting a field while its
row keeps the old value makes one event carry two times.

I tried the sweeping correction first and the validator rejected it, which is the evidence this
answer rests on rather than a preference:

```
tracker/items/BUG-0002/item.md: ERROR [item.updated.stale] updated (2026-08-16T22:30:00Z) is
    earlier than the last history row (2026-08-17T01:30:00Z); a skill wrote history without
    touching the item
tracker/items/EP-001/journal.md:351: ERROR [journal.order] entry timestamp 2026-08-16T22:41:00Z
    is earlier than the previous entry (2026-08-17T01:30:00Z)
```

So the rule applied is: **correct a skewed value where leaving it would break ordering, poison a
future field, or produce a false reading; leave it where the correction would only make a
correctable half disagree with an uncorrectable one.**

- **`created` on all three bug items → `2026-08-16T22:30:00Z`.** Corrected, and this one is not
  cosmetic: `updated` is forced forward by every transition, so a `created` three hours in the
  future would make `item.updated.before-created` fire on **every future transition of that
  item**. BUG-0001 was already in that state. Correcting `created` is what lets the three bugs be
  worked at all.
- **`updated` on BUG-0002 and BUG-0003 → left at `2026-08-17T01:30:00Z`.** Corrected first,
  reverted after the validator showed `item.updated.stale`: `updated` must be ≥ the last history
  row, and that row may not be touched. It will be replaced by a clamped value on their next
  transition.
- **`created` on `EP-001/questions/Q-001.md` → `2026-08-16T22:30:00Z`.** Corrected: at the old
  value, EP-001's reopening row (`22:40:08Z`, true UTC) read as though the epic was reopened three
  hours *before* the question that caused it was asked.
- **Journal headings → true UTC**, in `EP-001`, `BUG-0001`, `BUG-0002` and `BUG-0003`, including
  the regression pass's own entries and my four. Journals have no untouchable counterpart, and
  correcting the filer's entries is what keeps each journal ordered once mine are corrected.
  `EP-001`'s closure entry was also skewed and is now `2026-08-16T22:15:48Z`, the timestamp of
  the history row it reports.
- **WI-0001's and WI-0002's journal headings → left as they are.** They carry the same +3h skew,
  nothing in them reads out of order, both items are closed and merged, and correcting a settled
  record for no observable benefit is churn against the append-only principle.

Every one of these is recorded as a correction, with the old value, the new value and the reason,
in the journal of the item it touched — this execution's entries on `BUG-0001`, `EP-001`,
`BUG-0002` and `BUG-0003`.

### 3. One row cannot be repaired by any skill, and it still blocks the workspace

`tracker/items/BUG-0001/history.md` row 6 is stamped `2026-08-16T22:44:02Z` — true UTC, written
by `transition` before the clamp existed — and it follows row 5's skewed
`2026-08-17T01:30:00Z`. After every correction above, that is the **only** finding left:

```
tracker/items/BUG-0001/history.md:6: ERROR [history.order] timestamp 2026-08-16T22:44:02Z is
    earlier than the previous row (2026-08-17T01:30:00Z)
validate-workspace: 1 error, 0 warnings
```

Nothing available to a skill reaches it. The clamp only applies to rows being appended; a later
row cannot repair an earlier pair; `transition` never rewrites; and the row may not be edited —
the hook denies it and this answer will not route around that. The repair is one value, and it is
exactly what the fixed tool would have written had it existed at the time: **restamp row 6 to
`2026-08-17T01:30:01Z`**, or give `transition` a one-shot `--restamp-last` for precisely this
case, which is the same act performed by the tool that owns the file. Either needs a hand that
may rewrite `history.md`; both leave the record honest, because the journal on both sides of it
says what happened and why.

Until then the workspace does not validate, so `next` will not dispatch and no item — including
BUG-0002 and BUG-0003, which are otherwise clean and unblocked — can be worked.

**Not escalated to the human.** The methodology question this asked has been answered by the
tooling; what remains is a one-row repair with an unambiguous value, not a decision. It is
reported rather than escalated.
