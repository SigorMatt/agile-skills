## Context

The fix is implemented and all six criteria are met in substance. AC6 reads:

> regression tests in `tests/` cover AC1, AC2, AC3 and AC5, and each fails against the code as it
> stands at `6d1e437b4293571296809b322c47fb0dc83d1ad6`. `python3 -m unittest discover` from the
> repository root exits 0

The first clause is satisfied: `UnresolvableEntryTest` covers all four. The second clause cannot
be satisfied for the AC5 test, and the reason is structural rather than an oversight in the
implementation.

AC5 is a criterion about behaviour that must **not** change:

> WI-0001 AC11 is unchanged: a folder that genuinely cannot be listed (a directory of mode `000`,
> tested as a non-root user) still prints nothing on stdout, one line on stderr naming that path
> and the problem, and exits 2

A test for unchanged behaviour passes against the old code by definition. If
`test_ac5_an_unreadable_folder_still_exits_2` failed at `6d1e437`, that would mean the old code
did **not** satisfy WI-0001 AC11 — which would be a different defect, and would contradict AC5's
own claim that the behaviour is unchanged. It is also what makes the test worth having: it is the
guard that this fix's `except OSError` did not swallow the folder's own error.

Measured, not argued. With `linecount.py` restored to `6d1e437` and the new tests in place:

```

FAIL: test_ac2_self_referential_symlink
FAIL: test_ac3_symlink_into_an_untraversable_directory
Ran 50 tests in 1.381s
FAILED (failures=3)
```

Three of the four fail, which is the strongest demonstration available: the three that assert new
behaviour fail without the fix, and the one that asserts preserved behaviour passes on both sides.

I have not edited AC6, and I am not blocked — the item is at `verifying` with every other
criterion demonstrated. But `verify` will read AC6 literally, find the AC5 test passing at
`6d1e437`, and have to decide whether that is a failure. Settling it here is cheaper than a
send-back.

## Question

AC6 requires each of the four regression tests to fail against `6d1e437`, but the AC5 test asserts
behaviour that is unchanged by this fix and therefore passes there by construction. How should
AC6 read?

## Options considered

- **A — scope the failing clause to the tests that assert new behaviour.** AC6 becomes: "…cover
  AC1, AC2, AC3 and AC5; the tests for AC1, AC2 and AC3 each fail against the code as it stands at
  `6d1e437`…". Consequence: the criterion becomes satisfiable and still demands exactly the proof
  that matters — no fix passes without demonstrating the defect. It is also the wording BUG-0002's
  AC7 already uses ("the tests for AC1–AC3 fail against the code as it stands"), so the two bugs
  would agree rather than differ by accident.
- **B — drop the AC5 test from AC6's list**, leaving AC6 to cover AC1–AC3 only. Consequence: the
  criterion is satisfiable, but the regression guard that the fix did not swallow the folder's own
  error is no longer required by any criterion — and that guard is the one most worth keeping,
  because it is what makes the `except OSError` safe.
- **C — leave AC6 as written and record the AC5 test as a declared exception** in the
  implementation and verification reports. Consequence: nothing is edited, but every future reader
  meets an unsatisfiable clause and has to re-derive why it was ignored, which is how a criterion
  quietly stops being a criterion.
- **Recommendation: A.** It keeps all four tests required, keeps the demonstration requirement
  where it is meaningful, and aligns BUG-0001's wording with BUG-0002's, which already says it
  correctly.

## Answer

**Option A.** AC6's failing clause is scoped to the tests that assert new behaviour. It now reads:

> regression tests in `tests/` cover AC1, AC2, AC3 and AC5; the tests for AC1, AC2 and AC3 each
> fail against the code as it stands at `6d1e437b4293571296809b322c47fb0dc83d1ad6`. `python3 -m
> unittest discover` from the repository root exits 0.

The answer comes from the record rather than from judgement, and from two places in it:

- **The criteria of this item's siblings.** BUG-0002 AC7, written by the same regression pass in
  the same hour, already says it correctly: "regression tests in `tests/` cover AC1, AC2, AC3 and
  AC4, and **the tests for AC1–AC3** fail against the code as it stands at `6d1e437`". BUG-0003
  AC6 says "each", but every test it lists (AC1, AC2, AC4) asserts new behaviour, so "each" is
  satisfiable there. BUG-0001's AC6 is the only one whose list mixes new behaviour with preserved
  behaviour and still says "each". This is a slip in one criterion, not a difference of intent
  across three.
- **The measurement `implement` recorded before asking.** With `linecount.py` restored to
  `6d1e437`: `FAILED (failures=3)` — the AC1, AC2 and AC3 tests fail, the AC5 test passes. A test
  for AC5 *must* pass there: AC5 says WI-0001 AC11 is unchanged, so if the test failed against the
  old code, the old code would not have satisfied WI-0001 AC11 — a different defect, and one the
  original verification would have caught.

What this amendment does **not** do is weaken the demand that made it worth asking about. Every
test that asserts behaviour this fix introduces must still be shown to fail without the fix, and
three were. The AC5 test stays required by AC6's first clause, because it is the guard that this
fix's `except OSError` did not swallow the folder's own error — the one way the change could have
been wrong.

Option B (dropping the AC5 test from AC6's list) was rejected for exactly that reason: it would
have made the most valuable regression guard optional. Option C (leaving the clause unsatisfiable
and noting the exception in reports) was rejected because every future reader would meet the
contradiction and have to re-derive why it was ignored, which is how a criterion quietly stops
being one.

**Not escalated to the human.** None of `spec/question.md` §4's four conditions applies: the
intent is recorded in the sibling criteria written by the same pass, the change is reversible in
one sentence, it contradicts no ADR or product document, and it is not a coin flip — the
measurement decided it. `implement` was right to file rather than edit: a developer amending the
criterion they are being judged against is the failure this protocol exists to prevent.
